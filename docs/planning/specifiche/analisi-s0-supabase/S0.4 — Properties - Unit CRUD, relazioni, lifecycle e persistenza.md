## S0.4 — Properties / Unit: CRUD, relazioni, lifecycle e persistenza

### Stato corrente

Il dominio Property / Unit è funzionalmente maturo e protetto da numerosi test, ma la sua persistenza è ancora fortemente accoppiata al `LocalDatabase`.

`PropertyRecord` contiene:

```text
PropertyRecord
├─ id
├─ createdAt
├─ updatedAt
├─ archived
├─ formData
├─ relations
│  ├─ buildingId
│  ├─ tenantIds[]
│  └─ leaseIds[]
├─ notes[]
├─ activities[]
├─ coordinates?
└─ legacy?
```

`formData` contiene attualmente gran parte dell'anagrafica della Unit: indirizzo, tipologia, caratteristiche, dati catastali, economici, pubblicazione, chiavi, contratti, foto, contatti e documenti.

Questa struttura rappresenta bene il form e il database JSON corrente, ma **non deve essere assunta come schema PostgreSQL definitivo**.

---

### Boundary di persistenza corrente

Il dominio non dispone ancora di una repository Property unificata.

Il CRUD principale usa direttamente:

```text
getJsonDb()
saveJsonDb()
getRecordById()
```

e opera quindi sul database globale dell'account attivo.

Questo riguarda almeno:

```text
createProperty
updateProperty
listProperties
getPropertyById
getPropertyRecordById
addPropertyNote
deletePropertyNote
updatePropertyVisibility
```

Il lifecycle è invece già separato tramite `propertyLifecycleRepository.ts`, con operazioni account-scoped:

```text
archive
restore
delete
archiveMany
restoreMany
deleteMany
subscribe
```

Situazione corrente:

```text
CREATE / UPDATE / READ / NOTES / VISIBILITY
→ accesso globale a jsonDb

LIFECYCLE
→ repository account-scoped
```

Per Supabase questa divisione dovrà essere ricondotta a una boundary Property coerente, asincrona e workspace-scoped.

---

### Create e update

La create segue attualmente questo ordine logico:

```text
normalize
→ business rules
→ verifica Building
→ costruzione record
→ una save
→ rilettura record persistito
```

La disciplina è valida e va preservata, mentre deve essere sostituita la persistenza tramite riscrittura dell'intero `LocalDatabase`.

L'update distingue correttamente:

```text
dati Property
```

da:

```text
relationPatch
```

La relazione con il Building cambia solo se viene modificata esplicitamente.

Un normale update della Unit deve quindi preservare:

```text
buildingId
tenantIds[]
leaseIds[]
```

salvo modifica esplicita della relazione Building.

---

### Relazione Property ↔ Building

Il contratto corrente è:

```text
Building 1
↓
Property N
```

La relazione è opzionale:

```text
Property.relations.buildingId: string | null
```

Una Property può quindi essere:

```text
standalone
collegata a Building
riassegnata
scollegata
```

`PropertyBuildingId` può esistere nel form/draft, ma **non appartiene al `formData` canonico persistito**.

L'authority corrente è:

```text
Property.relations.buildingId
```

Un Building archiviato può continuare a essere referenziato da Property già esistenti, ma non può ricevere nuove Unit né diventare destinazione di una nuova riassegnazione.

Questo contratto va preservato.

L'indirizzo del Building viene inoltre copiato nel form della nuova Unit creata dal contesto Building. Non esiste però un aggiornamento automatico successivo Building → Property; questa semantica dovrà essere valutata esplicitamente in S1/S5.

---

### Identità Property

Il CRUD corrente **non usa più titolo o indirizzo come chiavi uniche**.

Sono ammessi:

```text
titoli duplicati
indirizzi duplicati
stesso indirizzo nello stesso Building
```

Il vincolo applicativo corrente è la **chiave catastale completa**.

La chiave usa:

```text
PropertyCountry
PropertyCadastreMunicipalityCode
PropertyCadastreRegistryType
PropertyCadastreMunicipality
PropertyUrbanSection
PropertyCadastreSheet
PropertyCadastrePart
PropertyCadastreSub
```

La chiave esiste soltanto quando sono presenti almeno:

```text
country
municipalityCode
registryType
sheet
part
```

Se il catasto è incompleto:

```text
cadastralKey = null
```

e non viene applicato alcun duplicate matching.

La nuova create/update blocca una chiave catastale completa già esistente nello stesso account.

Il futuro schema Supabase dovrà preservare questa semantica con enforcement concurrency-safe a livello database/workspace.

Vecchi helper/errori relativi a unicità di titolo o indirizzo devono essere considerati residui da verificare, non constraint da trasferire automaticamente a PostgreSQL.

---

### Collisioni catastali legacy

Il database corrente può contenere collisioni catastali legacy.

Queste vengono segnalate come warning:

```text
PROPERTY_CADASTRAL_KEY_DUPLICATE
```

ma non vengono:

```text
riparate
rinominate
eliminate
riscritte
```

Principio da preservare:

```text
nuove write
→ regola forte

dati legacy
→ nessun repair distruttivo implicito
```

Poiché il database locale corrente contiene dati temporanei e non costituisce una produzione da importare automaticamente, queste collisioni non devono deformare il nuovo schema Supabase.

---

### Relazioni Property ↔ Lease ↔ Tenant

`PropertyRecord` conserva:

```text
relations.leaseIds[]
relations.tenantIds[]
```

ma queste informazioni sono proiezioni derivate.

Le authority reali sono:

```text
Lease.propertyId
Lease.tenantIds[]
```

Il sistema verifica infatti che gli array Property siano coerenti con le Lease.

Classificazione:

```text
Property.relations.buildingId
→ relazione Property autoritativa

Property.relations.leaseIds[]
→ derived

Property.relations.tenantIds[]
→ derived
```

Nel modello PostgreSQL non devono essere trasferite automaticamente come array duplicati se possono essere ricavate dalle relazioni SQL.

---

### Stato della Unit

`PropertyStatusManual` non è l'unica authority dello stato locativo.

Lo stato effettivo della Unit dipende anche dalle Lease correnti.

Il sistema può infatti segnalare l'incoerenza:

```text
PropertyStatusManual = affittato
+
nessuna Lease corrente
```

Lo schema futuro dovrà quindi evitare una seconda authority indipendente sulle condizioni locative.

---

### Lifecycle

Il lifecycle è già ben definito:

```text
active
↔
archived
```

Archive/restore:

```text
modificano archived
aggiornano updatedAt
preservano formData
preservano Building
preservano relazioni
preservano nested IDs
preservano storico
```

L'archiviazione della Property non modifica il conteggio delle Unit appartenenti al Building.

---

### Delete

La cancellazione di una Property è consentita soltanto se la Unit non conserva storico persistente.

Il delete viene bloccato da:

```text
qualunque Lease riferita alla Property
qualunque Payment riferito alla Property
```

anche quando la Lease è storica, terminata o archiviata.

Semantica da preservare:

```text
Property con storico
→ DELETE bloccata
→ usare archive
```

Non esiste cascade distruttivo:

```text
DELETE Property
≠
DELETE Lease
≠
DELETE Payment
```

Il futuro database dovrà rafforzare questo comportamento con relazioni e constraint appropriati.

La cancellazione di una Property libera collegata a un Building deve eliminare soltanto la Unit; il Building rimane.

---

### Operazioni bulk

Le operazioni bulk hanno semantica all-or-nothing:

```text
archiveMany
restoreMany
deleteMany
```

Contratti da preservare:

```text
dedup degli ID
empty selection = no-op
validazione completa prima della mutation
bulk delete bloccata integralmente se almeno una Unit ha blocker
nessuna partial mutation
un'unica operazione atomica
```

Nel target Supabase non devono essere implementate come loop di mutation indipendenti.

---

### Read-model

La lista Property non deriva soltanto dalla tabella/property collection.

Per costruire il modello visualizzato vengono letti anche:

```text
Leases
Tenants
```

Il dettaglio Property usa inoltre:

```text
Property
Tenant
Leases
Payments
Notes
Activities
```

e costruisce anche un primo read-model finanziario con:

```text
grossIncome
expenses
netResult
occupancyRate
profitabilityNet
monthly chart
```

Questo implica che il target dovrà distinguere:

```text
Property entity repository
```

da:

```text
Property list read-model
Property detail read-model
Property finance read-model
```

senza ricostruire l'intero `LocalDatabase` nel client.

---

### Consumer runtime

`usePropertiesDb()` e `usePropertyDetail()` dipendono ancora da:

```text
listProperties/getPropertyById
+
subscribeJsonDb()
```

con authority globale dell'account attivo.

Questi consumer dovranno essere rifattorizzati verso query/repository asincrone e workspace-scoped.

---

### Notes e Activities

Le note sono attualmente embedded:

```text
Property.notes[]
```

e vengono mutate riscrivendo la Property/database corrente.

Sono candidate a diventare dati figli autonomi nel modello relazionale, decisione da prendere in S1.

Anche:

```text
Property.activities[]
```

è embedded, ma il suo writer/ruolo autoritativo non è ancora completamente chiarito.

Owner residuo:

```text
S0.11
```

prima della modellazione definitiva.

---

### Nested IDs

Devono essere preservati gli ID persistenti di almeno:

```text
PropertyCadastreDocument.id

PropertyKeys[].id

PropertyContracts[].id
PropertyContracts[].file.id

PropertyPhotos[].id

PropertyContacts[].id

PropertyDocuments[].id
PropertyDocuments[].file.id
```

I test verificano la loro conservazione attraverso:

```text
normalizzazione
draft
create
persistenza
reload
```

Il futuro schema non deve rigenerare arbitrariamente questi ID durante la lettura o l'aggiornamento.

---

### File

Foto e documenti sono attualmente memorizzati come `StoredLocalFile`:

```text
id
name
type
size
lastModified
dataUrl
```

Questo modello fisico è transitorio.

Target:

```text
PostgreSQL
→ metadata e relazioni

Supabase Storage
→ file binari
```

Il passaggio fisico sarà responsabilità di S7.

I limiti correnti di dimensione/formato file sono invece regole prodotto da riesaminare separatamente e non devono essere confusi con il limite tecnico del localStorage.

---

### Property Contacts

La UI dichiara che i contatti aggiunti alla Property vengono salvati nella rubrica, ma l'implementazione corrente li conserva soltanto in:

```text
PropertyContacts[]
```

dentro il form Property.

Non viene creato automaticamente un `ContactRecord`.

Esiste quindi un disallineamento:

```text
promessa UI
≠
persistence reale
```

La modellazione definitiva dovrà essere risolta dopo S0.5:

```text
Property Contact
→ relazione verso Contact canonico
```

oppure:

```text
Property Contact
→ snapshot specifico della Property
```

senza mantenere ambiguità.

---

### Property Documents

Anche i documenti Property sono attualmente embedded in:

```text
PropertyDocuments[]
```

nonostante la UI suggerisca il salvataggio nella sezione Documenti.

Non viene creato automaticamente un `DocumentRecord` globale.

Owner della decisione:

```text
S0.9 → inventario Documents corrente
S1/S7 → modello relazionale + Storage definitivo
```

---

### Draft

Il flusso Property Draft è già compatibile con callback asincrone e preserva una semantica utile:

```text
business mutation riuscita
→ cleanup draft fallisce
→ retry soltanto cleanup
→ nessuna seconda create/update
```

Questa parte è **KEEP** e può essere adattata alla futura repository Supabase.

### Conclusione

Property / Unit non deve essere migrata copiando il `PropertyRecord` corrente in una tabella con `formData JSONB`.

Il modello corrente contiene insieme:

```text
core Property
relazione Building
catasto
dati economici
pubblicazione
nested collections
file
read-model derivati
relazioni duplicate
```

La migrazione dovrà preservare le business rule già consolidate, ma decomporre il modello in una struttura relazionale coerente.

In particolare:

```text
PropertyFormData
= contratto del form/prototipo corrente

PropertyFormData
≠ schema PostgreSQL definitivo
```

Le decisioni concrete su tabelle, colonne, JSONB eventuali, child entity, Contacts, Documents, files e read-model vengono rinviate a S1 dopo il completamento di S0.5–S0.11.
