## S0.11 — Consumer, read-model, selector, subscription e dipendenze runtime

### Stato verificato

La persistence runtime corrente non viene consumata attraverso un'unica architettura.

Coesistono quattro modalità principali:

```text
1. repository async iniettati
   → Contacts
   → Drafts

2. repository account-scoped creati direttamente dai consumer
   → Buildings
   → parte Tenant
   → lifecycle Property

3. raw account scope
   → createJsonDbAccountScope(accountId)
   → Building detail
   → SearchBar

4. global active database
   → getJsonDb()
   → saveJsonDb()
   → subscribeJsonDb()
   → Property
   → parte Tenant
   → Lease
   → Payment
   → Documents
   → Dashboard
   → read-model vari
```

La migrazione Supabase non sarà quindi completa con la sola sostituzione dello storage: anche i consumer devono smettere di dipendere dal `LocalDatabase` globale.

---

## Composition root corrente

L'application root monta:

```text
QueryClientProvider
→ AuthProvider
→ Router
```

Nel root autenticato vengono iniettati solamente:

```text
DraftRepositoryProvider
ContactRepositoryProvider
```

Contacts e Drafts rappresentano quindi il pattern di composition più maturo.

Gli altri domini costruiscono spesso direttamente repository concrete oppure accedono a `jsonDb`.

### Conclusione S0

La scelta del concrete adapter deve spostarsi verso la composition applicativa.

Il target non deve diventare:

```text
UI
→ supabase.from(...)
```

ma:

```text
UI
→ repository / command / query
→ Supabase adapter
→ PostgreSQL / Storage
```

Non è necessario decidere in S0 il numero esatto di Context React o provider.

---

## Repository e read-model sono responsabilità differenti

Molte schermate non leggono una singola entity, ma aggregano diversi domini.

Esempi:

```text
Building detail
→ Building + Properties

Property list/detail
→ Property + Lease + Tenant + Payment

Tenant list/detail
→ Tenant + Lease + Property + Payment

Lease list/detail
→ Lease + Property + Tenant + Contact
  + Payment + Document + Message

Dashboard
→ Property + Tenant + Lease + Payment

Search
→ Property + Tenant + Lease
```

Il target dovrà distinguere:

```text
ENTITY REPOSITORY / COMMAND
→ authority e mutation

QUERY / READ-MODEL
→ composizione read-only di più authority
```

Non devono essere create repository monolitiche soltanto per replicare il vecchio `LocalDatabase`.

---

## Contacts e Drafts

Contacts e Drafts possiedono già port async indipendenti dallo storage e adapter locali separati.

Il Contact list store gestisce inoltre:

* loading;
* ready/error;
* stale response protection;
* refresh asincrono;
* lifecycle della subscription.

Questo pattern è già compatibile concettualmente con una persistence remota.

Classificazione:

```text
repository ports
→ KEEP

async semantics
→ KEEP

local adapters
→ REPLACE

concrete adapter scelto nel Provider
→ ADAPT alla composition Supabase
```

---

## Buildings

Buildings utilizza già repository account-scoped per list e mutation.

Il detail utilizza invece direttamente `createJsonDbAccountScope(accountId)` per leggere:

```text
Building
+
Properties collegate
```

Questo dimostra che Building detail è un read-model cross-domain e non una semplice `getById()` della repository.

Target:

```text
BuildingRepository
→ entity / commands

BuildingDetailQuery
→ Building + Units
```

Il raw account scope resta transitorio.

---

## Properties

Il dominio Property è ancora fortemente misto.

La lista usa:

```text
listProperties()
+
subscribeJsonDb()
```

globali.

Il lifecycle usa invece repository account-scoped.

Il detail combina:

* read-model globale;
* note mutation globali;
* visibility mutation globale;
* lifecycle repository scoped.

Create/edit restano prevalentemente globali.

`propertyRepository.ts` contiene oggi contemporaneamente:

* CRUD;
* lifecycle bridge;
* list projection;
* detail projection;
* cross-domain reads;
* financial summary;
* notes;
* visibility commands.

### Conclusione S0

Property richiede una separazione fra:

```text
PropertyRepository / Commands
PropertyListQuery
PropertyDetailQuery
```

Non basta sostituire `getJsonDb()` con query Supabase dentro il file corrente.

---

## Tenants

Tenant possiede più path runtime differenti:

```text
create
→ global bridge

edit
→ repository scoped

list
→ global read-model

detail
→ global read-model

lifecycle
→ repository scoped

invite
→ global
```

Il dominio deve convergere verso dependency workspace-scoped coerenti.

Target concettuale:

```text
TenantRepository / Commands
TenantListQuery
TenantDetailQuery
TenantInvitationCommand
```

Il form Tenant Documents contiene inoltre un accesso diretto:

```text
getJsonDb().documents
```

per il document picker.

Questo dovrà diventare una query/reference dependency esplicita e non un accesso diretto alla tabella/storage.

---

## Leases

Lease list/detail usano ancora:

```text
global repository functions
+
subscribeJsonDb()
```

e `LeasesPage` esegue anche letture dirette di Property e Lease dal `LocalDatabase`.

Il detail è già un aggregate read-model che alimenta tab dedicate a:

* overview;
* payments;
* participants;
* documents;
* contract;
* signature;
* activity.

Le mutation sono invece vere domain command.

Target:

```text
LeaseCommands
├─ create
├─ update
├─ activate
├─ deactivate
├─ terminate
├─ archive
├─ restore
└─ delete

LeaseQueries
├─ list
├─ detail
├─ byProperty
└─ byTenant
```

Le command multi-table restano owner di S6.

---

## Payments

Payments vengono letti da:

```text
Lease
Tenant
Property
Dashboard
```

ma le mutation hanno semantiche specifiche:

```text
createManualPayment
updateManualPayment
deleteManualPayment
confirmPaymentPaid
markPaymentUnpaid
registerDepositReturn
applyPrepaidRent
```

Il target non deve quindi esporre un CRUD generico finanziario che permetta di bypassare le business rule.

Separazione concettuale:

```text
PaymentCommands
→ mutation economiche

FinancialQueries
→ Lease/Tenant/Property/Dashboard read-model
```

---

## Dashboard

Dashboard non è un dominio persistence.

Il repository corrente legge più collection e calcola:

* conteggi;
* ricavi;
* costi;
* arretrati;
* risultato netto;
* serie temporali;
* distribuzioni per Property.

Quindi:

```text
Dashboard
→ analytics/read-model layer
```

e non deve diventare una tabella dedicata solo per replicare il codice locale.

Il modello corrente:

```text
qualunque DB mutation
→ subscribeJsonDb()
→ ricalcolo dashboard
```

è troppo coarse per un sistema multiutente.

Il target dovrà invalidare/refetch soltanto le query interessate.

---

## Search

SearchBar costruisce oggi un indice account-scoped leggendo direttamente:

```text
Properties
Tenants
Leases
```

Non risultano realmente indicizzati, allo stato verificato:

```text
Contacts
Documents
Finance
```

anche se alcuni tipi UI li contemplano.

La ricerca globale è quindi un vero read-model cross-domain:

```text
WorkspaceSearchQuery
```

e non deve appartenere a una singola repository entity.

La protezione stale-scope introdotta in C10-F01 è invece da preservare:

```text
result/query snapshot
→ associato allo scope che lo ha prodotto
```

---

## `dataSelectors.ts`

Il file contiene categorie differenti di logica.

### Pure/domain rule

Esempi:

* classificazione Lease;
* Payment overdue/collected;
* tenant display name.

Queste logiche possono essere mantenute.

### Selector legati al `LocalDatabase`

Esempi:

* Lease correnti per Property/Tenant;
* Tenant status;
* Tenant balance;
* Property financial summary.

Questi devono essere adattati a dati query-specifici oppure sostituiti da query/aggregazioni database.

### Projection persistite

Sono già stati identificati come derived/non-authority:

```text
Building.unitsCount
Property.relations.tenantIds[]
Property.relations.leaseIds[]
Tenant.leaseIds[]
effective Property status
effective Tenant status
Lease temporalStatus
Tenant balance
Lease balance
Property financial summary
Dashboard financial stats
```

Il target non deve trasformarli automaticamente in authority persistite indipendenti.

---

## Property activities e Lease activities

`Property.activities[]` è attualmente leggibile dal detail, ma non è stato identificato un writer business runtime significativo nel codice Property analizzato.

Quindi non deve essere trasformato automaticamente in un nuovo audit domain.

`Lease.activity[]`, invece, possiede writer verificati da:

* Lease lifecycle/update;
* Payments;
* Documents;
* Communications;
* Signature.

Ha quindi una vera natura di audit/event stream.

Il modello corrente:

```text
leggi activity[]
→ append in memoria
→ riscrivi aggregate
```

è vulnerabile a lost update multiutente.

Target concettuale:

```text
domain command
→ business mutation
→ append LeaseActivity
```

nella stessa transaction.

---

## Subscription corrente

`subscribeJsonDb()` funziona come event bus globale.

Una mutation produce un evento e i consumer rileggono il proprio snapshot.

Il meccanismo supporta:

* stessa tab;
* browser `storage` event;
* database account locale.

Non rappresenta però realtime multiutente.

### Contratto da preservare

```text
mutation rilevante
→ read-model interessato deve aggiornarsi
```

### Implementazione da sostituire

```text
whole DB event
→ refresh generalizzato
```

Supabase Realtime non deve essere adottato automaticamente su ogni tabella.

Le future strategie possono includere:

* mutation → query invalidation;
* refetch;
* Realtime dove utile;
* refresh al focus;
* combinazioni.

La scelta è rinviata a S3 e alle singole fasi.

---

## Async runtime

Molti hook correnti presuppongono storage sincrono:

```text
useState(() => listProperties())
useState(() => listTenants())
useState(() => listLeaseItems())
useState(() => getDashboardStats())
```

Con Supabase devono diventare honest-async e rappresentare realmente:

```text
loading
ready
error
refresh/stale
```

Contacts dimostra già un pattern valido.

---

## Query cache

TanStack Query è già disponibile nella root applicativa e la cache viene svuotata quando cambia account.

Non governa però ancora la maggior parte dei business data.

S0.11 non stabilisce che tutti i consumer debbano usare obbligatoriamente TanStack Query.

Stabilisce soltanto che il target deve avere:

```text
async reads
+
scope esplicito
+
cache/invalidation coerenti
```

La strategia concreta appartiene a S3.

---

## Filtering, sorting e pagination

Le list page caricano oggi l'intera collection e successivamente filtrano/sortano client-side.

Le semantiche funzionali di filtro e ordinamento devono essere preservate.

Non deve invece essere preservato come contratto:

```text
list()
→ carica sempre tutto
```

Il target deve consentire progressivamente:

* filtering;
* sorting;
* search;
* pagination;

lato query/database quando necessario.

L'attuale page size UI non costituisce vera database pagination.

---

## UI preference locali

Non ogni utilizzo di `localStorage` deve essere eliminato.

Esempi:

```text
properties-column-visibility
tenants-column-visibility
```

sono preferenze UI/browser e non business data condivisi.

Quindi:

```text
rimozione jsonDb
≠
rimozione totale localStorage
```

Le preference UI possono restare locali salvo futura decisione prodotto.

---

## Static resources e stato non persistente

Non appartengono alla business migration:

* onboarding state corrente;
* navbar mock alerts;
* component state;
* static Document Templates;
* static Property/Lease catalogs;
* altre risorse applicative statiche.

Le collection `EmptyRecord[]` già identificate in S0.9 non hanno mostrato un runtime owner reale e non devono diventare tabelle per inerzia.

## Cutover criterion

La migration non è completa quando esistono semplicemente le nuove tabelle Supabase.

È completa quando nessun runtime business consumer dipende più da:

```text
getJsonDb()
saveJsonDb()
subscribeJsonDb()
createJsonDbAccountScope()
LocalDatabase come mega-read-model
```

`createJsonDbAccountScope()` è migliore del singleton globale, ma rimane comunque un adapter transitorio al vecchio database locale.

---

## Authority durante la transizione

Ogni capability deve avere una sola authority runtime esplicita.

Da evitare:

```text
Tenant list
→ Supabase

Tenant detail
→ local

Tenant edit
→ Supabase

Tenant invite
→ local
```

come stato indefinito.

La migrazione può essere progressiva, ma non deve introdurre:

```text
implicit dual-write
silent local fallback
authority ambigua
```

## Keep / Adapt / Delete

### KEEP

* repository ports esistenti;
* business rule pure;
* explicit scoping;
* async contracts;
* stale-response protection;
* mutation → invalidation concept;
* DTO/read-model utili alla UI;
* client filtering/sorting quando appropriato;
* browser-local preference non business.

### ADAPT / REFACTOR

* repository ancora sincroni;
* page-level creation di concrete repository;
* `use*Db` hooks;
* list/detail read-model;
* Dashboard analytics;
* Search;
* selector legati al `LocalDatabase`;
* subscription/invalidation;
* Property/Tenant/Lease query layer;
* form lookup verso altri domini;
* Lease activity verso append-oriented audit model.

### DELETE / REPLACE

* global active database access;
* raw `getJsonDb()` nei consumer;
* raw `saveJsonDb()` nei consumer;
* `subscribeJsonDb()` come business event bus;
* `createJsonDbAccountScope()` come runtime persistence definitiva;
* whole `LocalDatabase` come query contract;
* sync reads come assunzione generale;
* whole-DB refresh;
* accesso diretto alle collection dai componenti;
* read-time mutation/repair.

## Implicazioni per S3


La decomposizione definitiva verrà stabilita in S0.12.

### Conclusione S0.11

Il runtime corrente può essere sintetizzato come:

```text
UI
├─ repository iniettati
├─ repository creati localmente
├─ raw account DB scope
└─ global active LocalDatabase
          ↓
   whole-db subscription
          ↓
   coarse refresh
```

Il target deve diventare:

```text
Auth User
→ Workspace / user scope
→ Application composition
   ├─ Entity repositories
   ├─ Transactional commands
   ├─ List/detail queries
   ├─ Analytics queries
   ├─ Search queries
   ├─ Draft repository
   └─ Document/Storage services
→ PostgreSQL / Storage
→ RLS + constraints + transactions
```

Regole definitive:

```text
query
→ side-effect free

command
→ mutation esplicita e atomica

derived data
→ non seconda authority

consumer
→ nessun accesso diretto allo storage

subscription/invalidation
→ scoped al read-model interessato
```

S0.11 completa quindi la mappa dei consumer necessaria per costruire in S0.12 la matrice finale della persistence e la decomposizione definitiva delle fasi S1–S7.
