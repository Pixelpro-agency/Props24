## S0.10 — Auth locale, account isolation e composition root

### File analizzati

* `src/auth/auth.types.ts`
* `src/auth/authStorage.ts`
* `src/auth/AuthContext.tsx`
* `src/router.tsx`
* `src/App.tsx`
* `src/db/jsonDb.ts`
* `tests/navigation/appRouter.test.tsx`
* `tests/navigation/logoutDatabaseTeardown.integration.test.tsx`
* `tests/navigation/unsavedChangesLogout.integration.test.tsx`
* `tests/contacts/contactRepositoryComposition.test.ts`
* `tests/db/draftRepositoryContext.test.tsx`

Sono inoltre considerate le evidenze già emerse in S0.3–S0.9 sui consumer che utilizzano repository account-scoped o accessi globali a `jsonDb`.

### Stato verificato

**VERIFICATO NEL CODICE**

L'autenticazione corrente è una simulazione interamente locale.

`LocalAccount` contiene identità anagrafica, email, codice fiscale, password in chiaro e ID locale `user-NNN`. `LocalSession` contiene solamente `accountId`.

Gli account e la sessione sono salvati in `localStorage` tramite:

* `props24.auth.accounts`
* `props24.auth.session`

Non esistono token, scadenza sessione, verifica server-side, membership, workspace o autorizzazione server-side.

La password locale e l'intero meccanismo di sessione sono codice prototipale da sostituire, non dati o contratti da migrare in PostgreSQL.

### Relazione Auth → persistenza corrente

**VERIFICATO NEL CODICE**

`AuthContext` controlla direttamente anche la persistence business tramite `setActiveDatabaseAccount()`.

Il flusso corrente è:

```txt
LocalAccount autenticato
→ account.id
→ setActiveDatabaseAccount(account.id)
→ props24.localDb.<accountId>
→ LocalDatabase dell'account
```

Login, registrazione, restore della sessione e logout modificano quindi sia lo stato Auth sia il singleton globale del database attivo.

`jsonDb.ts` mantiene `activeDatabaseAccountId`; gli accessi globali `getJsonDb()` / `saveJsonDb()` dipendono dall'account attivo corrente e falliscono se non esiste un account autenticato.

### Account isolation corrente

**VERIFICATO NEL CODICE**

Ogni account locale possiede un database separato:

```txt
user-001 → props24.localDb.user-001
user-002 → props24.localDb.user-002
...
```

L'account predefinito può essere inizializzato dal seed `database.json`; gli account secondari iniziano con database vuoto.

Questo fornisce isolamento logico dei dati nel browser, ma non permette collaborazione: due utenti distinti non possono operare sullo stesso insieme di Buildings, Properties, Tenants, Leases, Payments, Contacts e Documents.

L'account locale è quindi oggi contemporaneamente:

* identità autenticata;
* profilo personale;
* chiave di sessione;
* owner/scope dei dati business;
* chiave fisica della persistence.

### Conclusione sul target di isolamento

**CONCLUSIONE S0**

La migrazione non deve sostituire semplicemente `accountId` con `auth.uid()` nelle tabelle business.

Un modello `row.user_id = auth.uid()` ricreerebbe nel cloud lo stesso isolamento one-user/one-database e non soddisferebbe il requisito di collaborazione.

Il target dovrà separare almeno concettualmente:

```txt
Authenticated User
→ Membership
→ Workspace
→ business data condivisi
```

La workspace sarà la boundary minima necessaria per permettere a più utenti autorizzati di operare sugli stessi dati.

Ruoli avanzati, deleghe complete, tenant portal e permission matrix definitiva restano fuori da S0.10 e non devono essere considerati automaticamente completati dalla migrazione.

### Auth user, Profile e business identity

**CONCLUSIONE S0**

L'attuale `LocalAccount` deve essere scomposto concettualmente.

Target preliminare:

```txt
Authenticated User
├─ identità Auth sicura
└─ sessione

Profile
└─ dati personali applicativi

Workspace Membership
├─ user
└─ workspace

Workspace
└─ scope dei business data
```

Potrebbe inoltre essere necessario distinguere il soggetto/business profile rappresentato dall'utente autenticato.

Questo è rilevante perché S0.9 ha già verificato due authority differenti:

* Navbar/display profile → `AuthContext.account`
* dati locatore usati dalle ricevute → `LocalDatabase.userProfile`

Un collaboratore autenticato non coincide necessariamente con il soggetto locatore rappresentato dal workspace.

La modellazione definitiva è rinviata a S1/S2.

### Composition root corrente

**VERIFICATO NEL CODICE**

La root applicativa compone:

```txt
QueryClientProvider
→ AuthProvider
→ RouterProvider
```

Nel root autenticato vengono inoltre montati:

```txt
DraftRepositoryProvider(accountId)
→ ContactRepositoryProvider(accountId)
→ Layout
→ Outlet
```

Contacts e Drafts rappresentano quindi già un primo modello di dependency composition esplicita.

I relativi test verificano che repository costruite con account differenti restino isolate anche quando cambia il global active account.

Principio da preservare:

> una repository deve catturare esplicitamente il proprio scope e non dipendere dal singleton globale dell'account attivo.

La composition root è però incompleta: molti altri domini continuano a utilizzare direttamente o indirettamente `getJsonDb()` / `saveJsonDb()`.

### Target della composition

**CONCLUSIONE S0**

Supabase non deve essere chiamato direttamente da pagine e componenti in sostituzione di `getJsonDb()`.

Il target deve mantenere una separazione del tipo:

```txt
UI
→ repository / command / query
→ Supabase adapter
→ PostgreSQL / Storage
```

`AuthContext` dovrà inoltre smettere di selezionare direttamente lo storage business.

Il flusso concettuale target sarà:

```txt
Supabase Auth session
→ Authenticated User
→ workspace/membership resolution
→ workspace-scoped dependencies
→ PostgreSQL + RLS
```

Non tutte le repository devono necessariamente usare lo stesso scope. I business data saranno normalmente workspace-scoped; dati personali come le Drafts potrebbero richiedere una combinazione user + workspace/entity context.

### Sicurezza

**CONCLUSIONE S0**

Lo scope applicativo passato dal frontend serve alla correttezza, ma non costituisce una security boundary.

Il target deve usare autorizzazione server-side/RLS per verificare che l'utente autenticato abbia accesso al workspace richiesto.

Quindi:

```txt
frontend scope
→ dependency/query correctness

RLS / server authorization
→ authority di sicurezza
```

### Cache e teardown

**VERIFICATO NEL CODICE**

`AuthenticatedRootRoute` esegue `queryClient.clear()` quando cambia `accountId`, impedendo il riuso immediato della cache appartenente allo scope precedente.

Il logout possiede inoltre contratti già testati da preservare:

* nessun business access dopo il teardown dello scope;
* smontaggio della UI autenticata;
* nessun errore da consumer rimasti temporaneamente montati;
* logout dirty intercettato dal navigation guard;
* save/discard completati prima del logout;
* fallimento di save/discard mantiene sessione e form attivi;
* operazioni concorrenti/doppi click serializzati.

Il regression test C10-F01 dimostra inoltre che Auth state e persistence state possono attraversare brevemente fasi diverse durante il teardown. Il target deve quindi gestire esplicitamente cleanup di query, subscription e dependency scoped.

### Keep / Adapt / Delete

**KEEP**

* `AuthContext` come boundary UI, rifattorizzato;
* stato `isAuthenticated` / initialization;
* API pubbliche async di login/register/logout;
* route authentication gate;
* unsaved-changes guard prima del logout;
* invalidazione dei dati client quando cambia scope;
* principio di repository scoped esplicitamente;
* composition pattern già usato da Contacts/Drafts.

**ADAPT / REFACTOR**

* profilo utente;
* repository providers/composition root;
* query cache scope;
* logout/session teardown;
* distinzione fra user-scoped e workspace-scoped dependencies.

**DELETE / REPLACE**

* password salvate localmente;
* registry `props24.auth.accounts`;
* sessione locale `{ accountId }`;
* ID `user-NNN` come identity target;
* `AuthContext → setActiveDatabaseAccount`;
* singleton `activeDatabaseAccountId`;
* `getJsonDb()` / `saveJsonDb()` come scope implicito;
* automatic seed locale associato al nuovo account;
* localStorage come authority Auth.

**ADD**

* Auth reale;
* minimal workspace/membership boundary;
* workspace-scoped business access;
* server-side authorization/RLS;
* composition root coerente per gli adapter Supabase.

### Implicazioni per le fasi successive

**S1**
Definire il modello target di user, profile, workspace, membership, business-data scope ed eventuale business/landlord profile.

**S2**
Introdurre Supabase Auth e la minima infrastruttura workspace/membership necessaria alla condivisione sicura dei dati.

**S3**
Eliminare progressivamente il global `jsonDb` dai consumer e comporre repository/query async scoped tramite dependency esplicite.

**S7**
Rimuovere definitivamente auth localStorage, account DB keys, singleton active database, local adapters residui e seed runtime quando nessun consumer li utilizza più.

### Conclusione S0.10

Il modello corrente è:

```txt
LocalAccount
→ Auth session
→ activeDatabaseAccountId
→ database locale per account
→ business data
```

È adeguato al prototipo locale e garantisce separazione fra account, ma lega identità, profilo, authorization scope e persistence in un unico concetto.

Il target Supabase deve eliminare l'equazione:

```txt
utente = database
```

e introdurre:

```txt
utente autenticato
→ membership
→ workspace condiviso
→ repository/query scoped
→ PostgreSQL protetto da RLS
```

La composition esplicita già presente per Contacts e Drafts è il pattern architetturale da estendere; il global active database è invece una dependency transitoria da eliminare.
