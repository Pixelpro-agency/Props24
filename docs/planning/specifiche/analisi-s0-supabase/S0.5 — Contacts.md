## S0.5 — Contacts

### Stato attuale

`ContactRecord` è un'entità autonoma relativamente semplice e già adatta a una futura persistenza relazionale. Contiene dati anagrafici, fiscali, recapiti, indirizzo, note, lifecycle e timestamp, senza grandi strutture embedded o file.

Il dominio dispone già di un vero contratto asincrono:

```text
ContactRepository
├─ list
├─ getById
├─ create
├─ update
├─ archive
├─ restore
├─ canDelete
├─ delete
└─ subscribe
```

`ContactRepository` non dipende da `LocalDatabase` o `localStorage`.

L'implementazione corrente è:

```text
ContactRepositoryProvider
→ createLocalContactRepository(accountId)
→ createJsonDbAccountScope(accountId)
→ createContactRepositoryOperations(...)
→ LocalDatabase.contacts
```

Il provider è già montato nel root autenticato, quindi il dominio possiede una buona composition boundary.

### CRUD corrente

Create:

```text
input
→ normalizzazione
→ validazione tipo person/company
→ controllo unicità fiscale
→ generazione ID
→ archived = false
→ timestamp
→ save dell'intero LocalDatabase
→ reread del Contact persistito
```

Update:

```text
lookup Contact
→ merge patch
→ normalizzazione
→ controllo unicità fiscale escludendo il record corrente
→ preservazione managed fields
→ updatedAt
→ whole-database save
```

Archive/restore modificano `archived` e `updatedAt`.

Il delete è consentito soltanto se il Contact non è referenziato da:

```text
Lease.guarantorIds[]
Tenant.guarantors[].contactId
Tenant.emergencyContacts[].contactId
```

Non esiste cascade.

### Identità fiscale

Le regole correnti sono:

```text
Contact person
→ fiscalCode, se valorizzato

Contact company
→ fiscalCode e/o vatNumber, se valorizzati
```

Normalizzazione:

```text
NFKC
→ rimozione whitespace
→ uppercase
```

Gli identificatori vuoti non costituiscono identità e quindi non collidono.

I Contact archived continuano a partecipare ai controlli di unicità.

L'email è un recapito, non una chiave di identità.

L'identità fiscale Contact è separata da quella Tenant:

```text
Contact ↔ Contact
Tenant ↔ Tenant
```

Non esiste duplicate matching fiscale cross-domain.

Con Supabase/PostgreSQL il controllo applicativo dovrà essere mantenuto per UX e messaggi di errore, ma rafforzato con constraint database concurrency-safe.

### Relazioni Tenant ↔ Contact

Tenant usa Contact tramite relazioni proprie.

Per un garante o contatto di emergenza:

```text
relation.id
≠
contactId
```

`relation.id` identifica la relazione Tenant.

`contactId` identifica il Contact canonico.

Le relazioni mantengono inoltre uno snapshot dei dati anagrafici e metadata propri, per esempio:

```text
comments
isPrimary
```

Questi metadata non appartengono al Contact canonico.

Collegare un Contact esistente non modifica il Contact.

I dati canonici aggiornati possono essere mostrati dopo refresh della rubrica, mentre metadata e identità della relazione restano separati.

### Riferimenti archived, missing e legacy

Per nuove relazioni vengono utilizzati soltanto Contact validi e attivi.

Un riferimento già persistito verso un Contact archived o missing viene invece preservato insieme allo snapshot.

Regola:

```text
existing historical/broken reference
→ preserve

new invalid reference
→ block
```

Esistono inoltre relazioni Tenant legacy senza `contactId`.

Non deve essere eseguito alcun matching euristico.

In particolare:

```text
relation.id == Contact.id
```

non significa che esista una relazione con quel Contact.

Solo `contactId` esplicito costituisce il collegamento canonico.

### Emergency Contact

Per essere utilizzato come contatto di emergenza un Contact deve avere un telefono valido.

`isPrimary` appartiene alla relazione Tenant e il dominio mantiene la semantica di un solo contatto principale.

Queste regole saranno approfondite in S0.6.

### Lease ↔ Contact

Lease usa invece riferimenti diretti:

```text
Lease.guarantorIds[]
→ Contact.id
```

Il writer Lease verifica attualmente l'esistenza dei Contact selezionati.

È però da verificare in S0.7 se un Contact archived debba essere rifiutato anche dal writer Lease, perché il controllo attuale verifica l'esistenza ma non esplicitamente `archived === false`.

### PropertyContacts

`PropertyContacts[]` non è attualmente collegato alla rubrica Contact canonica.

Il fatto che `ContactRepository.canDelete()` non consideri `PropertyContacts` conferma che i due concetti sono oggi indipendenti.

Non devono essere unificati implicitamente durante la migrazione.

Decisione rinviata a S0.9/S1.

### Subscription

`contactListStore` dipende esclusivamente da `ContactRepository` e usa:

```text
repository.list()
repository.subscribe()
```

La subscription funziona come invalidazione seguita da refresh.

Questa architettura è compatibile con una source remota.

La futura implementazione potrà usare invalidazione locale, Supabase Realtime o altro meccanismo; la decisione appartiene a S0.11/S3.

### Debito tecnico locale

Restano wrapper legacy sincroni:

```text
listContacts
getContactById
createContact
updateContact
archiveContact
restoreContact
canDeleteContact
deleteContact
```

che usano direttamente:

```text
getJsonDb
saveJsonDb
```

Devono essere eliminati dopo il cutover di tutti i consumer.

`ContactDatabaseGateway` espone ancora:

```text
getDatabase()
saveDatabase(LocalDatabase)
```

ed è utile soltanto per l'implementazione locale corrente.

Non deve essere trasformato in un adapter Supabase che scarica e riscrive l'intero database.

### Target concettuale

```text
authenticated user
→ workspace membership
→ ContactRepository
→ SupabaseContactRepository
→ contacts PostgreSQL
```

CRUD target:

```text
list      → SELECT
getById   → SELECT row
create    → INSERT
update    → UPDATE
archive   → UPDATE lifecycle
restore   → UPDATE lifecycle
delete    → DELETE protetto da integrità referenziale
```

`canDelete()` resterà utile come preflight UX, ma PostgreSQL dovrà essere l'autorità finale contro race condition e riferimenti concorrenti.

### Valutazione S0.5

Contacts è uno dei domini più maturi per una migrazione Supabase progressiva.

A differenza di Property, non richiede prima la costruzione di una nuova repository architecture:

```text
Property
→ repository boundary ancora da consolidare

Contacts
→ repository boundary già esistente
→ sostituzione adapter locale con adapter Supabase
```

È quindi un candidato forte per il pilot CRUD di S4, decisione da confermare soltanto dopo la matrice comparativa finale di S0.12.
