## S0.6 — Tenants

### Stato attuale

`TenantRecord` è un aggregate ricco che contiene nello stesso oggetto:

```text
Tenant
├─ identity / lifecycle
├─ dati persona
├─ dati società
├─ contatti
├─ residenza
├─ lavoro
├─ banca
├─ documenti identità
├─ guarantors[]
├─ emergencyContacts[]
├─ documents[]
├─ invitation
├─ leaseIds[]
└─ legacy?
```

Il modello business è in gran parte valido, ma la forma attuale del record riflette il database JSON locale e **non deve essere trasferita 1:1 in PostgreSQL**.

### Boundary di persistenza corrente

Esiste già una factory account-scoped:

```text
createTenantRepository({ accountId })
→ createJsonDbAccountScope(accountId)
→ createTenantRepositoryOperations(gateway)
```

che espone:

```text
getById
create
update
archive
restore
delete
archiveMany
restoreMany
deleteMany
```

Il dominio non possiede però ancora un vero `TenantRepository` port asincrono indipendente dallo storage.

Restano inoltre funzioni globali:

```text
listTenants()
getTenantById()
sendTenantInvite()
```

basate direttamente su:

```text
getJsonDb()
saveJsonDb()
```

Situazione corrente:

```text
CREATE / UPDATE / LIFECYCLE
→ repository account-scoped

LIST / DETAIL / INVITE
→ global jsonDb
```

Questa divisione dovrà essere eliminata.

### Create

Il flusso corrente è:

```text
normalizeTenantFormData
→ attachment quota
→ fiscal uniqueness
→ relation integrity
→ Contact reference integrity
→ generate Tenant ID
→ costruzione candidate
→ una save
→ reread record persistito
```

I test proteggono:

```text
una sola write
account scope catturato
input non mutato
nessun record parziale
save failure senza retry implicito
return basato sul risultato reale della persistence
```

Questa disciplina è da preservare.

### Atomicità dell'aggregate

Oggi Tenant, guarantor, emergency contact e documenti embedded vengono salvati con una sola whole-database write.

Se nel target tali strutture diventano child row, deve restare la stessa semantica:

```text
BEGIN
→ Tenant
→ child relations
→ metadata documenti
→ COMMIT
```

Non devono essere possibili Tenant parzialmente persistiti.

La whole-database write locale deve invece essere eliminata.

### Contact creati dal flusso Tenant

Un Contact creato autonomamente dalla rubrica durante la compilazione Tenant diventa una vera entità indipendente prima della create Tenant.

Se la successiva create Tenant fallisce:

```text
Contact
→ rimane

Tenant
→ non viene creato
```

Non deve quindi essere introdotto un rollback automatico del Contact.

### Fiscal identity

Regole correnti:

```text
Tenant person
→ fiscalCode, se valorizzato

Tenant company
→ companyFiscalCode e/o vatNumber, se valorizzati
```

Per una company non partecipano alla fiscal identity corrente:

```text
fiscalCode
vatNumberPersonal
email
SIRET
```

Il matching è type-aware e account-scoped.

Identificatori vuoti non costituiscono identità.

I Tenant archived continuano a partecipare all'unicità.

L'identità fiscale Tenant resta distinta da Contact:

```text
Tenant ↔ Tenant
Contact ↔ Contact
```

Il target PostgreSQL dovrà mantenere validation applicativa e aggiungere enforcement concurrency-safe a livello database/workspace.

### Relazioni Lease

`TenantRecord.leaseIds[]` è una proiezione derivata.

Authority corrente:

```text
Lease.tenantIds[]
```

Il validator ricostruisce infatti i lease ID attesi dalle Lease e considera errore una divergenza.

Classificazione:

```text
Lease.tenantIds[]
→ authority

Tenant.leaseIds[]
→ derived
```

`leaseIds[]` non deve essere trasferito automaticamente come seconda authority nel modello PostgreSQL.

### Stato Tenant

`Tenant.status` non rappresenta da solo lo stato operativo.

Il read-model deriva:

```text
archived
→ inattivo

Lease corrente
→ attivo

stored status == candidato
→ candidato

altrimenti
→ inattivo
```

Quindi:

```text
status attivo
→ principalmente derivato dalle Lease
```

La futura persistenza non deve creare una seconda authority indipendente.

### Relazione verso Property

Tenant non possiede oggi una relazione autoritativa diretta verso Property.

La Property corrente viene derivata:

```text
Tenant
→ Lease corrente
→ Property
```

Non deve quindi essere introdotta automaticamente una `property_id` diretta nel Tenant.

### Tenant ↔ Contact

Guarantor ed Emergency Contact sono vere relazioni figlie.

Contratto:

```text
relation.id
≠
contactId
```

`relation.id` identifica la relazione Tenant.

`contactId` identifica il Contact canonico.

Ogni relation ID deve essere:

```text
non vuoto
unico nella propria collection
```

Lo stesso Contact può essere usato in ruoli differenti nello stesso Tenant.

Non deve essere applicata una uniqueness globale `tenant + contact` indipendente dal ruolo.

### Emergency Contact

Regole correnti:

```text
massimo 5 emergency contact
```

e, se ne esiste almeno uno:

```text
esattamente un isPrimary = true
```

`isPrimary` è metadata della relazione, non del Contact canonico.

### Contact references

La create blocca un nuovo `contactId` inesistente.

L'update preserva invece un riferimento legacy dangling se:

```text
relation.id
+
contactId
```

restano invariati.

Regola:

```text
legacy dangling invariato
→ preserve

nuovo dangling
→ block
```

Non viene eseguito alcun read-repair e non vengono creati Contact implicitamente.

Non esiste matching euristico tramite nome, email, telefono o `relation.id`.

### Contact archived — incoerenza da risolvere

Il repository Tenant valida oggi soltanto l'esistenza del Contact e quindi accetta anche Contact archived.

La UI invece non li propone per nuove relazioni.

Situazione:

```text
UI
→ archived Contact non selezionabile

Tenant repository
→ archived Contact accettabile
```

La regola autoritativa deve essere definita prima della modellazione definitiva Supabase.

Owner:

```text
S1 / S5
```

### Nested IDs

Devono essere preservati gli ID persistenti di:

```text
TenantGuarantors[].id
TenantEmergencyContacts[].id
TenantPhoto.id
TenantIDCard.id
TenantIDCardBack.id
TenantCompanyRegistryFile.id
TenantDocuments[].id
TenantDocuments[].file.id
```

I test ne verificano la conservazione attraverso:

```text
normalizzazione
draft
create
persistenza
reload
```

senza rigenerazione.

Se diventano child row, questi ID restano identità persistenti.

### Person / Company e file identità

Una nuova company viene creata intenzionalmente con:

```text
identityDocumentFile = null
identityDocumentBackFile = null
```

e può utilizzare:

```text
companyRegistryFile
```

L'update:

```text
company → company
```

preserva eventuali identity document legacy già presenti.

Il cambio:

```text
person → company
```

non deve invece trascinare automaticamente documenti specifici della persona.

Questa è una semantica di compatibilità da preservare durante la transizione, non necessariamente una struttura da replicare nel nuovo schema.

### File

I file Tenant sono attualmente `StoredLocalFile`:

```text
id
name
type
size
lastModified
dataUrl
```

Il sistema usa limiti modellati sullo storage browser:

```text
foto max 1 MB
documento max 2 MB
totale allegati 3 MB
```

Target:

```text
PostgreSQL
→ metadata e relazioni

Supabase Storage
→ file binari
```

I limiti prodotto dovranno essere riesaminati separatamente dai limiti tecnici del localStorage.

### TenantDocuments

`TenantDocuments[]` è oggi un modello ibrido.

Un documento può contenere:

```text
document metadata
file embedded
```

oppure anche:

```text
existingDocumentId
```

verso un `DocumentRecord` globale.

La UI legge direttamente:

```text
getJsonDb().documents
```

per scegliere documenti esistenti.

Il repository Tenant però **non verifica** che `existingDocumentId` corrisponda realmente a un `DocumentRecord`.

Quindi:

```text
TenantDocument.existingDocumentId
→ collegamento UI
→ non FK protetta
```

La struttura definitiva deve essere risolta dopo S0.9.

### Lifecycle

Archive/restore singoli e bulk sono già maturi.

Contratti:

```text
preservazione dati
dedup ID
empty selection = no-op
validazione completa prima della mutation
nessuna partial mutation
una sola mutation logica
```

Da preservare con query set-based/transazioni PostgreSQL.

### Delete

Il Tenant può essere eliminato solo se non conserva storico.

Blocker:

```text
qualunque Lease che contiene tenantId
qualunque Payment con tenantId
```

anche se:

```text
Lease terminata
Lease archived
Payment paid
```

Regola:

```text
Tenant con storico contrattuale/economico
→ DELETE bloccata
→ usare archive
```

Nessun cascade:

```text
DELETE Tenant
≠ DELETE Lease
≠ DELETE Payment
```

e non viene azzerato `Payment.tenantId`.

PostgreSQL dovrà essere l'autorità finale di integrità referenziale.

### Bulk delete

`deleteMany()` è all-or-nothing.

Se almeno un Tenant:

```text
ha blocker
oppure
non esiste
```

nessun Tenant viene eliminato.

Questa semantica richiede una transaction/set-based mutation nel target.

### Draft orchestration

Create ed edit sono già predisposti a mutation asincrone.

Il form usa:

```text
await onCreateTenant(...)
await onUpdateTenant(...)
```

Dopo una business mutation riuscita:

```text
draft cleanup fallisce
→ retry solo cleanup
→ nessuna seconda create/update
```

Questa orchestrazione è da preservare.

### Invitation

`TenantInvitation` è attualmente una simulazione locale.

`sendTenantInvite()` aggiorna soltanto:

```text
status
email
sentAt
acceptedAt
```

nel Tenant.

Non viene inviata realmente alcuna email.

Anche il link:

```text
/tenant/invite/<tenantId>
```

è un read-model locale e non rappresenta un token Auth sicuro.

Quindi:

```text
TenantInvitation
≠ Supabase Auth
≠ workspace membership
```

La futura architettura di autenticazione/inviti va trattata separatamente in S0.10/S1/S2.

### Read-model lista

La lista Tenant dipende da:

```text
Tenant
Lease
Property
Payment
```

per derivare:

```text
Property corrente
Property name
status
balance
```

Non equivale quindi a un semplice `SELECT tenants`.

Target:

```text
Tenant repository
≠ Tenant list query/read-model
```

### Read-model dettaglio

Il dettaglio aggrega:

```text
Tenant core
Property corrente
current Lease
future Leases
historical Leases
archived Leases
financial balance
invitation state
```

e contiene ancora placeholder:

```text
messages: []
activityHistory: []
```

Quindi anche il dettaglio dovrà diventare una query/read-model specifica.

### Consumer runtime

Restano consumer globali:

```text
useTenantsDb
→ listTenants + subscribeJsonDb

useTenantDetail
→ getTenantById + sendTenantInvite + subscribeJsonDb
```

Questi devono essere sostituiti da query/repository async workspace-scoped.

### Target concettuale

```text
authenticated user
→ workspace
→ TenantRepository / TenantQueries
→ Supabase adapter
→ PostgreSQL
```

con una struttura concettuale simile a:

```text
Tenant
├─ canonical person/company fields
├─ fiscal identity
├─ recapiti
├─ indirizzo
├─ professional data
├─ bank data
├─ lifecycle
│

→ authority economica

```

Non:

```text
tenants
└─ TenantRecord JSONB
```

### Valutazione S0.6

Tenant è un dominio business maturo ma strutturalmente più complesso di Contacts.

La migration strategy dovrà preservare le regole esistenti senza conservare il blob JSON:

```text
business aggregate
→ KEEP

current physical storage shape
→ REFACTOR
```

Il write-side offre già una buona base logica, ma deve diventare asincrono e row/transaction-oriented.

Il read-side necessita invece di una rifattorizzazione più profonda verso query multi-dominio dedicate.
