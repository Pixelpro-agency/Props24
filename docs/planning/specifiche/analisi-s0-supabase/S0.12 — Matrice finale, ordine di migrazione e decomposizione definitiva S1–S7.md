## S0.12 — Matrice finale, ordine di migrazione e decomposizione definitiva S1–S7

### Stato finale S0

S0.1–S0.11 hanno permesso di distinguere quattro livelli differenti dell'attuale persistenza:

```text
BUSINESS AUTHORITY
→ Building
→ Property
→ Contact
→ Tenant
→ Lease
→ Payment
→ Document

DERIVED / READ-MODEL
→ status
→ balance
→ reverse relation
→ dashboard
→ search
→ list/detail aggregate

INFRASTRUTTURA LOCALE
→ jsonDb
→ localStorage
→ active database account
→ whole-database save
→ repair
→ subscription globale

STATO NON BUSINESS
→ UI preferences
→ static catalogs/templates
→ mock
→ placeholder collections
```

La migrazione Supabase deve:

```text
KEEP
→ business semantics consolidate

NORMALIZE
→ relazioni e child entity reali

SEPARATE
→ command e query/read-model

REPLACE
→ persistenza locale

NON MIGRARE
→ scaffolding e stato browser non business
```

Il database locale dei Blocchi A/B/C resta baseline comportamentale da preservare, non modello fisico da replicare in PostgreSQL.


### Tenant / Property corrente

```text

```

Non serve una relazione diretta autoritativa `Tenant → Property`.

### Contact

```text
ContactRecord
→ authority rubrica

Tenant relation.id
→ identity della relazione

→ riferimento al Contact canonico
```

`relation.id != contactId`.

```text

Lease balance
Tenant balance

Dashboard financial KPI
→ derived
```

La futura area Finanze deve costruire sopra questa stessa authority e non creare una persistence economica parallela.

View, cache o materialized view future restano possibili, ma non devono introdurre una seconda fonte business indipendente.

## `LocalDatabase` non deve sopravvivere come runtime contract

Non deve essere adottato un modello:

```text

→ scarica tutte le tabelle
→ ricostruisce LocalDatabase
→ riusa i selector correnti
```

Il target è:

```text
PostgreSQL
→ repository / commands / queries specifiche
→ DTO/read-model necessari
→ UI
```

La migrazione deve quindi eliminare sia il vecchio storage sia la dipendenza applicativa dal mega-object `LocalDatabase`.

# Acceptance criterion finale Blocco S

Il Blocco S sarà chiuso soltanto quando:

1. Auth reale sostituisce l'Auth locale runtime.
2. Due utenti autorizzati possono usare lo stesso workspace.
3. Un utente non autorizzato viene bloccato da RLS.
4. Building, Property, Contact, Tenant, Lease, Payment e document metadata usano PostgreSQL come authority.
5. I file runtime usano Supabase Storage.
6. Draft utilizza l'authority definita.
7. Dashboard, Search, list e detail non ricostruiscono `LocalDatabase`.
8. Le query sono side-effect free.
9. Lease/Payment commands sono atomicamente transazionali.
10. Nessun business consumer usa più:

```text
getJsonDb
saveJsonDb
subscribeJsonDb
createJsonDbAccountScope
```

11. Non esistono silent fallback o dual-write impliciti.
12. I dataset locali correnti non vengono importati automaticamente come produzione.
13. I contratti funzionali dei Blocchi A/B/C restano verdi.
14. Collaborazione multiutente e isolamento cross-workspace sono verificati.
15. Data URL e persistence runtime locale non sono più authority dei business data.
