### Stato verificato

`LocalDatabase` contiene aree con livelli di maturità molto differenti:

* `documents`: dominio persistente reale;
* `drafts`: dominio tecnico maturo con port async già separato dallo storage;
* `messages`: dominio reale ma limitato alle comunicazioni Lease preparate;
* `settings`: `Record<string, unknown>`, non ancora vero modello persistente;
* `userProfile`: `Record<string, unknown>` con authority non uniforme;
* `reservations`, `catalogs`, `inventory`, `maintenance`, `tasks`, `notes`, `candidates`: collezioni `EmptyRecord[]`, quindi placeholder strutturali e non domini implementati.

La presenza di una collection nel vecchio `LocalDatabase` non costituisce da sola una ragione per creare una corrispondente tabella Supabase.

## Documents

### Modello corrente

`DocumentRecord` è una vera entità persistente con:

* `id`;
* `ownerType: 'lease' | 'global'`;
* `ownerId`;
* `sourceDocumentId`;
* categoria e metadata;
* `isShared`;
* `file`;
* `createdAt`;
* `updatedAt`.

Il modello distingue due casi:

1. documento fisico:

   * `sourceDocumentId = null`;
   * `file` presente;

2. documento collegato:

   * `sourceDocumentId` valorizzato;
   * `file = null`;
   * il file viene risolto dal documento sorgente.

Un link Lease → documento globale non duplica fisicamente il file.

`resolveDocumentFile()` segue la provenance tramite `sourceDocumentId` e protegge da riferimenti ciclici.

### Storage corrente

Il contenuto binario è salvato come `StoredLocalFile` con `dataUrl`.

La UI usa `FileReader.readAsDataURL()` prima della persistence.

Questo storage è transitorio e non deve essere portato in PostgreSQL.

Target concettuale:

```text
PostgreSQL
→ metadata
→ ownership
→ relazioni
→ riferimento allo storage

Supabase Storage
→ contenuto binario
```

I limiti attuali di 2 MB per file e 3 MB totali per Lease sono fortemente legati al modello locale e devono essere rivalutati.

Le policy sui formati supportati possono invece restare come business/security rule.

### Relazioni e business rules

Esistono già relazioni forti fra Documents e Lease.

Il delete di un Lease Document è bloccato se il documento è utilizzato da:

* `Lease.signatureProcess.contractDocumentId`;
* `LeaseInsuranceContracts[].LeaseInsuranceDocumentId`.

La Lease stessa non può essere eliminata mentre possiede Document collegati.

Create, link, update e delete di un Document modificano anche `Lease.activity`.

Nel database futuro queste operazioni dovranno preservare atomicità tra:

```text
Document mutation
+
Lease activity event
```

Il repository corrente usa direttamente `getJsonDb()` / `saveJsonDb()` ed è sincrono: non è un boundary adatto al target Supabase e dovrà essere rifattorizzato verso API async.

### Global documents

Il modello supporta `ownerType = global` e la UI Lease può collegare documenti globali esistenti.

Nel writer analizzato non è però emerso un flusso completo equivalente a `createGlobalDocument()`.

La global document library è quindi prevista dal modello, ma il suo ciclo di vita completo deve essere confermato in S0.11 prima della modellazione definitiva.

### Categoria e condivisione

`categoryId` non è oggi una FK affidabile verso un vero catalogo: nella UI Lease viene valorizzato con `1`, mentre `categoryLabel` è modificabile liberamente.

Non va quindi trasformato automaticamente in una relazione SQL a `document_categories`.

`isShared` è metadata persistito, ma nel codice analizzato non rappresenta ancora una vera policy di autorizzazione.

La sua semantica finale dovrà essere collegata al futuro modello Auth/workspace/RLS.

### Duplicazioni documentali da risolvere

Oggi esistono almeno tre rappresentazioni separate:

```text
DocumentRecord
TenantDocuments[]
PropertyDocuments[]
```

`TenantDocuments[].existingDocumentId` può riferirsi a `DocumentRecord`, ma il riferimento non è protetto come vera FK.

`PropertyDocuments[]` resta invece embedded nella Property.

S1 dovrà decidere come separare e riconciliare:

```text
file fisico
document metadata
ownership
document link/use
```

senza migrare automaticamente tutte le rappresentazioni attuali.

## Drafts

### Modello corrente

`DraftRecord` contiene:

* `id`;
* `accountId`;
* `formType`;
* `mode`;
* `entityId`;
* `payload`;
* `schemaVersion`;
* `createdAt`;
* `updatedAt`.

Form supportati:

* `building`;
* `property`;
* `tenant`;
* `lease`.

Mode supportati:

* `create`;
* `edit`.

Esiste già un vero port asincrono:

```text
DraftRepository
├─ get
├─ list
├─ save
└─ delete
```

Questa architettura è già adatta alla sostituzione dell'adapter locale.

### Logical identity

La Draft possiede una chiave logica composta da:

```text
account
formType
mode
entityId
```

Per `create`, `entityId` deve essere `null`.

Per `edit`, `entityId` è obbligatorio.

Create ed Edit sono volutamente isolate e draft riferite a entity differenti non collidono.

I test proteggono inoltre:

* account isolation;
* collision safety;
* immutabilità degli input;
* clone dei payload;
* upsert senza duplicazioni;
* preservazione di `id` e `createdAt`;
* aggiornamento di `updatedAt`;
* rilevazione della corruzione.

### Payload versionato

Ogni form possiede una `DraftDefinition` con:

```text
formType
schemaVersion
parse(payload, storedSchemaVersion)
```

Il payload non viene quindi trattato come JSON arbitrario non verificato.

Corruzione di payload, versione o metadata produce errore invece di essere accettata silenziosamente.

Questo contratto deve essere preservato.

### Adapter locale

`localDraftRepository` implementa il port async utilizzando `createJsonDbAccountScope(accountId)` e modifica la collection `drafts` dentro l'intero `LocalDatabase`.

Classificazione:

```text
DraftRepository port
→ KEEP

DraftRepositoryProvider
→ KEEP / ADAPT

draft domain logic
→ KEEP

localDraftRepository
→ REPLACE dopo il cutover
```

### JSON flessibile

Draft è uno dei pochi casi in cui un payload strutturalmente flessibile può essere corretto anche nel target.

Il suo scopo è memorizzare uno stato temporaneo di form versionato e dipendente dal `formType`.

Quindi, a differenza dei core domain come Property/Tenant/Lease, un campo JSON/JSONB per il payload può essere appropriato.

La scelta concreta resta S1.

### Scope futuro

Non bisogna trasformare automaticamente:

```text
accountId
→ workspaceId
```

Le Draft potrebbero essere personali all'utente pur essendo memorizzate in Supabase.

Database remoto non implica automaticamente draft collaborativa.

S1/S2 devono decidere ownership e policy delle bozze.

Il port corrente non espone `subscribe`; non esiste quindi un requisito consolidato di collaborative realtime editing.

### Draft cleanup

Resta valido il contratto già verificato nei form:

```text
business mutation riuscita
→ cleanup Draft fallisce
→ non ripetere la business mutation
→ retry soltanto delete Draft
```

## Messages

`messages` è una collection reale, non un placeholder.

`MessageRecord` rappresenta oggi comunicazioni Lease con:

* `entityType = lease`;
* `entityId`;
* `channel = email`;
* `status = prepared`;
* `recipientTenantIds`;
* snapshot dei destinatari;
* `subject`;
* `body`;
* `createdAt`.

Il flusso corrente prepara il record e genera un `mailto:`.

Non esiste quindi prova di:

* invio;
* delivery;
* failure;
* apertura.

Semantica corretta:

```text
MessageRecord corrente
→ comunicazione preparata
```

non:

```text
→ email effettivamente inviata
```

Il record conserva sia riferimenti Tenant sia snapshot di nome/email, distinzione utile per uno storico delle comunicazioni.

La preparazione di una comunicazione modifica anche `Lease.activity`, quindi il futuro modello dovrà preservare la coerenza transactionale fra comunicazione e activity.

La semantica delle operazioni multi-Lease e dei destinatari aggregati va confermata prima della progettazione definitiva.

## Settings

`LocalDatabase.settings` è soltanto:

```text
Record<string, unknown>
```

Non esistono attualmente:

* `SettingsRecord`;
* `SettingsRepository`;
* schema tipizzato;
* ownership definita.

Non deve quindi essere creata automaticamente una tabella `settings` soltanto per riprodurre il vecchio JSON.

Le future impostazioni dovranno essere classificate almeno fra:

* preferenze personali utente;
* configurazioni del workspace;
* configurazione statica dell'app;
* preferenze locali/UI.

S0.11 dovrà identificare gli eventuali consumer reali.

## User profile

`LocalDatabase.userProfile` è ancora un `Record<string, unknown>`.

La UI corrente tramite `useUserProfile()` non lo utilizza: prende `id`, nome, cognome ed email direttamente da `AuthContext.account`.

Esiste però almeno un consumer differente, già verificato in S0.8: `receiptRepository` usa `database.userProfile` per ricavare i dati del locatore.

Esistono quindi due authority differenti:

```text
profilo UI
→ AuthContext.account

dati locatore ricevuta
→ LocalDatabase.userProfile
```

Questa duplicazione non deve essere preservata.

`mockUserProfile.ts` è un placeholder storico e candidato alla rimozione dopo il consolidamento Auth/Profile.

S0.10 dovrà distinguere correttamente:

* utente autenticato;
* profilo personale;
* membership;
* workspace;
* dati anagrafici/fiscali del locatore o soggetto business.

Non va assunto che questi concetti coincidano.

## Collezioni residue

Le collection:

* `reservations`;
* `catalogs`;
* `inventory`;
* `maintenance`;
* `tasks`;
* `notes`;
* `candidates`;

sono attualmente `EmptyRecord[]` e non costituiscono modelli di dominio implementati.

Non devono essere trasformate automaticamente in tabelle Supabase.

Inoltre:

```text
LocalDatabase.catalogs
≠
propertyTypeCatalog / propertyRentTypeCatalog / ecc.
```

I veri cataloghi Property correnti sono definiti staticamente nel codice.

Analogamente:

```text
LocalDatabase.notes
≠
Property.notes

LocalDatabase.candidates
≠
Tenant.status = candidato
```

La regola per S1 è quindi:

```text
dominio realmente implementato
→ progettare persistence quando necessaria

placeholder del vecchio LocalDatabase
→ non migrare per semplice compatibilità
```

La rimozione definitiva delle collection residue dal runtime locale appartiene a S7, dopo che non esisteranno più consumer.

## Keep / Adapt / Delete

### KEEP

* `DocumentRecord` come concetto di dominio;
* ownership/provenance dei documenti;
* link senza duplicazione fisica del file;
* business blockers Document;
* no-delete implicito delle source globali quando si elimina un link;
* `DraftRecord`;
* logical key Draft;
* `DraftDefinition` e `schemaVersion`;
* `DraftRepository` async;
* contratti di isolamento e corruption handling Draft;
* cleanup Draft separato dalla business mutation;
* `MessageRecord` come comunicazione preparata;
* snapshot dei destinatari.

### ADAPT / REFACTOR

* Document model verso metadata + relation + Storage;
* Document repository verso API async;
* `sourceDocumentId` verso relazione professionale equivalente;
* `isShared` verso policy coerente con Auth/workspace;
* Tenant/Property embedded documents;
* Message persistence e activity transaction;
* Draft ownership da account locale a modello user/workspace esplicito;
* `userProfile` verso authority unica;
* eventuali future Settings verso scope tipizzati.

### DELETE / NON MIGRARE

* `StoredLocalFile.dataUrl` come persistence runtime;
* storage binario dentro PostgreSQL;
* repository Documents basato direttamente su `getJsonDb/saveJsonDb`;
* `localDraftRepository` dopo cutover;
* `mockUserProfile` dopo consolidamento Auth;
* creazione automatica di tabelle per collection `EmptyRecord[]`;
* assunzione che `categoryId = 1` rappresenti un vero catalogo;
* assunzione che `MessageRecord` equivalga a email inviata.

### Conclusione S0.9

S0.9 conferma che la migrazione Supabase non deve riprodurre meccanicamente la forma di `LocalDatabase`.

Classificazione definitiva:

```text
Documents
→ dominio reale
→ normalizzare e spostare file su Supabase Storage

Drafts
→ dominio tecnico già ben separato
→ mantenere port/contratti e sostituire adapter locale

Messages
→ dominio reale ma limitato alle comunicazioni preparate

Settings
→ non ancora un vero modello persistente

UserProfile
→ authority corrente non uniforme
→ da risolvere insieme ad Auth/workspace

Residual collections
→ placeholder
→ non creare tabelle Supabase per inerzia
```

Il principio da preservare per S1 è:

```text
modellare il dominio reale del prodotto,
non convertire automaticamente ogni proprietà del vecchio JSON in SQL.
```
