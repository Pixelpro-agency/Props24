## S0.3 — CRUD e persistenza Buildings

### Stato corrente

Il dominio `Building` è già uno dei domini con la separazione più solida tra UI, logica CRUD e persistence locale.

L'entità canonica è `BuildingRecord` e contiene:

* identificazione e indirizzo;
* dati fisici dell'edificio;
* descrizione, nota privata e feature;
* dati di acquisizione ed economici;
* lifecycle `archived`;
* timestamp;
* `unitsCount`, attualmente persistito ma derivato dalle `Property` collegate.

I campi gestiti dal sistema e non controllabili dal normale input CRUD sono:

```text
id
createdAt
updatedAt
archived
unitsCount
```

Create e update preservano questa distinzione.

### Repository e authority delle mutation

Il writer principale è:

```text
src/db/buildingRepository.ts
```

La struttura corrente è:

```text
UI
↓
BuildingRepository
↓
BuildingDatabaseGateway
↓
createJsonDbAccountScope(accountId)
↓
LocalDatabase / localStorage
```

`BuildingRepository` espone:

```text
list
getById
create
update
archive
restore
delete
archiveMany
restoreMany
deleteMany
subscribe
```

`createBuildingRepositoryOperations(gateway)` contiene la logica CRUD indipendente dal concrete storage.

`createBuildingRepository({ accountId })` collega invece tale logica al database JSON account-scoped.

La repository è quindi una boundary utile da mantenere, mentre il gateway:

```text
getDatabase()
saveDatabase(database)
```

è specifico dell'attuale modello a blob e deve essere sostituito nella migrazione.

### Writer UI verificati

I flussi principali di scrittura Building passano dalla repository:

```text
BuildingCreateForm
→ repository.create()

BuildingEditForm
→ repository.update()

BuildingsPage
→ archive / restore / delete
→ archiveMany / restoreMany / deleteMany

BuildingDetailPage
→ archive / restore / delete
```

Non è emersa nel normale CRUD Building una mutation UI diretta su `db.buildings`.

### Read path

La lista usa correttamente la repository:

```text
useBuildings
→ createBuildingRepository({ accountId })
→ repository.list()
→ repository.subscribe()
```

Filtro active/archived, ricerca e ordinamento vengono attualmente eseguiti client-side dopo aver caricato tutti i Building.

Il dettaglio presenta invece un accoppiamento residuo alla persistence locale:

```text
useBuildingDetail
→ createJsonDbAccountScope(accountId)
→ getDatabase()
→ database.buildings.find(...)
→ database.properties.filter(...)
```

`useBuildingDetail` conosce quindi direttamente:

```text
LocalDatabase
buildings
properties
Property.relations.buildingId
```

Questo read-model dovrà essere rifattorizzato: il futuro hook/UI non deve interrogare direttamente né `localStorage` né le tabelle Supabase.

Il bisogno funzionale reale del dettaglio è un read-model multi-entità:

```text
Building
+
Property / Unit collegate
```

La forma definitiva della query boundary sarà valutata dopo S0.4 e definita in S3.

### Account isolation

La repository Building è costruita esplicitamente con:

```text
createBuildingRepository({ accountId })
```

Una repository già costruita resta legata allo scope originario anche se cambia l'account globale.

I test verificano isolamento tra account per:

* reader;
* writer;
* storage fisico;
* subscription.

Questo contratto deve essere preservato concettualmente nella migrazione.

Nel target Supabase lo scope non dovrà però coincidere semplicemente con un `user_id`: il modello condiviso previsto dal Blocco S richiede uno scope `workspace`.

### Relazione Building → Property

La relazione canonica corrente è:

```text
Property.relations.buildingId
→
Building.id
```

Una Property può essere:

```text
buildingId = null
```

Il modello funzionale corrente è quindi:

```text
1 Building → N Property
1 Property → 0..1 Building
```

L'authority della relazione è la `Property`, non `Building.unitsCount`.

Il collegamento Property deve preservare anche gli altri array relazionali della Property, come `tenantIds` e `leaseIds`.

### `unitsCount`

`Building.unitsCount` viene attualmente persistito, ma è un dato derivato dal numero reale di Property collegate.

I test verificano il riallineamento su:

* create Property collegata;
* reassignment;
* detach;
* delete Property.

La validazione globale segnala inoltre:

```text
BUILDING_UNITS_COUNT_OUT_OF_SYNC
```

se il valore persistito non corrisponde alle relazioni reali.

Contratto da preservare:

```text
unitsCount non determina mai la relazione Building ↔ Property.
```

La soluzione target — query `COUNT`, view, projection mantenuta o altra strategia — appartiene a S1.

### Business rule — identificativo univoco

L'identificativo Building deve essere unico nello scope anche rispetto ai Building archiviati.

Per il confronto vengono normalizzati:

* Unicode NFKC;
* spazi iniziali/finali;
* whitespace multiplo;
* maiuscole/minuscole.

Esempi equivalenti:

```text
Palazzo Centro
 PALAZZO   CENTRO
palazzo centro
```

La regola corrente è application-level e viene verificata prima della write.

Con database condiviso questa protezione non è sufficiente contro mutation concorrenti.

Il target dovrà quindi preservare la validazione applicativa ma aggiungere un enforcement atomico PostgreSQL nello scope workspace.

La tecnica concreta viene definita in S1.

### Business rule — location univoca

È presente anche un vincolo di unicità geografica basato su:

```text
address
city
postalCode
country
```

`address2`, `county` e `state` non partecipano alla chiave corrente.

Whitespace, case e formato vengono normalizzati per il confronto.

Suffissi civici distinti restano invece distinti:

```text
Via Roma 10
Via Roma 10 bis
Via Roma 10 ter
```

Anche questa regola include i Building archiviati e dovrà ricevere enforcement concurrency-safe nel database target.

### Lifecycle

Il lifecycle corrente è:

```text
active
↔
archived
```

Archiviare un Building:

* non elimina Property;
* non scollega Property;
* non modifica le relazioni già esistenti.

Un Building archiviato può mantenere Property già collegate.

Non può invece ricevere:

* una nuova Property;
* un reassignment di una Property proveniente da un altro Building.

Aggiornare una Property già collegata allo stesso Building archiviato resta valido.

### Delete Building

L'eliminazione è consentita soltanto per Building senza Property collegate.

Qualunque Property collegata blocca il delete, compresa una Property archiviata.

Il blocco produce:

```text
BuildingDeleteBlockedError
buildingId
linkedPropertyIds[]
```

Non esiste cascade Building → Property.

Contratto da preservare:

```text
archive ≠ delete

DELETE Building
con Property collegate
→ BLOCK

DELETE Building
libero
→ consentito
```

Il target PostgreSQL dovrà mantenere anche una protezione referenziale database-side coerente con questa semantica.

### Bulk lifecycle

Sono disponibili:

```text
archiveMany
restoreMany
deleteMany
```

I contratti verificati sono:

* deduplicazione degli ID mantenendo l'ordine della prima occorrenza;
* empty selection = no-op;
* validazione completa degli ID prima della mutation;
* stesso timestamp per tutti i record di archive/restore;
* una sola write logica;
* verifica completa dei blocker prima del delete;
* nessuna mutation parziale in caso di errore.

Questa semantica all-or-nothing deve essere preservata.

Con Supabase non deve essere sostituita da:

```text
for each id
    await mutation(id)
```

perché un errore intermedio produrrebbe persistence parziale.

Il target richiede una mutation set-based o una vera boundary transazionale.

### Create e Draft cleanup

La create Building possiede già un contratto importante con il Draft:

```text
Building create riuscita
↓
cleanup Draft fallisce
↓
Building NON viene creata di nuovo
↓
retry soltanto della cancellazione Draft
```

Il fallimento del cleanup della bozza non deve quindi causare una seconda business mutation.

Questa semantica deve essere preservata indipendentemente da dove verranno persistiti i Draft.

### Subscription

`BuildingRepository.subscribe()` deriva attualmente dalla subscription del `JsonDbAccountScope`.

`useBuildings` la usa per invalidare/rileggere la lista dopo una modifica.

Il contratto utile è:

```text
mutation
→ invalidazione
→ refresh
```

L'implementazione basata su eventi browser/localStorage è transitoria.

La scelta futura tra normale query invalidation, Supabase Realtime o altra soluzione appartiene a S0.11/S1/S3.

### Limiti architetturali correnti

#### Repository sincrona

Il contratto corrente è sincrono perché `localStorage` è sincrono:

```text
repository.create()
repository.update()
repository.archive()
```

Supabase richiederà operazioni realmente asincrone.

La repository dovrà quindi diventare async; non deve essere costruito un wrapper fittiziamente sincrono.

#### Whole-database gateway

Ogni mutation Building passa ancora concettualmente da:

```text
get intero LocalDatabase
↓
modifica buildings
↓
save intero LocalDatabase
```

Questa implementazione non deve essere trasportata in Supabase.

Il target deve operare sui record e sulle relazioni necessarie.

#### Composition root

Diversi componenti costruiscono direttamente:

```text
createBuildingRepository({ accountId })
```

Con adapter Supabase sarà preferibile centralizzare la dependency nel composition root/provider, evitando che ogni componente scelga direttamente il concrete adapter.

#### List all

La lista Building attuale carica l'intera collection e applica lato client:

* filtro lifecycle;
* ricerca;
* sorting.

Questo comportamento può essere mantenuto inizialmente se il dataset lo consente, ma non deve diventare un vincolo strutturale del repository Supabase.

Pagination/search/sort database-side dovranno essere valutati in S3/S4.

### Integrità corrente

Il dominio è attualmente protetto da due livelli applicativi:

```text
Zod / form validation
+
databaseValidation
```

Le verifiche comprendono almeno:

```text
BUILDING_IDENTIFIER_REQUIRED
BUILDING_IDENTIFIER_DUPLICATE
ADDRESS_REQUIRED
CITY_REQUIRED
POSTAL_CODE_REQUIRED
BUILDING_COUNTRY_REQUIRED
BUILDING_LOCATION_DUPLICATE
BUILDING_UNITS_COUNT_OUT_OF_SYNC
```

Nel target alcune garanzie dovranno essere rafforzate tramite PostgreSQL:

```text
NOT NULL
CHECK
FK
UNIQUE / INDEX
```

La validazione applicativa resta comunque necessaria per business rule e feedback UI.

### Conseguenza per la migrazione

Buildings non richiede una riscrittura funzionale del dominio.

La direzione corretta è:

```text
preservare
→ entità
→ business rule
→ lifecycle
→ relazioni
→ atomicità
→ error semantics

sostituire
→ whole LocalDatabase
→ localStorage gateway
→ API sincrona
→ read-model direttamente accoppiati a JsonDb
```

Il target non deve essere:

```text
Supabase
→ tabella con un unico blob JSON Building
```

né:

```text
Supabase
→ scarica tutti i dati
→ ricostruisce LocalDatabase
→ riutilizza saveDatabase()
```

Il target concettuale è invece:

```text
authenticated user
↓
workspace
↓
Building repository / query boundary
↓
Building rows
↓
Property relation
↓
PostgreSQL constraints e transazioni
```

### Decisioni rinviate

S0.3 identifica ma non decide:

```text
features → array / tabella / altra modellazione
unitsCount → COUNT / view / projection
tipo ID → UUID o altra strategia
normalizzazione uniqueness → generated column / expression index / altro
tipi monetari e precisione
forma definitiva della repository async
query service per Building detail
Realtime
pagination/search/sort server-side
```

Owner:

```text
S0.4 → completa la relazione con Property
S0.11 → inventario consumer/subscription trasversali
S1 → schema, constraint, relazioni e transazioni PostgreSQL
S3 → repository async, adapter e composition root
S4 → cutover CRUD Building
```
