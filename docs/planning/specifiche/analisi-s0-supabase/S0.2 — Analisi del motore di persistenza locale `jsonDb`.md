## S0.2 — Analisi del motore di persistenza locale `jsonDb`

### Stato attuale

`src/db/jsonDb.ts` è oggi il cuore della persistenza locale e concentra responsabilità diverse:

* selezione e isolamento dell'account;
* bootstrap del database;
* seed iniziale;
* migrazioni legacy;
* normalizzazione;
* repair dei dati;
* validazione di integrità;
* cache in memoria;
* persistenza tramite `localStorage`;
* subscription e invalidazione;
* CRUD generico;
* gestione legacy delle bozze.

Il database fisico non è relazionale: ogni account possiede un intero `LocalDatabase` serializzato nella chiave:

```text
props24.localDb.<accountId>
```

I record interni non necessitano quindi oggi di un `accountId` proprio, perché è l'intero contenitore JSON a essere account-scoped.

---

### Flusso di inizializzazione

Per l'account principale il sistema tenta, in ordine:

```text
database account corrente
→ database locale condiviso legacy
→ vecchie versioni Rentila/Gestionale
→ eventuali backup legacy recuperabili
→ database.json come seed
```

Gli account secondari, se privi di database persistito, vengono invece inizializzati con un database vuoto.

Ogni sorgente recuperata viene:

```text
letta
→ migrata/normalizzata
→ validata
→ persistita nel formato corrente
→ riletta e verificata
→ solo successivamente vengono rimosse le sorgenti legacy
```

Questo principio di migrazione sicura è valido e deve essere preservato.

---

### Flusso di lettura

La lettura non è una semplice deserializzazione.

Il flusso corrente è:

```text
JSON persistito
→ JSON.parse
→ normalizeDatabase()
→ repairRecoverableDatabase()
→ assertDatabaseIntegrity()
→ LocalDatabase runtime
```

Il repair può ricostruire relazioni derivate e correggere dati recuperabili, soprattutto:

* relazioni Lease → Property/Tenant;
* conteggio unità degli edifici;
* schedule dei pagamenti;
* duplicati di pagamenti generati;
* stati e date di pagamento incoerenti.

Queste logiche possono essere utili come migration/maintenance, ma in un database PostgreSQL serio non dovrebbero essere normalmente eseguite come effetto collaterale delle letture.

Il target deve preferire:

```text
WRITE / TRANSACTION
→ produce uno stato già coerente

READ
→ legge lo stato persistito
```

---

### Flusso di scrittura

Una normale mutation oggi opera sull'intero `LocalDatabase`.

```text
leggi intero database
→ modifica il candidato
→ normalizza
→ valida
→ JSON.stringify dell'intero database
→ localStorage.setItem
→ rilettura
→ normalizzazione/repair
→ verifica integrità
→ aggiornamento cache
→ evento di change
```

Di conseguenza, anche una modifica a un singolo Contact o Tenant provoca la riscrittura di tutte le collezioni.

Questo modello deve essere eliminato con Supabase.

Il target dovrà usare mutation granulari su record e tabelle specifiche, mantenendo transazioni quando un'operazione coinvolge più entità.

---

### Atomicità

L'attuale modello possiede una forma utile di atomicità applicativa: molte operazioni costruiscono prima un database candidato completo e poi effettuano una sola write fisica.

Il contratto deve essere mantenuto, ma non l'implementazione.

Target:

```text
BEGIN
→ mutation sulle tabelle coinvolte
→ verifiche e vincoli
→ COMMIT
```

Quindi:

```text
atomicità multi-record = mantenere
whole-database write = eliminare
```

---

### Account scope

`createJsonDbAccountScope(accountId)` cattura esplicitamente lo scope dell'account.

Questo impedisce a un repository creato per un account di cambiare improvvisamente destinazione a seguito della modifica dello stato globale.

Il principio è valido e deve essere mantenuto.

Nel target lo scope dovrà però diventare coerente con il futuro workspace:

```text
repository
→ workspace/account scope catturato
→ query e mutation limitate allo scope
```

e l'isolamento dovrà essere garantito anche dal database, non soltanto dal client.

---

### Cache e subscription

Oggi esiste una cache dell'intero database attivo in memoria.

Le notifiche usano:

* custom DOM event per mutation nella stessa app;
* evento browser `storage` per modifiche provenienti da altre tab.

La subscription funziona principalmente come invalidazione:

```text
dato modificato
→ evento
→ invalidazione
→ nuova lettura
```

Il principio può essere mantenuto, ma cache globale, DOM event e `storage` event sono implementazioni locali da sostituire.

L'eventuale utilizzo di Supabase Realtime verrà deciso nelle task successive.

---

### Limite strutturale: concorrenza

Il modello attuale non è adatto a più collaboratori.

Due client possono leggere contemporaneamente lo stesso blob JSON e successivamente riscriverlo integralmente.

Esempio:

```text
client A legge DB v1
client B legge DB v1

A modifica Contact
→ salva DB v2

B modifica Building partendo ancora da v1
→ salva DB v3
```

L'ultima write può sovrascrivere anche modifiche appartenenti a entità completamente differenti.

Non sono presenti veri meccanismi di:

* transazioni concorrenti;
* row-level locking;
* MVCC applicativo;
* versioning dei record;
* optimistic concurrency.

Questo è uno dei motivi principali per cui il modello JSON locale deve essere sostituito da PostgreSQL.

---

### Failure handling

Le normali mutation esplicite validano e propagano gli errori.

Durante alcune inizializzazioni, invece, in caso di failure della persistenza è previsto un fallback al database in memoria.

Questo comportamento è accettabile come resilienza di un prototipo locale, ma non deve esistere nel target condiviso.

Nel database definitivo:

```text
write fallita
=
operazione fallita
```

Non deve essere possibile continuare con una seconda copia locale/in-memory che diverga dallo stato autoritativo remoto.

---

### Seed e versioning

Attualmente coesistono:

* `schemaVersion`, che rappresenta il formato canonico del database;
* `seedVersion`, che rappresenta la lineage/versione dei dati iniziali.

Nel target Supabase queste responsabilità devono essere separate:

```text
schema database
→ migration SQL versionate

dati demo/test
→ seed e fixture separati
```

Il seed non deve diventare parte significativa del modello business runtime.

---

### Responsabilità da separare

`jsonDb.ts` concentra oggi troppe responsabilità.

Nel target queste aree dovranno diventare indipendenti:

```text
domain rules / normalization
repository contracts
Supabase adapters
SQL migrations
transaction boundaries
workspace/auth scope
query invalidation/cache
development fixtures
legacy migration/maintenance
```

La migrazione non dovrà quindi consistere nella creazione di un nuovo `supabaseDb.ts` monolitico equivalente a `jsonDb.ts`.

---

### Classificazione preliminare

#### KEEP

* validazione prima della persistence;
* business rule esplicite;
* errori espliciti;
* atomicità multi-record;
* scope catturato dai repository;
* migrazione source → target → verifica → cleanup;
* integrità del dato;
* invalidazione dopo una mutation riuscita.

#### ADAPT / REFACTOR

* normalizzazione canonica;
* repair legacy;
* subscription;
* cache;
* gestione della versione del database;
* transaction boundaries.

#### DELETE / REPLACE

* `localStorage` come database;
* un blob `LocalDatabase` per account;
* riscrittura dell'intero database a ogni CRUD;
* cache in memoria dell'intero workspace;
* custom DOM/storage events come infrastructure definitiva;
* account key `props24.localDb.*`;
* fallback silenzioso alla cache in memoria;
* seed runtime automatico;
* compatibilità con vecchie chiavi Rentila/Gestionale dopo il cutover;
* `LocalStorageQuotaError` come errore infrastrutturale definitivo.

---

### Conclusione S0.2

L'attuale motore locale contiene buone discipline di integrità e diversi contratti che possono essere conservati, ma la persistence architecture fisica non deve essere trasferita su Supabase.

Il target deve mantenere:

```text
validazione
integrità
scope
atomicità
migrazioni sicure
errori espliciti
invalidazione
```

eliminando invece:

```text
whole-database JSON
localStorage
singleton globale
read-repair ordinario
cache autoritativa locale
fallback in-memory
compatibilità legacy permanente
```

La migrazione dovrà quindi preservare i contratti applicativi validi, ma rifattorizzare la persistence intorno a tabelle PostgreSQL, mutation granulari e transazioni reali.
