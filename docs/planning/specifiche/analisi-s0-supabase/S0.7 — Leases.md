## S0.7 — Leases

### Stato attuale

`LeaseRecord` è un aggregate complesso che rappresenta contemporaneamente:

```text
contratto
+
relazioni Property/Tenant/Guarantor
+
configurazione economica
+
lifecycle
+
termination
+
financial state
+
activity
+
signature process
```

La Lease è inoltre l'authority di diverse relazioni usate altrove nel progetto.

Il modello business è in gran parte maturo, ma la persistence architecture è ancora fortemente legata a `getJsonDb()/saveJsonDb()` e alla riscrittura dell'intero `LocalDatabase`.

### Boundary corrente

Non esiste ancora una vera repository Lease indipendente dallo storage.

Il dominio usa direttamente `leaseRepository.ts` con accesso globale a:

```text
getJsonDb()
saveJsonDb()
```

per:

```text
create
update
activate
deactivate
terminate
archive
restore
delete
bulk lifecycle
notes
list read-model
detail read-model
```

Non sono presenti:

```text
LeaseRepository port
LeaseDatabaseGateway account/workspace scoped
Supabase-ready adapter boundary
```

La migration richiederà quindi una nuova boundary async e workspace-scoped.

### Create Lease

La create è una vera operazione multi-dominio:

```text
normalize form
→ schema validation
→ verifica Property
→ verifica Lease type
→ verifica date
→ verifica Tenant
→ verifica Guarantor
→ verifica overlap
→ verifica riferimenti assicurazioni/documenti
→ crea Lease
→ genera Payment schedule
→ crea/aggiorna deposito
→ ricostruisce relazioni Property/Tenant
→ una save
→ reread
```

La whole-database write corrente fornisce una forma di atomicità che dovrà essere sostituita da una vera transaction PostgreSQL.

Target concettuale:

```text
BEGIN
→ Lease
→ Lease-Tenant relations
→ Lease-Guarantor relations
→ generated Payments
→ deposit Payment
→ eventuali child data
→ COMMIT
```

Nessuna persistence parziale deve essere possibile.

### Property relation

Ogni Lease richiede una Property esistente e non archived.

La relazione autoritativa è:

```text
Lease.propertyId
```

Activate/restore devono ricontrollare che la Property esista e sia ancora utilizzabile.

La futura FK database proteggerà l'esistenza; le business rule lifecycle resteranno anche applicative/server-side.

### Tenant relation

Lease conserva:

```text
tenantIds[]
```

e costituisce l'authority della relazione contrattuale.

I Tenant selezionati devono:

```text
esistere
non essere archived
non essere duplicati
```

Il numero di Tenant consentiti dipende dal tipo di Lease tramite `multiTenant`.

Relazioni inverse:

```text
Tenant.leaseIds[]
Property.relations.leaseIds[]
Property.relations.tenantIds[]
```

sono proiezioni derivate e non authority indipendenti.

Nel target non devono essere replicate automaticamente come array persistiti ridondanti.

### Regola overlap

Il progetto vieta attualmente Lease sovrapposte quando:

```text
stesso Tenant
+
date sovrapposte
+
Property differente
+
Lease non archived
```

Le Lease archived non partecipano alla regola.

Questa business rule deve essere preservata.

In un ambiente multiutente la sola validazione client non è sufficiente: il target richiederà enforcement transazionale/server-side concurrency-safe.

La forma tecnica definitiva verrà decisa in S1/S6.

### Guarantor Contact

Lease conserva direttamente:

```text
guarantorIds[]
→ Contact.id
```

a differenza del Tenant, che usa child relation con `relation.id`, `contactId` e snapshot.

Il writer Lease verifica attualmente l'esistenza dei Contact, ma non impedisce esplicitamente l'uso di Contact archived.

Il reference layer distingue invece:

```text
active
archived
missing
pending
unverified
```

Esiste quindi una regola non uniforme da risolvere prima dello schema definitivo:

```text
writer Lease
→ archived Contact tecnicamente accettato

UI/reference layer
→ archived distinto e non equivalente ad active
```

### `formData` e duplicazione

`LeaseRecord` conserva sia campi top-level sia gli stessi dati dentro `formData`.

Esempi:

```text
propertyId ↔ formData.PropertyID
tenantIds ↔ formData.LeaseTenantIds
guarantorIds ↔ formData.LeaseGarantIds
leaseType ↔ formData.LeaseType
startDate ↔ formData.LeaseStartDate
endDate ↔ formData.LeaseEndDate
rentAmount ↔ formData.LeaseRentHC
utilitiesAmount ↔ formData.LeaseMaintenance
depositAmount ↔ formData.LeaseDeposit
billingPeriod ↔ formData.LeaseBillingPeriod
```

Questa duplicazione è figlia del modello form/JSON corrente e non deve diventare una seconda authority PostgreSQL.

### Configurazione economica

`LeaseFormData` contiene, oltre ai dati core:

```text
billing period
payment timing
payment method
payment day
receipt period
payment generation offset
rent
VAT
maintenance
extra PaymentItems[]
first bill
deposit
prepaid rent
receipt settings
notifications
insurance contracts[]
rent update / ISTAT settings
```

Questi dati dovranno essere classificati e modellati in S1 senza copiare automaticamente l'intero `formData` in JSONB.

### PaymentItems

`PaymentItems[]` rappresenta configurazione economica contrattuale.

Non è equivalente a `PaymentRecord`.

Regola:

```text
Lease PaymentItems
≠
Payments contabili
```

La distinzione deve essere mantenuta nel modello futuro.

### Insurance Contracts

La Lease può contenere fino a due insurance contract, con:

```text
type
description
startDate
endDate
documentId
```

La normalizzazione legacy conserva deterministicamente la prima voce per tipo.

Questi elementi hanno natura di child data contrattuali.

Il riferimento documentale è però ancora debole e può rappresentare anche riferimenti legacy/non risolti.

La relazione definitiva verrà chiarita insieme a S0.9 Documents.

### Payment generation

La create Lease genera automaticamente Payment di tipo rent/rent-first.

Ogni Payment generated conserva:

```text
leaseId
propertyId
tenantId
category
amount
dueDate
status
source = generated
accountingRole = revenue
```

La schedule è deterministica e protegge la combinazione logica:

```text
leaseId
category
dueDate
```

Queste semantiche devono essere preservate.

### Multi-tenant Payment ownership

Una Lease può avere più Tenant, ma i Payment generated usano attualmente:

```text
tenantId = lease.tenantIds[0]
```

Questo è un limite/modello corrente da riesaminare.

Non deve essere assunto automaticamente come struttura economica definitiva.

Owner:

```text
S0.8 + S1
```

### Update Lease

L'update non è una semplice `UPDATE`.

Flusso:

```text
load current Lease
→ blocco archived/signature/terminated
→ normalize/validate
→ verify relations/overlap
→ verifica storico deposito
→ verifica prepaid allocations
→ verifica modifiche Property/Tenant contro storico Payment
→ costruisce next Lease
→ riconcilia Payment futuri generated
→ gestisce deposito
→ ricostruisce derived relations
→ one save
```

Nel target questa operazione deve essere una command transazionale.

### Edit lock

Una Lease non può essere modificata quando:

```text
archived
oppure
signatureProcess attivo
oppure
status = terminata
```

La regola è protetta sia nella UI sia nel writer.

Questo doppio livello è da preservare.

### Storico finanziario

Lo storico economico limita le modifiche contrattuali.

Esempi:

```text
deposito già pagato
→ dati deposito non modificabili

Payment storici/manuali
→ possono bloccare cambio Property/Tenant

prepaid allocations
→ possono bloccare modifiche incompatibili
```

Principio:

```text
future schedule
→ rigenerabile quando consentito

historical financial evidence
→ preservata/protetta
```

### Deposit

Il deposito può generare un vero `PaymentRecord` dedicato:

```text
payment-deposit-<leaseId>
```

e `financialState.depositPaymentId` lo collega alla Lease.

Una restituzione deposito genera a sua volta:

```text
payment-deposit-return-<leaseId>
```

come expense paid.

Queste operazioni modificano Lease + Payment e devono diventare transaction atomiche.

### Prepaid rent

`financialState.prepaidAllocations[]` collega la Lease a specifici Payment generated tramite:

```text
paymentId
amount
allocatedAt
appliedAt
```

Si tratta di una vera relazione economica e non di semplice metadata cosmetico.

`financialState` non deve quindi essere trasferito automaticamente come unico blob JSONB senza distinguere authority e dati derivati.

### Lifecycle

Il lifecycle distingue chiaramente:

```text
attiva
inattiva
terminata
archived
```

Activate:

```text
ricontrolla Property
ricontrolla Tenant
ricontrolla Guarantor
ricontrolla overlap
può rigenerare deposito
```

Deactivate:

```text
status = inattiva
preserva storico e Payment
```

Terminate:

```text
valida termination date
aggiorna endDate
disabilita rinnovo
crea termination state
elimina solo generated Payment futuri non pagati
preserva storico
```

Archive:

```text
archived = true
preserva contratto/storico
```

`archive` e `terminate` sono concetti distinti e devono restare tali.

### Temporal status

Il read-model deriva:

```text
current
future
historical
inactive
archived
```

a partire da:

```text
stored status
dates
archived
```

`temporalStatus` è quindi una projection e non deve diventare automaticamente una seconda authority persistita.

### Delete

Il delete viene bloccato se la Lease possiede:

```text
Payment paid
Payment non-generated
Document owned dalla Lease
signatureProcess
```

Regola:

```text
Lease con storico/evidenze
→ archive

Lease priva di storico significativo
→ hard delete possibile
```

Non deve esistere cascade distruttivo sullo storico.

Quando il delete è consentito possono essere eliminati dati rigenerabili/non storici collegati, come generated Payment e Message collegati.

La policy singola e bulk dovrà essere uniformata nel futuro implementation layer.

### Bulk lifecycle

Le operazioni bulk:

```text
deduplicano gli ID
validano l'intero set
non producono partial mutation
effettuano una sola mutation logica
```

Il target richiede transazioni o mutation set-based.

Non devono essere implementate come loop indipendenti dal client.

### Read-model lista

La lista Lease deriva dati da:

```text
Lease
Property
Tenant
Payment
```

per costruire:

```text
Property title/address
Tenant name/email
balance
temporal status
```

`balance` è una projection derivata dai Payment.

Quindi:

```text
Lease entity repository
≠
Lease list read-model
```

### Read-model dettaglio

Il dettaglio compone:

```text
Lease
Property
Tenants
Guarantors
Payments
Documents
Communications
balance
deposit
prepaid state
temporal status
```

Il target richiederà query/read-model specifiche, non il caricamento dell'intero workspace.

### Consumer runtime

Restano accessi globali tramite:

```text
useLeasesDb
→ listLeaseItems + subscribeJsonDb

useLeaseDetail
→ getLeaseDetail + subscribeJsonDb

LeasesPage
→ getJsonDb per Property/filter/azioni

LeaseForm
→ getJsonDb per Property/Tenant snapshot
```

Contacts sono invece già letti tramite `useContactList()`.

Il cutover dovrà uniformare tutte queste source verso repository/query async workspace-scoped.

### Draft

La create Lease possiede già un buon recovery contract:

```text
Lease create riuscita
→ cleanup Draft fallisce
→ Lease resta creata
→ retry solo Draft cleanup
→ nessuna seconda create
```

Questa semantica è da preservare.

### Signature process

La firma è oggi locale.

`signatureProcess` conserva:

```text
status
startedAt
completedAt
contractDocumentId
signers[]
signatureDataUrl
```

La firma PNG viene memorizzata come Data URL.

Questo storage fisico è transitorio.

Target futuro:

```text
signature metadata
→ database

asset/file
→ Storage o servizio firma
```

Il processo di firma blocca inoltre edit e delete della Lease.

Questa business rule deve essere preservata anche se l'implementazione firma verrà rifatta.

### Contract snapshot

Prima della firma viene creato un `DocumentRecord` snapshot del contratto.

La preview live usa i dati correnti di:

```text
Lease
Property
Tenant
Contact guarantor
```

mentre il documento salvato rappresenta uno snapshot storico.

Questi due concetti devono restare distinti.

### Communications

Le comunicazioni Lease generano:

```text
MessageRecord
+
Lease activity
```

e oggi producono soltanto una bozza `mailto`.

Non esiste ancora un vero backend email.

Il futuro sistema dovrà distinguere:

```text
message persistence
activity
external send
```

### Activity

`Lease.activity[]` raccoglie eventi:

```text
created
updated
status
archive
restore
note
payment
signature
communication
```

ed è aggiornato da molte operazioni differenti.

Ha quindi natura di child/audit stream più che di semplice array embedded.

È un forte candidato a modellazione relazionale append-oriented.

Questo ridurrebbe anche il rischio di lost update concorrenti sugli array.

### Lease type catalog

`LEASE_TYPES` è attualmente un catalogo statico TypeScript con:

```text
id
label
durationMonths
multiTenant
autoRenewDefault
hasVat
```

Non è oggi un'entità database.

Non deve essere trasformato automaticamente in tabella senza una decisione esplicita in S1.

### Valutazione S0.7

Lease è il dominio che più chiaramente richiederà una vera architettura transazionale PostgreSQL.

```text
Lease business semantics
→ mature da preservare

Lease persistence architecture
→ legacy da sostituire

Lease CRUD
→ in realtà domain commands multi-table

Lease read side
→ query multi-dominio

whole-database atomicity locale
→ da sostituire con transaction reali
```

La migrazione non dovrà quindi trasformare `createLease()` in una sequenza di query Supabase indipendenti dal client.

Il contratto da preservare è:

```text
una command business
→ un risultato atomico
```

anche quando sotto vengono coinvolte più tabelle.
