## S1.10 — Contratti query e read-model

### Scopo

Definire i contratti canonici di lettura del modello Supabase target.

Le query devono sostituire i selector e le letture del `LocalDatabase` locale senza ricostruire un mega-record nel client.

Il modello read segue questi principi già approvati:

* le business table restano authority;
* i read-model possono comporre più authority e valori derivati;
* le query sono sempre side-effect free;
* il Workspace corrente definisce lo scope applicativo;
* la RLS resta il boundary di sicurezza;
* le mutation passano dai command definiti in S1.9;
* dopo una mutation il client invalida/refetcha i read-model canonici;
* nessun read-model derivato diventa una seconda authority persistita.

---

### 1. Contratto generale delle query

Una query restituisce un DTO applicativo e non deve necessariamente rispecchiare una singola row PostgreSQL.

Può comporre, per esempio:

```text
Property
+ Building
+ Lease corrente
+ Tenant
+ aggregate Payment
```

e restituire valori derivati come:

```text
unitsCount
displayName
temporalStatus
effectivePaymentStatus
monthlyEquivalent
overdueAmount
```

Tali valori non vengono persistiti come authority duplicate.

Non deve esistere una query equivalente al vecchio:

```text
LocalDatabase
```

contenente l'intero Workspace.

---

### 2. Side-effect free

Ogni query deve poter essere eseguita ripetutamente senza produrre:

```text
INSERT
UPDATE
DELETE
payment generation
read-repair persistito
draft migration persistita
Lease Activity
```

In particolare:

* una Lease query non genera Payment mancanti;
* una financial query non modifica lo stato dei Payment;
* una Draft query non aggiorna automaticamente `schema_version`;
* `unitsCount` Building viene calcolato dalla relazione con Property e non scritto durante una read.

---

### 3. Scope applicativo

Il Query Service viene costruito nel contesto del Workspace attivo.

La UI non sceglie arbitrariamente `workspace_id` per ogni query.

Le query user-private, come Draft e private note, usano anche l'Auth User corrente senza accettare un `user_id` arbitrario dal consumer.

Le cache key devono comunque includere sempre `workspace_id`.

---

### 4. Reference date

Ogni query che dipende dal tempo riceve esplicitamente:

```text
referenceDate
```

nel formato:

```text
YYYY-MM-DD
```

Vale almeno per:

* Property;
* Tenant;
* Lease;
* Payment;
* financial read-model;
* Dashboard.

Il risultato non deve dipendere implicitamente dalla timezone o dal clock del browser.

---

### 5. Paginazione e ordinamento

Le list query espongono il contratto logico:

```text
limit
cursor
```

e restituiscono:

```text
items
nextCursor
```

Il `cursor` è opaco alla UI.

S3 potrà implementarlo tramite keyset pagination, range/offset o altra tecnica compatibile senza cambiare il contratto applicativo.

Ogni ordinamento deve essere deterministico e usare `id` come tie-breaker stabile.

`totalCount` non è obbligatorio su ogni list query; viene calcolato solo quando richiesto dal prodotto.

---

### 6. Concorrenza nei read-model

I read-model relativi a root modificabili devono includere `rowVersion` quando possono essere usati come base per una command.

Vale per:

```text
Workspace
Building
Property
Contact
Tenant
Lease
Payment
Document
```

---

### 7. Lease temporal status

Il read-model Lease usa:

```text
current
future
historical
inactive
archived
```

Regole:

```text
archived_at IS NOT NULL
→ archived

contract_status = terminated
→ historical

start_date > referenceDate
→ future

end_date < referenceDate
→ historical

contract_status = active
AND start_date <= referenceDate
AND end_date >= referenceDate
→ current

altrimenti
→ inactive
```

`auto_renew = true` non estende autonomamente la Lease oltre `end_date`.

Finché PA-13 resta aperta, il rinnovo deve essere materializzato tramite date/stato canonici prima che il read-model consideri nuovamente la Lease corrente.

---

### 8. Payment effective status

`payments.status` non esiste come authority.

Il read-model deriva:

```text
paid_date IS NOT NULL
→ paid

paid_date IS NULL
AND accounting_role = revenue
AND due_date <= referenceDate
→ late

altrimenti
→ pending
```

Le metriche cash usano `paid_date`.

Le metriche due/accrual e overdue usano `due_date`.

### 14. Tenant effective status

```text

→ inactive
```

### 21. Importi Lease derivati

`periodicAmount` e `monthlyEquivalent` devono usare la stessa semantica canonica usata dalla payment schedule.

Billing period target:

```text
monthly
quarterly
semiannual
annual
```

Conversione mensile:

```text
monthly      → periodicAmount × 12 / 12
quarterly    → periodicAmount × 4  / 12
semiannual   → periodicAmount × 2  / 12
annual       → periodicAmount × 1  / 12
```

I billing period legacy esclusi da S1.5 non entrano nel nuovo read contract.

## Reference lookup

### 38. Selection vs resolve

I lookup vengono distinti in:

```text
Selection lookup
Resolve lookup
```

Selection lookup:

* restituisce soltanto entity attive;
* stesso Workspace;
* utilizzabile per creare nuove relation.

Resolve lookup:

* può restituire entity archived;
* può rappresentare riferimenti mancanti/unresolvable;
* serve a visualizzare relation storiche già esistenti.

---

### 39. Reference query iniziali

Sono previste:

```text
BuildingReferenceLookup
PropertyReferenceLookup
TenantReferenceLookup
ContactReferenceLookup
WorkspaceDocumentReferenceLookup
```

Output minimale:

```text
id
displayLabel
archived
secondaryLabel
```

Non viene caricato un Detail completo soltanto per popolare una select.

I cataloghi statici di prodotto, come Property Type, Lease Type, billing period, payment method e insurance type, restano versionati nel codice e non diventano tabelle/query PostgreSQL senza un requisito specifico.

## Implementazione fisica

### 41. Select, View e Function

S1.10 definisce i contratti applicativi ma non obbliga ogni query a una specifica implementazione PostgreSQL.

S3 potrà usare:

```text
Supabase select
PostgreSQL view
Database Function / RPC
composizione controllata
```

a seconda della complessità.

Le view accessibili dal client devono preservare la RLS delle table sottostanti e non diventare un bypass dell'authorization model.

---

### 42. Nessuna materializzazione preventiva

Non vengono introdotte inizialmente:

```text
materialized dashboard
materialized financial summary
tenant balance cache
property status cache
```

Materialized View o cache persistite saranno valutate soltanto dopo misure reali di performance.

---

## Cache e invalidation

### 43. Query key

La cache key include almeno:

```text
workspaceId
queryName
query parameters
referenceDate / period quando rilevante
```

Un cambio Workspace non può riutilizzare read-model del Workspace precedente.

---

### 44. Mutation invalidation

Dopo una command conclusa con successo:

```text
Command
→ invalidate query interessate
→ refetch canonical read-model
```

La UI non deve mantenere manualmente copie indipendenti della nuova business authority.

---

### 45. Realtime

Supabase Realtime non è obbligatorio in S1.10.

Se introdotto successivamente:

```text
Realtime event
→ cache invalidation
→ Query refetch
```

e non:

```text
Realtime payload
→ nuova authority completa del client
```

---

## Vincoli consolidati

S1.10 stabilisce quindi che:

* il client non ricostruisce più `LocalDatabase`;
* le query restituiscono read-model mirati per capability;
* i valori derivati restano derivati;
* le query non producono mutation;
* Workspace e Auth User definiscono lo scope;
* ogni semantica temporale usa `referenceDate`;
* Lease, Tenant, Property e Payment hanno stati effettivi derivati deterministicamente;
* `auto_renew` non estende implicitamente una Lease oltre `end_date`;
* Payment multi-tenant viene attribuita finanziariamente soltanto a `payments.tenant_id`;
* Detail e tab pesanti sono query separate;
* Dashboard e financial read-model distinguono cash da due/accrual;
* Document file access viene risolto on-demand;
* Draft read non esegue migration persistite;
* selection lookup e resolve lookup hanno semantiche diverse;
* Realtime, quando presente, serve all'invalidation e non sostituisce la Query authority;
* implementation detail SQL resta rinviato a S3;
* la matrice index S1.8 viene estesa con i query path identificati in questa task.
