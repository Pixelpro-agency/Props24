## S1.6 — Schema Documents, Files, Communications e Drafts

### Scopo

S1.6 definisce il modello target PostgreSQL/Supabase per:

* file fisici;
* documenti e relativi metadata;
* collegamenti documentali a Property, Tenant e Lease;
* libreria documenti Workspace;
* contract snapshot;
* firme locali;
* Draft;
* file temporanei delle Draft;
* comunicazioni Lease preparate.

Il modello separa definitivamente:

```text
File Object
→ contenuto fisico

Document
→ significato e metadata

Document Link
→ utilizzo nel dominio

Draft
→ stato temporaneo personale

Communication
→ comunicazione preparata e relativo storico destinatari
```

Non vengono trasferiti nel target `StoredLocalFile.dataUrl`, ownership polimorfe prive di FK, `Lease.signatureProcess` embedded o `MessageRecord` duplicati per Lease.

---

## Vincoli ereditati da S0/S1.1–S1.5

Restano vincolanti:

* business data Workspace-scoped;
* Supabase Storage per i byte;
* PostgreSQL per metadata, ownership e relazioni;
* nessuna FK business verso `storage.objects`;
* bucket business privati;
* UUID opachi per entity con identity propria;
* cross-workspace integrity protetta dal database;
* RLS separata dai flag business di condivisione;
* file/documenti non modellati come JSONB;
* JSONB ammesso soltanto dove il dominio è realmente flessibile e versionato;
* Draft personali anche quando persistite remotamente;
* command multi-record atomiche;
* Lease Activity separata e append-oriented in S1.7;
* delete dello Storage gestito tramite workflow compensante;
* nessuna tabella creata per semplici placeholder del vecchio `LocalDatabase`.

---

# Modello Documents / Files approvato

## 1. File Object

Il contenuto fisico viene rappresentato da:

```text
public.file_objects

id
workspace_id

storage_bucket
storage_path

original_name
mime_type
size_bytes

created_at
```

`file_objects.id` è un UUID.

`storage_bucket` e `storage_path` identificano l'oggetto conservato in Supabase Storage.

Non vengono persistiti:

```text
data_url
file_url
signed_url
public_url
```

e non viene introdotta alcuna FK verso `storage.objects`.

---

## 2. Lifecycle del file fisico

Un File Object rappresenta una specifica versione fisica del contenuto.

La sostituzione di un file produce:

```text
nuovo File Object
+
nuovo Storage object
```

e non sovrascrive silenziosamente quello precedente.

Il file fisico può essere eliminato soltanto quando non è più referenziato.

L'eliminazione della row PostgreSQL e dell'oggetto Storage deve essere gestita tramite workflow idempotente/compensante.

I limiti locali derivati dai Data URL, come 2 MB per file o 3 MB complessivi, non diventano constraint strutturali del nuovo schema.

---

## 3. Document

Il significato business viene rappresentato separatamente:

```text
public.documents

id
workspace_id

file_object_id nullable
source_document_id nullable

origin
is_library_item

category nullable
title nullable
description nullable

issued_on nullable
expires_on nullable
comments nullable

is_shared

row_version
created_at
updated_at
```

`file_object_id` collega il documento alla versione fisica.

`source_document_id` conserva la provenance quando il documento deriva dal collegamento di un documento esistente.

---

## 4. Origin e provenance

Valori iniziali di `origin`:

```text
uploaded
linked
generated
metadata
```

Semantica:

```text
uploaded
→ file fornito dall'utente

linked
→ documento derivato da un documento esistente

generated
→ artifact creato da Props24

metadata
→ record documentale senza file fisico
```

Un documento `linked` riceve un proprio `documents.id`, conserva metadata propri e condivide il `file_object_id` esistente.

`source_document_id` indica la provenienza, ma non viene utilizzato come catena runtime per risolvere il file.

La versione fisica viene quindi fissata al momento del collegamento.

---

## 5. Workspace Document Library

Il vecchio concetto:

```text
ownerType = global
```

diventa una libreria interna al Workspace.

Target:

```text
documents.is_library_item = true
```

Non esistono documenti business globali fra Workspace differenti.

Un documento della libreria può essere riutilizzato creando un nuovo Document `linked`, senza duplicare il File Object.

---

## 6. Document Link

L'associazione al dominio viene rappresentata da:

```text
public.document_links

workspace_id
document_id

property_id nullable
tenant_id nullable
lease_id nullable

role
position nullable

created_at
```

Per ogni row deve essere valorizzato esattamente uno fra:

```text
property_id
tenant_id
lease_id
```

Non viene utilizzato:

```text
owner_type
owner_id
```

come relazione polimorfa priva di FK.

Ogni Document non-library appartiene inizialmente a un singolo contesto business.

---

## 7. Ruoli documentali

Ruoli Property iniziali:

```text
photo
cadastral_attachment
contract
document
```

Ruoli Tenant:

```text
photo
identity_front
identity_back
company_registry
document
```

Ruoli Lease:

```text
document
contract_snapshot

```

Le cardinalità e i `CHECK` owner-aware definitivi appartengono a S1.8.

---

## 8. Mapping Property

Il modello Property approvato in S1.3 viene completato così:

```text
PropertyCadastreDocument
→ cadastral_attachment

PropertyPhotos[]
→ photo

PropertyContracts[]
→ contract

PropertyDocuments[]
→ document
```

Gli ID persistenti delle entity documentali esistenti vengono preservati come `documents.id`.

Metadata quali tipo, descrizione, data di rilascio, scadenza, commenti e condivisione vengono normalizzati nelle colonne Document.

---

## 9. Mapping Tenant

Il modello Tenant approvato in S1.4 viene completato così:

```text
TenantPhoto
→ photo

TenantIDCard
→ identity_front

TenantIDCardBack
→ identity_back

TenantCompanyRegistryFile
→ company_registry

TenantDocuments[]
→ document
```

`TenantDocument.id` diventa `documents.id`.

L'attuale `existingDocumentId` converge in:

```text
source_document_id
+
file_object_id condiviso
```

Filename, MIME e dimensione appartengono al File Object e non vengono duplicati come authority Tenant.

---

## 10. Mapping Lease

I Document Lease correnti diventano:

```text
Document
+
DocumentLink(role = document)
```

Il contract snapshot diventa:

```text
Document
origin = generated

DocumentLink
role = contract_snapshot
```

S1.6 completa inoltre S1.5 aggiungendo:

```text
lease_insurance_contracts.document_id nullable
```

verso il relativo documento Lease.

Il vecchio `LeaseDepositDocument` non genera invece una nuova authority finché il relativo flusso non viene realmente implementato.

---

## 11. Categoria e condivisione

Non viene introdotta una tabella:

```text
document_categories
```

soltanto per replicare gli ID numerici legacy.

Il target iniziale usa:

```text
documents.category
```

come valore testuale.

Il vecchio `category_id` numerico non è authority.

Anche:

```text
documents.is_shared
```

resta metadata business e non rappresenta:

```text
RLS
accesso anonimo
bucket pubblico
permission grant
```

L'authorization documentale viene definita separatamente.

---

## 12. Delete Document

Un Document non può essere eliminato quando una relazione business ne richiede la conservazione.

Sono già casi espliciti:

```text
contract snapshot usato dalla firma
insurance document collegato
```

L'eliminazione di un Document linked non elimina né il Document sorgente né il relativo File Object se ancora referenziato.

# Signature

## 13. Processo di firma

L'attuale `Lease.signatureProcess` embedded viene normalizzato in:

```text
public.lease_signature_processes

workspace_id
lease_id
contract_document_id

started_at
completed_at nullable
```

PK logica:

```text
lease_id
```

Il modello iniziale mantiene una sola procedura corrente per Lease.

---

## 14. Firmatari

Target:

```text
public.lease_signature_signers

workspace_id
lease_id

signer_key
position
role

tenant_id nullable
contact_id nullable

name_snapshot

signed_at nullable
signature_document_id nullable
```

Identity logica:

```text
(lease_id, signer_key)
```

Ruoli:

```text
landlord
tenant
guarantor
```

Il locatore viene rappresentato tramite snapshot dei dati Workspace, senza inventare una FK Tenant/Contact.

---

## 15. Stato e file firma

Lo stato del singolo firmatario deriva da:

```text
signed_at
```

e quello complessivo del processo da signer e `completed_at`.

Non vengono quindi persistiti stati duplicati `pending/signed/in_progress/completed` come authority parallele.

La firma grafica viene salvata attraverso:

```text
File Object
→ Document
→ signature_document_id
```

e non tramite `signatureDataUrl`.

La feature continua a rappresentare la firma locale corrente e non viene qualificata da S1.6 come firma elettronica qualificata.

Il reset del processo elimina processo, signer e relativi attachment di firma, ma conserva il contract snapshot.

# Receipts

## 16. Ricevute

Nel primo cutover la ricevuta resta un artifact derivato dai dati Payment/Lease.

Non viene creata automaticamente una Document row persistente per ogni ricevuta.

Resta quindi:

```text
payments.receipt_number
→ metadata economico

render/download ricevuta
→ derived artifact
```

Il futuro lifecycle documentale/fiscale delle ricevute resta collegato alle decisioni PA-04/PA-05.

# Drafts

## 17. Draft come entity tecnica personale

Target:

```text
public.drafts

id
workspace_id
user_id

form_type
mode
entity_id nullable

payload jsonb
schema_version

created_at
updated_at
```

`payload` è uno dei casi intenzionali in cui JSONB è appropriato.

Il contenuto resta però:

```text
temporaneo
versionato
validato dalla DraftDefinition
privo di byte/file incorporati
```

---

## 18. Ownership e identity Draft

La Draft appartiene a:

```text
user_id
```

ed è contestualizzata da:

```text
workspace_id
```

Non diventa collaborativa.

La logical identity è:

```text
user_id
+
workspace_id
+
form_type
+
mode
+
entity_id
```

Per:

```text
mode = create
→ entity_id NULL

mode = edit
→ entity_id valorizzato
```

L'upsert conserva `id` e `created_at` e aggiorna payload, schema version e `updated_at`.

`entity_id` è un riferimento tecnico polimorfo governato dal Draft Repository e non una FK generica verso più business table.

---

## 19. Draft Files

I file temporanei delle Draft non entrano nel JSONB.

Target:

```text
public.draft_files

workspace_id
draft_id
file_object_id

role
position nullable

created_at
```

Quando la business mutation riesce:

```text
Draft File
→ stesso File Object
→ Document
→ Document Link
```

Il file fisico non viene caricato nuovamente.

---

## 20. Cleanup Draft

Resta vincolante:

```text
business mutation riuscita
+
cleanup Draft fallisce

→ business mutation resta valida
→ non viene ripetuta
→ si ritenta soltanto il cleanup
```

La Draft e i relativi Draft File sono user-private.

Non viene introdotto un requisito di collaborative realtime editing.

---

# Communications

## 21. Communication come authority

L'attuale `MessageRecord` rappresenta una comunicazione preparata e non una email realmente inviata.

Target:

```text
public.communications

id
workspace_id

channel
status

subject
body

created_at
```

Valori iniziali:

```text
channel = email
status = prepared
```

Non vengono inventati stati `sent`, `delivered`, `opened` o `failed` prima dell'introduzione di un vero servizio di invio.

---

## 22. Una Communication per azione

Una preparazione che coinvolge più Lease genera:

```text
1 Communication
+
N Communication Targets
```

e non una copia dello stesso Message per ogni Lease.

---

## 23. Communication Targets

Target:

```text
public.communication_targets

workspace_id
communication_id
lease_id
tenant_id

position

name_snapshot
email_snapshot
```

Identity logica:

```text
(communication_id, lease_id, tenant_id)
```

Ogni row conserva sia il riferimento business sia lo snapshot storico del destinatario.

---

## 24. Snapshot destinatari

`name_snapshot` ed `email_snapshot` sono duplicazioni intenzionali.

Non sostituiscono la Tenant authority corrente.

Rappresentano invece:

```text
chi risultava destinatario
+
con quale nome/email
```

nel momento in cui la comunicazione è stata preparata.

L'eventuale deduplicazione degli indirizzi durante `mailto` o futuro invio non elimina i target business distinti.

---

## 25. Lifecycle Communication

La Communication corrente è append-oriented.

Nel primo modello non richiede `row_version`.

La futura introduzione di delivery, retry o provider email potrà aggiungere un modello operativo separato senza modificare il significato storico di `prepared`.

---

# Transaction boundary e Activity

## 26. Command documentali e comunicazioni

Quando una command produce anche Lease Activity, la mutation business e l'append Activity devono essere atomici.

Comprende almeno:

```text
CreateLeaseDocument
LinkLeaseDocument
UpdateLeaseDocument
DeleteLeaseDocument

StartSignature
SignLease
ResetSignature

PrepareCommunication
```

S1.7 definisce il modello Activity.

S1.9 definisce le transaction concrete.

# Scope e RLS

## 27. Classificazione

Sono Workspace-scoped:

```text
file_objects
documents
document_links

communications
communication_targets

lease_signature_processes
lease_signature_signers
```

Sono invece Workspace-contextual ma user-private:

```text
drafts
draft_files
```

Le relazioni devono impedire riferimenti cross-workspace anche indipendentemente dalla RLS.

I business file restano privati nello Storage.

Le policy PostgreSQL/Storage definitive appartengono a S1.11 e S2.7.
