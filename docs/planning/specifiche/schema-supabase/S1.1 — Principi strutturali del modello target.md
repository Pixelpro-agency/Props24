## S1.1 — Principi strutturali del modello target

### Scopo

S1.1 definisce le regole strutturali comuni che devono vincolare l'intero modello PostgreSQL/Supabase di Props24.

Questa sottotask non definisce ancora lo schema dettagliato di Buildings, Properties, Contacts, Tenants, Leases, Payments, Documents o Drafts. Tali modelli vengono progettati nelle successive S1.2–S1.7.

S1.1 stabilisce invece la grammatica comune del nuovo database, così che le successive decisioni non introducano convenzioni incompatibili, authority duplicate o nuovi accoppiamenti alla persistence fisica.

Le decisioni derivano dai vincoli consolidati in S0.1–S0.12 e dalla verifica delle capacità correnti di PostgreSQL/Supabase.

---

## Vincoli ereditati da S0

Restano vincolanti:

* il database locale costruito durante i Blocchi A/B/C costituisce baseline comportamentale, non modello fisico da copiare;
* `LocalDatabase` non deve essere ricostruito come mega-record o mega-read-model sopra PostgreSQL;
* business authority, dati derivati, query/read-model e stato UI devono essere distinti;
* Auth User, Profile, Workspace e Membership sono concetti separati;
* i dati business condivisi devono essere workspace-scoped;
* RLS/server authorization costituisce il confine di sicurezza;
* repository, command e query/read-model devono avere boundary esplicite;
* le query devono essere side-effect free;
* le mutation multi-record che costituiscono una singola operazione business devono avere una vera transaction boundary;
* PostgreSQL conserva dati business, metadata e relazioni; i file binari utilizzano Supabase Storage;
* non sono ammessi implicit dual-write o silent fallback Supabase → persistence locale;
* i dataset locali correnti sono dati di sviluppo/collaudo e non vengono importati automaticamente come dati produzione;
* gli ID persistiti sono identità opache: formato e prefissi non determinano tipo, validità o relazione.

# Convenzioni strutturali approvate

## 1. Naming SQL

Lo schema PostgreSQL usa identificatori:

```text
lowercase
snake_case
non quotati
```

Esempi:

```text
workspace_memberships
workspace_id
created_at
fiscal_code
archived_at
```

Le tabelle applicative usano nomi plurali.

Convenzioni:

```text
table
→ plurale

foreign key
→ <entity>_id

timestamp
→ *_at

date business
→ *_date quando necessario
```

Il modello TypeScript può continuare a utilizzare `camelCase`; il mapping fra modello applicativo e persistence appartiene agli adapter.

Non introdurre identificatori SQL CamelCase che richiedano quoting permanente.

---

## 2. Schema PostgreSQL

Il target utilizza:

```text
auth.*
→ gestito da Supabase Auth

storage.*
→ gestito da Supabase Storage

public.*
→ tabelle applicative Props24 protette da RLS
```

Un eventuale schema non esposto alla Data API potrà essere introdotto soltanto se emergerà una necessità server-side concreta.

Non introdurre uno schema applicativo custom soltanto per separazione nominale.

Le business table esposte al frontend devono avere RLS abilitata e policy coerenti con il modello Workspace/Membership definito nelle successive S1.

---

## 3. Strategia degli ID

La primary key standard delle nuove entity è:

```sql
id uuid primary key default gen_random_uuid()
```

Il principio si applica alle business entity quali:

* Workspace;
* Building;
* Property;
* Contact;
* Tenant;
* Lease;
* Payment;
* Document;
* altre entity reali definite successivamente.

Regole:

* UUID opaco;
* nessun prefisso semantico richiesto;
* il formato dell'ID non determina il tipo;
* il server può generare l'ID tramite default PostgreSQL;
* il client può generare anticipatamente un UUID quando l'identità deve esistere prima del primo salvataggio;
* gli ID già creati devono essere preservati nei successivi round-trip.

Questo consente di mantenere il contratto:

```text
create once
→ preserve thereafter
```

Le relation che possiedono già una propria identità persistente, come TenantGuarantor o TenantEmergencyContact, mantengono un proprio UUID.

Le pure join table senza identità autonoma possono invece utilizzare primary/unique key composite se il loro dominio non richiede un ID indipendente.

Non aggiungere automaticamente un `legacy_id` a tutte le tabelle.

Gli eventuali requisiti di mapping legacy durante il cutover saranno definiti esplicitamente in S1.12.

---

## 4. Timestamp e date

Usare `timestamptz` per istanti reali, metadata ed eventi.

Esempi:

```text
created_at
updated_at
archived_at
confirmed_at
sent_at
event_at
```

Standard di base:

```sql
created_at timestamptz not null default now()
updated_at timestamptz not null default now()
```

`updated_at` deve essere gestito in modo affidabile lato database/infrastruttura e non dipendere esclusivamente dall'orologio del browser.

Usare invece `date` per date civili o contrattuali prive di un significato di istante UTC.

Esempi:

* data di nascita;
* data inizio locazione;
* data fine locazione;
* scadenza documento.

Non convertire automaticamente una data civile in `timestamptz`.

---

## 5. Archive e delete

Lo stato archivio target usa:

```text
archived_at timestamptz null
```

Semantica:

```text
archived_at IS NULL
→ active

archived_at IS NOT NULL
→ archived
```

Non persistere anche un boolean `is_archived` o equivalente come seconda authority.

La UI può continuare a ricevere un read-model boolean derivato.

Archive e delete restano operation differenti:

```text
archive
→ lifecycle reversibile

delete
→ cancellazione reale
```

Non introdurre un generico `deleted_at` per trasformare automaticamente ogni delete in soft-delete.

---

## 6. Foreign key e delete policy

Le relazioni canoniche devono essere rappresentate da vere foreign key.

Default per le business relation:

```text
RESTRICT / NO ACTION
```

`ON DELETE CASCADE` non è il comportamento predefinito.

Cascade è ammesso soltanto quando il record figlio:

* è realmente owned dal parent;
* non possiede vita autonoma;
* non deve sopravvivere al parent;
* non viola un contratto di delete protection esistente.

Devono essere preservati i contratti già consolidati, fra cui:

* Building non cancellabile quando referenziato da Property;
* Contact non cancellabile quando referenziato;
* Property non cancellabile quando esistono Lease/Payment bloccanti;
* nessuna cancellazione transitiva implicita dei business record.

---

## 7. Workspace scope

Ogni business row condivisa deve possedere direttamente, quando semanticamente appropriato:

```text
workspace_id uuid not null
```

Questo vale non soltanto per le aggregate root, ma anche per child, link e audit row quando utile all'integrità e alle policy.

Esempi concettuali:

```text
properties
property_notes
tenant_guarantors
lease_tenants
lease_activities
documents
payments
```

Lo scope diretto permette di:

* applicare RLS in modo semplice;
* evitare policy dipendenti da lunghe catene di join;
* rendere evidente l'ownership della row;
* indicizzare direttamente il confine autorizzativo.

Non tutte le row applicative sono necessariamente workspace-scoped: dati personali come le Draft potranno richiedere un modello user/workspace specifico definito in S1.6.

---

## 8. Integrità cross-workspace

RLS non deve essere l'unico meccanismo che impedisce relazioni fra workspace differenti.

Il database deve rendere impossibile costruire una relazione del tipo:

```text
child.workspace_id = workspace A
parent            = record del workspace B
```

Le foreign key o constraint definite in S1.8 devono quindi garantire workspace consistency.

Principio concettuale:

```text
child(workspace_id, parent_id)
→ parent(workspace_id, id)
```

La forma SQL definitiva viene rimandata alla matrice constraint di S1.8.

---

## 9. NULL e valori assenti

Un valore opzionale semanticamente assente deve essere rappresentato con:

```text
NULL
```

non con:

```text
''
'   '
```

Il persistence boundary deve normalizzare i valori vuoti secondo la semantica del dominio.

Questo principio è particolarmente importante per:

* codice fiscale;
* P.IVA;
* email opzionale;
* riferimenti opzionali;
* identificatori che partecipano a uniqueness rule.

Le business rule già verificate per cui un identificatore fiscale vuoto non identifica e non collide devono essere preservate.

---

## 10. Tipi di dato di base

Vocabolario target di default:

| Semantica                   | PostgreSQL    |
| --------------------------- | ------------- |
| Identità                    | `uuid`        |
| Testo                       | `text`        |
| Boolean reale               | `boolean`     |
| Data civile/contrattuale    | `date`        |
| Istante/evento              | `timestamptz` |
| Importo/numero esatto       | `numeric`     |
| Payload flessibile motivato | `jsonb`       |

Per importi monetari o valori economici esatti:

```text
numeric
```

Non utilizzare:

```text
real
float
double precision
```

La precisione esatta viene definita nella relativa sottotask di dominio.

`text` è il default per le stringhe salvo esista un vero limite business che giustifichi una lunghezza massima.

Non introdurre `varchar(255)` per convenzione generica.

---

## 11. Stati applicativi

Per vocabolari finiti applicativi il default è:

```text
text
+
CHECK constraint
```

Non usare PostgreSQL native ENUM come scelta automatica.

La scelta consente di evolvere più facilmente gli stati tramite migration versionate.

Se un vocabolario rappresenta dati configurabili dall'utente o dal prodotto, deve essere valutata una tabella catalogo invece di ENUM/CHECK.

Un ENUM PostgreSQL potrà essere adottato soltanto quando una successiva S1 dimostrerà che il vocabolario è sufficientemente stabile e condiviso da giustificarlo.

---

## 12. Dati derivati

Un dato derivabile da altre authority non viene persistito come seconda authority salvo motivazione esplicita.

Restano classificati come derived, fra gli altri:

```text
Building.unitsCount
Property.relations.leaseIds
Property.relations.tenantIds
Tenant.leaseIds
effective lifecycle/status
balance
financial summary
Dashboard KPI
```

Ordine di preferenza:

```text
query
→ view
→ aggregate query
```

Materialized view o denormalizzazione controllata possono essere introdotte soltanto se dati e misure reali dimostrano una necessità.

Non denormalizzare preventivamente per replicare il modello locale.

Generated columns PostgreSQL non sono la soluzione per dati derivati da altre tabelle.

---

## 13. Policy JSONB

JSONB non sostituisce il modello relazionale.

È ammesso quando la struttura è realmente variabile o rappresenta intenzionalmente uno snapshot.

Casi approvati:

### Draft payload

```text
drafts.payload
```

perché rappresenta form state:

* temporaneo;
* versionato;
* potenzialmente polymorphic;
* non authority relazionale.

### Snapshot storico immutabile

Esempi concettuali:

```text
*_snapshot
recipient_snapshot
contract_snapshot
provider_response_snapshot
```

quando serve conservare lo stato storico esatto.

Ogni snapshot deve essere distinguibile dall'authority corrente e, quando necessario, possedere una propria versione.

### Metadata variabile

Ammesso soltanto quando non costituisce business relation o authority che richieda colonne e constraint dedicate.

Non sono ammessi come scorciatoia:

```text
properties.data jsonb
tenants.data jsonb
leases.data jsonb
payments.data jsonb
```

né array JSON di ID per modellare relazioni canoniche.

---

## 14. Nested data e child table

Un nested object deve diventare una child table quando possiede una o più delle seguenti caratteristiche:

* ID persistente;
* cardinalità multipla;
* riferimento verso altre entity;
* constraint proprie;
* lifecycle proprio;
* modifica indipendente;
* interrogazione indipendente;
* necessità di concurrency indipendente.

Esempi da valutare come child entity nelle S1 successive:

* Tenant guarantors;
* Tenant emergency contacts;
* Tenant documents;
* Property keys;
* Lease activities;
* Lease participants.

Regola:

```text
stable identity
→ row
```

non elemento anonimo dentro un mega-JSON.

Le relazioni N:N devono usare join table e non array JSON/UUID persistiti nella parent.

---

## 15. Identity delle relation

Distinguere due casi.

### Pure relation

Una relazione senza identity o attributi propri può utilizzare una chiave composite.

Esempio concettuale:

```text
lease_tenants
PRIMARY/UNIQUE (lease_id, tenant_id)
```

se il modello finale confermerà che la relation non necessita di un proprio ID.

### Relation con identità propria

Le relation per cui l'applicazione possiede già un contratto di ID persistente mantengono un proprio:

```text
id uuid
```

Esempi:

* TenantGuarantor;
* TenantEmergencyContact.

La migrazione relazionale non deve distruggere i contratti ID consolidati nei Blocchi B/C.

---

## 16. Optimistic concurrency

Le aggregate root condivise e mutabili devono proteggere gli utenti da lost update concorrenti.

Principio target:

```text
row_version bigint not null
```

con incremento monotono ad ogni modifica rilevante.

Update concettuale:

```text
WHERE id = requested_id
AND row_version = expected_version
```

Se la versione non coincide:

```text
concurrent_update
/
stale_record
```

La persistence non deve applicare silenziosamente un last-write-wins che sovrascrive modifiche concorrenti.

La UI iniziale non deve tentare merge automatici non progettati.

Comportamento minimo:

```text
record modificato da un altro utente
→ blocco del save
→ richiesta di reload/riconciliazione
```

L'applicazione concreta del meccanismo ai singoli domini viene definita nelle successive S1.

---

## 17. Atomicità multi-record

Una business command che modifica più record come singola operazione logica deve essere eseguita all'interno di una vera transaction PostgreSQL/server-side.

Non sostituire una mutation locale atomica con una sequenza browser:

```text
await write A
await write B
await write C
```

che possa lasciare persistenza parziale.

Esempi di operation già candidate:

* Property aggregate mutation;
* Tenant aggregate mutation;
* bulk lifecycle;
* Lease create/update;
* Lease terminate;
* Payment confirmation;
* deposit return;
* prepaid allocation;
* Document + Lease Activity.

La matrice definitiva delle transaction command appartiene a S1.9.

Il meccanismo concreto server-side viene deciso soltanto dopo tale matrice.

---

## 18. Query side-effect free

Ogni query/read operation deve essere:

```text
read-only
```

Una normale lettura non può provocare:

* INSERT;
* UPDATE;
* DELETE;
* repair persistito;
* generazione Payment;
* cambio persistito di stato temporale;
* normalizzazione con write.

Principio:

```text
SELECT / query
→ nessuna mutation
```

Qualunque modifica automatica deve avere un owner esplicito:

* command;
* job;
* scheduler;
* migration;
* server process.

---

## 19. Repository, Command e Query

Non introdurre una `GenericRepository<T>` come abstraction universale.

Il target distingue:

### Entity repository

Per CRUD/lifecycle relativamente semplici.

Esempi:

```text
ContactRepository
BuildingRepository
```

### Command

Per mutation business aggregate o transazionali.

Esempi concettuali:

```text
CreateLease
ConfirmPayment
ArchiveTenant
```

### Query / read-model

Per list, detail, analytics e cross-domain read.

Esempi:

```text
PropertyDetailQuery
LeaseDetailQuery
DashboardQueries
WorkspaceSearchQuery
```

La UI deve dipendere da boundary applicative e non conoscere:

* SQL;
* nomi fisici delle tabelle;
* `.from(...)` Supabase sparsi nei componenti;
* dettagli dei bucket Storage.

Target:

```text
UI
→ repository / command / query
→ adapter Supabase
→ PostgreSQL / Storage
```

---

## 20. Supabase Storage

Supabase Storage è il target dei file binari.

Le nostre tabelle PostgreSQL conservano i metadata business necessari, come:

* relazione al dominio;
* bucket;
* object path/key;
* MIME type;
* size;
* hash se necessario;
* original filename;
* ownership/access metadata;
* timestamp.

Non creare foreign key applicative verso `storage.objects`.

Lo schema `storage` è gestito da Supabase e non costituisce il nostro domain schema.

Le operazioni fisiche sui file devono utilizzare la Storage API prevista dal provider.

---

## 21. Atomicità fra Storage e PostgreSQL

Upload binario e mutation PostgreSQL non appartengono automaticamente alla stessa transaction ACID.

Il sistema deve quindi utilizzare workflow espliciti, idempotenti e compensativi.

Pattern possibili da dettagliare in S1.6/S3.8:

```text
upload object
→ commit metadata/business mutation
→ success

metadata/business failure
→ cleanup object
```

oppure un modello con stato pending/finalizzazione se necessario.

Requisiti:

* niente file orfani permanenti;
* niente metadata orfani;
* retry sicuro;
* idempotenza;
* cleanup verificabile;
* error handling esplicito.

Non promettere atomicità cross-provider che Supabase Storage/PostgreSQL non forniscono come singola transaction.

---

## 22. Storage privato di default

I documenti business sono privati di default.

Esempi:

* documenti identità;
* contratti;
* ricevute;
* assicurazioni;
* documenti Tenant/Property/Lease.

Bucket pubblico soltanto per asset che il prodotto dichiara intenzionalmente pubblici.

Le policy di accesso definitive vengono progettate in S1.11/S2.7.

---

## 23. Schema version e migration

La versione fisica del database non viene gestita tramite un campo equivalente a:

```text
LocalDatabase.meta.schemaVersion
```

La source of truth dello schema diventa la history delle migration SQL versionate.

Target:

```text
supabase/migrations/*.sql
```

Le modifiche di schema devono essere:

* versionate;
* riproducibili;
* salvate nel repository;
* applicabili agli ambienti previsti.

Il Dashboard Supabase non deve diventare una source of truth parallela non tracciata.

Un eventuale `schemaVersion` resta invece valido quando rappresenta domain data.

Esempio:

```text
Draft.schemaVersion
```

per interpretare correttamente un payload versionato.

---

## 24. Compatibilità PostgreSQL

Il modello progettato in S1 deve essere compatibile con PostgreSQL 17.

S2.1 deve verificare la versione effettiva utilizzata dal progetto Supabase prima di usare feature dipendenti dalla specifica release.

Non introdurre in S1 dipendenze da feature PostgreSQL 18-only.

# Grammatica generale delle business table

Una aggregate root condivisa potrà assumere concettualmente una forma del tipo:

```text
public.<business_table>

id
→ uuid

workspace_id
→ uuid

created_at
→ timestamptz

updated_at
→ timestamptz

archived_at
→ nullable timestamptz, se il dominio supporta archive

row_version
→ bigint, quando richiesta optimistic concurrency

campi canonici
→ colonne tipizzate

relazioni
→ foreign key / join table

derived values
→ query / view, non authority

payload variabili motivati
→ jsonb

file binari
→ Supabase Storage
```

Non tutte le tabelle devono necessariamente possedere tutte queste colonne.

Questa struttura rappresenta una grammatica comune, non uno schema universale da copiare automaticamente.
