## S1.11 — Matrice RLS

### Scopo

S1.11 definisce il security boundary PostgreSQL/Supabase del modello Props24.

La catena autorizzativa target è:

```text
Supabase Auth User
→ auth.uid()
→ Workspace Membership attiva
→ RLS / command authorization
→ business data
```

Lo scope scelto dal frontend serve alla composizione applicativa, ma non costituisce mai authority di sicurezza.

RLS, PostgreSQL grants e command authorization sono livelli complementari e non sostituibili fra loro.

---

## 1. Principi generali

Tutte le table applicative esposte hanno RLS attiva.

Nel primo cutover:

```text
anon
→ nessun accesso ai dati Props24

authenticated
→ accesso esplicitamente autorizzato

service_role
→ solo server/system
```

`is_public` sulle Property e `is_shared` sui Document restano metadata business/presentation e non concedono accesso anonimo.

Non vengono introdotti accessi automatici basati su:

```text
Tenant.email = Auth email
Invitation status
Tenant record
Document.is_shared
Property.is_public
```

Il futuro tenant portal resta fuori scope.

---

## 2. Role model iniziale

I soli Workspace role iniziali restano:

```text
owner
member
```

Entrambi possono operare sui normali business data del Workspace tramite le command autorizzate.

La differenza iniziale è:

```text
owner
→ business management
→ Workspace administration
→ Membership administration

member
→ business management
→ nessuna Workspace administration
```

Non vengono anticipati ruoli futuri come:

```text
read_only
accountant
manager
professional
tenant
```

`owner` non è un superutente capace di leggere dati dichiarati user-private.

---

## 3. Membership come authorization authority

L’authority resta:

```text
workspace_memberships
WHERE revoked_at IS NULL
```

I role Workspace non vengono copiati nel JWT come security authority.

La revoca deve essere effettiva dalla richiesta DB successiva anche se il JWT dell’utente non viene aggiornato.

L’Active Workspace della UI non partecipa alla RLS: un utente può essere autorizzato contemporaneamente su più Workspace.

---

## 4. Helper autorizzativi

Lo schema `private` contiene almeno:

```text
private.is_workspace_member(workspace_id uuid)
private.is_workspace_owner(workspace_id uuid)
```

Gli helper sono:

```text
STABLE
SECURITY DEFINER
SET search_path = ''
```

e usano nomi schema-qualified.

`private` non viene esposto tramite Data API.

Le policy non interrogano ricorsivamente `workspace_memberships`; i lookup Membership passano dagli helper `private`.

Possono inoltre esistere helper dedicati come:

```text
private.can_access_draft(...)
private.can_access_file_object(...)
```

quando l’authorization dipende da più relazioni.

---

# Profile / Workspace / Membership

## 5. Profiles

`profiles` è user-scoped.

```text
SELECT
→ user_id = auth.uid()

UPDATE
→ soltanto propria row
→ soltanto colonne mutabili

INSERT
→ non diretto

DELETE
→ non diretto
```

La creazione del Profile appartiene al signup lifecycle.

Il Profile resta leggibile e modificabile anche se l’Auth User non appartiene ancora ad alcun Workspace.

I Profile degli altri Workspace member non diventano genericamente leggibili.

Campi come:

```text
user_id
created_at
```

non sono direttamente modificabili.

---

## 6. Workspace

`workspaces`:

```text
SELECT
→ active Workspace member

direct INSERT/UPDATE/DELETE
→ DENY
```

Create e mutation passano dalle command.

`workspace_profiles`:

```text
SELECT
→ active Workspace member

mutation
→ owner command
```

---

## 7. Membership

La propria Membership attiva è leggibile dall’utente.

Un owner può leggere tutte le Membership del proprio Workspace, comprese quelle revoked, tramite il relativo contratto amministrativo.

Il client non esegue direttamente:

```text
INSERT
UPDATE
DELETE
```

su `workspace_memberships`.

Le mutation passano da:

```text
AddWorkspaceMember
ReactivateWorkspaceMember
ChangeWorkspaceMemberRole
RevokeWorkspaceMember
```

e richiedono owner authorization.

`CreateWorkspace` fa eccezione perché un nuovo Workspace non possiede ancora una Membership: richiede soltanto un Auth User valido.

La directory amministrativa dei membri usa una proiezione minima e non espone automaticamente l’intero Profile personale.

---

# Business data condivisi

## 8. SELECT Workspace-scoped

La baseline per le normali business table è:

```text
private.is_workspace_member(workspace_id)
```

Si applica ai domini condivisi, compresi:

```text
Buildings
Properties
Contacts
Tenants
Leases
Payments
Documents
Communications
Signature
Lease Activity
relative child/join table
```

Owner e member possiedono la stessa visibilità business nel primo modello.

---

## 9. Direct business DML

Per le business table condivise:

```text
direct INSERT
direct UPDATE
direct DELETE
→ DENY
```

Le mutation passano sempre dal command boundary definito in S1.9.

Questo impedisce di aggirare:

```text
row_version
transaction boundary
overlap Lease
Payment invariants
history blocker
Activity append-only
last-owner rules
```

Anche una mutation internamente semplice, come un Contact single-row, resta una business operation controllata e non una table liberamente modificabile dal browser.

---

## 10. Property access items

`property_access_items` resta esclusa dai read-model Property generici.

Nel permission model iniziale è comunque leggibile da active owner/member attraverso una query esplicita dedicata.

Non viene introdotta una permission speciale solo per questa feature.

---

# Dati user-private

## 11. Private notes

`property_private_notes` e `tenant_private_notes` richiedono contemporaneamente:

```text
active Workspace membership
AND
user_id = auth.uid()
```

per SELECT e mutation.

Un owner non può leggere o modificare le Private Note di un altro member.

---

## 12. Drafts

`drafts` è:

```text
user-private
+
Workspace-scoped
```

SELECT/INSERT/UPDATE/DELETE richiedono:

```text
active Membership
AND
user_id = auth.uid()
```

Una Membership revocata rende immediatamente non accessibili le Draft di quel Workspace, anche se appartengono allo stesso Auth User.

`draft_files` eredita l’accesso dalla relativa Draft.

---

# File Objects e Documents

## 13. FileObject authorization

`file_objects` non usa una semplice policy:

```text
is_workspace_member(workspace_id)
```

perché un FileObject può essere ancora legato esclusivamente a una Draft privata.

L’helper:

```text
private.can_access_file_object(...)
```

consente accesso quando:

```text
active Workspace member
AND
(
  FileObject usato da un business Document
  OR
  FileObject usato da una Draft del Current User
)
```

Un FileObject Draft-only resta quindi invisibile agli altri Workspace member.

Quando viene promosso a business Document, la visibility cambia automaticamente attraverso le nuove relazioni senza duplicare il file.

Direct FileObject DML resta negato.

---

## 14. Documents

I business Document sono leggibili dagli active Workspace member.

`documents.is_shared` non modifica la RLS.

Il primo cutover non introduce ancora visibilità differenziata per:

```text
specific Tenant
selected Tenant
read-only collaborator
external user
```

La mutation Document passa dalle command.

---

# Lease Activity

## 15. Activity

`lease_activities` e `lease_activity_changes`:

```text
SELECT
→ active Workspace member

direct INSERT
direct UPDATE
direct DELETE
→ DENY
```

Le Activity vengono create esclusivamente dalle business command.

Il client non può forgiare:

```text
actor_user_id
event_type
occurred_at
before/after
```

---

# Command authorization

## 16. Function boundary

`SECURITY INVOKER` resta il default.

Le implementazioni che devono scrivere dati non direttamente modificabili dal client possono usare una function privata:

```text
SECURITY DEFINER
SET search_path = ''
```

dietro un wrapper/RPC controllato.

Il pattern raccomandato è:

```text
public/exposed command wrapper
→ authorization boundary
→ private privileged implementation
→ business tables
```

Non vengono usate genericamente exposed `SECURITY DEFINER` function prive di un authorization layer esplicito.

---

## 17. Authorization dentro le command

Ogni command privilegiata verifica sempre:

```text
auth.uid()
Workspace Membership
owner role quando necessario
Workspace reale della entity
business invariants
```

Per una entity esistente:

```text
entity_id
→ resolve row
→ derive workspace_id
→ authorize
```

Il client non può imporre il Workspace della entity.

Per una create root il Workspace ricevuto come intent viene verificato tramite Membership.

I `workspace_id` delle child vengono derivati server-side.

---

## 18. Function grants

Il privilegio `EXECUTE` sulle application function viene revocato di default e concesso soltanto agli entry point realmente necessari.

Le system function non sono invocabili da `authenticated`.

Esempi:

```text
ApplyDuePrepaidAllocations
Storage cleanup
orphan cleanup
future background jobs
```

restano system/server-only.

---

## 19. Service role

`service_role` bypassa RLS e resta esclusivamente server-side.

Non deve essere presente in:

```text
frontend
Vite bundle
browser storage
client configuration
```

Una normale richiesta utente server-side continua a richiedere authorization esplicita e non deve affidarsi indiscriminatamente al service role.

---

# Read-model e View

## 20. View

Le View esposte usate dai read-model devono preservare la RLS delle table sottostanti.

Quando applicabile vengono create come:

```text
security_invoker = true
```

Le normali query function restano `SECURITY INVOKER`.

Una query privilegiata è ammessa soltanto per casi espliciti, con projection minima e authorization interna, come una futura query amministrativa delle Membership.

---

# Storage

## 21. Bucket

Il primo cutover usa un bucket privato:

```text
workspace-files
```

Non esistono business bucket pubblici.

---

## 22. Storage path

Path canonico:

```text
<workspace_id>/<file_object_id>/blob
```

Il nome originale del file resta in:

```text
file_objects.original_name
```

Il path Storage non contiene inutilmente dati business o personali.

---

## 23. Upload

Un Auth User può caricare soltanto:

```text
bucket = workspace-files
+
path Workspace di cui è active member
```

Upload:

```text
INSERT
→ ALLOW quando Workspace autorizzato
```

Overwrite/update:

```text
DENY
```

perché il FileObject è immutabile e un replacement produce un nuovo FileObject/path.

---

## 24. Storage ownership

`storage.owner_id` non costituisce authorization authority.

Può essere utilizzato soltanto come supporto per l’accesso immediatamente successivo all’upload, sempre subordinato a Membership attiva.

Una Membership revocata non mantiene accesso ai file soltanto perché l’utente ne era uploader.

---

## 25. Storage SELECT

Dopo il commit business:

```text
business Document
→ active Workspace member

Draft-only file
→ Draft owner
```

La policy Storage deve riflettere la stessa authorization dei FileObject.

---

## 26. Storage DELETE

Direct Storage delete da `authenticated` è negato.

L’utente che ha originariamente caricato un file non può eliminarne fisicamente i byte aggirando Document/FileObject.

La cancellazione segue il workflow trusted definito in S1.9.

Lo schema Storage non viene manipolato direttamente tramite SQL business.

---

# Download e revoca

## 27. Download autenticato come default

Le signed URL non sono il meccanismo standard del primo cutover.

Il default è accesso al private bucket tramite sessione autenticata, così ogni nuova richiesta Storage attraversa nuovamente il controllo autorizzativo.

Questo mantiene il contratto:

```text
Membership revocata
→ successiva richiesta file DENY
```

---

## 28. Signed URL

Eventuali future signed URL vengono trattate come capability temporanee.

Devono avere:

```text
TTL corto
scope esplicito
revoca non immediata dichiarata
```

e non diventano mai persistence authority.

---

# Matrice autorizzativa consolidata

| Area                  | Lettura                        | Mutation             |
| --------------------- | ------------------------------ | -------------------- |
| Profile               | self                           | self limitata        |
| Workspace             | active member                  | command              |
| Workspace Profile     | active member                  | owner command        |
| Membership            | self / owner admin             | owner command        |
| Business data         | active member                  | member/owner command |
| Property Access Items | active member, query dedicata  | command              |
| Private Notes         | self + member                  | self + member        |
| Drafts                | self + member                  | self + member        |
| FileObject            | Document member o Draft owner  | trusted workflow     |
| Documents             | active member                  | command              |
| Communications        | active member                  | command              |
| Lease Activity        | active member                  | command only         |
| Storage upload        | active member nel proprio path | INSERT only          |
| Storage download      | authorization corrente         | —                    |
| Storage delete        | —                              | trusted server       |
| System command        | —                              | server/system        |

# Test RLS obbligatori

## 34. Personas minime

S2.6 deve verificare almeno:

```text
anon
user senza Workspace
owner Workspace A
member Workspace A
owner Workspace B
user member A+B
revoked member A
```

---

## 35. Cross-workspace

Per ogni dominio pilot:

```text
owner/member A
→ legge A
→ non legge B

member A
→ command A ALLOW
→ command B DENY

revoked member A
→ accesso A DENY
```

---

## 36. Private data

Due utenti dello stesso Workspace:

```text
Draft A
→ User A ALLOW
→ User B DENY

Private Note A
→ User A ALLOW
→ User B DENY
→ owner B DENY
```

---

## 37. Direct bypass

Un active member che prova direttamente:

```text
UPDATE leases
INSERT payments
DELETE documents
INSERT lease_activities
```

deve ricevere DENY.

La stessa business operation attraverso la command autorizzata può riuscire.

---

## 38. Revocation

Test obbligatorio:

```text
User A ha Membership attiva
→ query ALLOW

Owner revoca Membership

User A mantiene stessa sessione/JWT
→ nuova query DENY
```

Questo dimostra che l’autorità è live nel database.

---

## 39. Negative metadata tests

Devono essere verificati:

```text
anon
+ Property.is_public = true
→ DENY

anon
+ Document.is_shared = true
→ DENY
```

---

## 40. Storage tests

Almeno:

```text
member A upload path A
→ ALLOW

member A upload path B
→ DENY

member Workspace download business Document
→ ALLOW

altro member download Draft-only file
→ DENY

revoked member download
→ DENY

authenticated direct Storage delete
→ DENY
```

---

## 41. View e RPC tests

Ogni View esposta deve essere verificata contro utenti autorizzati e cross-workspace.

Ogni RPC deve avere test di spoofing almeno per:

```text
workspace_id
entity_id
user_id
actor_user_id
```

Un client non deve poter ottenere accesso cambiando semplicemente gli ID del payload.

---

# Vincoli consolidati

S1.11 stabilisce quindi che:

* Membership attiva è la security authority Workspace;
* owner e member condividono inizialmente i permessi business;
* owner aggiunge amministrazione Workspace/Membership;
* l’Active Workspace frontend non è authorization state;
* RLS protegge ogni table applicativa esposta;
* `anon` non accede a dati Props24;
* `is_public`, `is_shared` e Invitation non concedono accesso;
* Profile, Draft e Private Note conservano il proprio user scope;
* un owner non può leggere dati user-private altrui;
* il browser non modifica direttamente le business table condivise;
* tutte le mutation business attraversano command autorizzate;
* helper RLS privilegiati vivono nello schema `private`;
* View e Function non devono bypassare accidentalmente RLS;
* service role resta esclusivamente server-side;
* business Storage è privato e Workspace-scoped;
* `storage.owner_id` non è authority;
* signed URL non è il download standard del primo cutover;
* la revoca Membership deve bloccare DB e nuove richieste file senza richiedere JWT refresh;
* test RLS, cross-workspace, spoofing e Storage sono parte obbligatoria del gate Supabase.
