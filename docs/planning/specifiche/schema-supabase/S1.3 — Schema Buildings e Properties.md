## S1.3 — Schema Buildings e Properties

### Scopo

S1.3 definisce il modello target PostgreSQL/Supabase per:

* Buildings;
* Properties / Unit;
* relazione Building–Property;
* identità catastale Property;
* child data direttamente owned da Building e Property;
* lifecycle archive/delete;
* dati derivati da non trasformare in authority;
* confine Property ↔ Documents/File.

S1.3 non replica `BuildingRecord`, `PropertyRecord` o `PropertyFormData` come shape fisiche PostgreSQL.

Il target normalizza le authority reali e applica i principi già approvati in S1.1 e S1.2.

---

## Vincoli ereditati da S0/S1.1/S1.2

Restano vincolanti:

* business rows workspace-scoped;
* UUID opachi per entity con identity propria;
* `archived_at` per lifecycle active/archived;
* `row_version` sulle aggregate root condivise;
* niente derived data persistiti come seconda authority;
* niente JSONB per core domain strutturati;
* FK reali al posto di array di ID;
* nessun cascade distruttivo su storico business;
* mutation multi-record atomiche;
* query/read-model separati dalle entity authority;
* RLS come authorization boundary;
* `workspace_id` come scope business;
* file binari fuori PostgreSQL;
* nessun matching euristico fra domini differenti.

S0 ha inoltre stabilito che:

```text
Building.unitsCount
Property.relations.tenantIds[]
Property.relations.leaseIds[]
Property effective status
Property financial summary
```

sono projection/read-model e non authority da migrare.

---

# Modello Buildings / Properties approvato

## 1. Building e Property restano entity autonome

Il modello canonico è:

```text
Workspace
├── Building
└── Property
```

Relazione:

```text
1 Building
→ 0..N Property

1 Property
→ 0..1 Building
```

L’unica authority Building–Property vive su:

```text
properties.building_id
```

nullable.

Non vengono introdotti:

```text
buildings.property_ids[]
buildings.unit_ids[]
```

Una Property può essere:

* standalone;
* collegata a un Building;
* riassegnata;
* scollegata.

---

Gli optional semanticamente assenti devono convergere verso `NULL` invece di mantenere indiscriminatamente stringhe vuote.

---

## 3. Lifecycle Building

Semantica:

```text
archived_at IS NULL
→ active

archived_at IS NOT NULL
→ archived
```

Archiviare un Building:

* non elimina Property;
* non scollega Property;
* non modifica relazioni esistenti.

Un Building archiviato:

* può continuare a essere referenziato dalle Property già collegate;
* non può ricevere una nuova Property;
* non può essere nuova destinazione di reassignment.

---

## 4. Delete Building

Regola:

```text
Building con almeno una Property
→ DELETE BLOCK

Building senza Property
→ DELETE consentito
```

Anche una Property archiviata blocca il delete.

Non esiste:

```text
DELETE Building
→ CASCADE Property
```

---

## 5. `Building.unitsCount` è derived

`Building.unitsCount` non viene persistito come authority.

Authority:

```text
properties.building_id
```

Derivazione:

```text
COUNT(Property WHERE building_id = Building.id)
```

Le Property archiviate restano collegate e partecipano al conteggio.

Il valore appartiene a query/read-model S1.10.

---

## 6. Unicità Building

### Identificativo

L’identificativo Building è unique nel Workspace, includendo i Building archiviati.

Normalizzazione semantica da preservare:

```text
NFKC
trim
whitespace normalizzato
case-insensitive
```

Scope:

```text
workspace_id
+
normalized(identifier)
```

### Location

Esiste inoltre uniqueness sulla location:

```text
address
city
postal_code
country
```

Non partecipano:

```text
address2
county
state
```

Anche questa uniqueness è Workspace-scoped e include gli archiviati.

L’enforcement PostgreSQL concreto appartiene a S1.8.

---

## 7. Building Features

Le feature Building non vengono conservate come JSONB.

Target concettuale:

```text
public.building_features

workspace_id
building_id
feature_code
```

Identity logica:

```text
(building_id, feature_code)
```

Il catalogo resta una risorsa statica applicativa.

La persistence utilizza codici stabili e non label localizzate come identity.

---

## 8. Building internal note

L’attuale `Building.privateNote` viene interpretata come nota interna del Workspace.

Target semantico:

```text
buildings.internal_note
```

Non è una nota personale del singolo Auth User.

---

## 9. Property non utilizza `form_data JSONB`

Il target non replica:

```text
PropertyRecord.formData
```

```text

```

I dati core Property vengono normalizzati in colonne reali e child relation.

`PropertyFormData` resta un contratto form/UI e non diventa schema PostgreSQL.

## 11. Indirizzo Property indipendente dal Building

`properties.building_id` non rende l’indirizzo Property derivato dal Building.

Il Building può essere usato per precompilare il form, ma dopo la creazione:

```text
Building.address
≠
Property.address authority
```

Modificare il Building non deve propagare automaticamente l’indirizzo alle Property collegate.

---

## 12. Titolo e location Property non sono identity

Sono consentite più Property con:

```text
stesso titolo
stesso indirizzo
stesso Building
```

quando non collidono sulla vera identity catastale.

Non devono essere introdotti:

```text
UNIQUE(title)
UNIQUE(address)
UNIQUE(title, address)
```

---

## 13. Identità catastale Property

La duplicate identity Property verificata dal dominio è composta da:

```text
country
cadastre_municipality_code
cadastre_registry_type
cadastre_municipality
urban_section
cadastre_sheet
cadastre_part
cadastre_sub
```

La chiave è considerata completa soltanto se sono presenti almeno:

```text
country
cadastre_municipality_code
cadastre_registry_type
cadastre_sheet
cadastre_part
```

Se manca uno di questi valori:

```text
cadastral identity
→ assente

duplicate enforcement
→ non applicato
```

Gli altri campi partecipano alla identity quando valorizzati.

---

## 14. Unicità catastale Workspace-scoped

Semantica:

```text
stessa cadastral identity completa
+
stesso workspace
→ BLOCK

stessa cadastral identity completa
+
workspace differente
→ consentito
```

Le Property archiviate continuano a partecipare all’unicità.

La normalizzazione corrente dei valori catastali deve essere preservata.

La tecnica concreta tramite expression index, generated column o partial unique index appartiene a S1.8.

Un’eventuale `cadastral_key` tecnica resta derived e non business authority.

---

## 15. Lifecycle Property

Target:

```text
archived_at IS NULL
→ active

archived_at IS NOT NULL
→ archived
```

Archiviare una Property:

* non scollega il Building;
* non elimina child;
* non elimina Lease;
* non elimina Payment;
* non elimina storico.

Una Property archiviata resta parte del Building.

---

## 16. Delete Property

Regola consolidata:

```text
Property referenziata da qualunque Lease
→ DELETE BLOCK

Property referenziata da qualunque Payment
→ DELETE BLOCK
```

La regola vale anche per storico terminato o archiviato.

Non esiste:

```text
DELETE Property
→ CASCADE Lease
→ CASCADE Payment
```

Quando esiste storico business deve essere utilizzato l’archive.

---

## 17. Rental status

L’attuale valore speciale:

```text
PropertyStatusManual = '0'
```

non viene trasferito letteralmente.

Target:

```text
rental_status_override = NULL
→ Automatico
```

Un valore non-null rappresenta override manuale.

L’effective status resta derived da:

```text
Property override
+
Lease state
```

e appartiene a S1.10.

---


## 22. Property Private Note

La nota attualmente presentata come:

```text

Solo tu puoi leggere questa nota
```

non può essere una normale colonna workspace-shared.

Target:

```text
public.property_private_notes

workspace_id
property_id
user_id
note
created_at
updated_at
```

Identity logica:

```text
(property_id, user_id)
```

Ogni User può avere la propria nota personale sulla stessa Property.

La policy concreta user-specific appartiene a S1.11.

---

## 23. Property Access Items

Gli attuali `PropertyKeys[]` diventano child entity:

```text

workspace_id
property_id
position

description
code_or_number
quantity

created_at
updated_at
```

Gli ID già persistiti devono essere preservati nel cutover.

`holder` resta metadata.

Non viene trasformato in FK verso User, Tenant, Contact o Party senza una relation authority esplicita.

Questi dati sono sensibili e dovranno essere considerati specificamente dalle policy S1.11.

---

## 24. Property Contacts

Gli attuali `PropertyContacts[]` non sono la Rubrica `Contact`.

Target:

```text
public.property_contacts

id
workspace_id
property_id
position

first_name
last_name
profession
email
phone
comments

created_at
updated_at
```

Sono snapshot/child specifiche della Property.

Non viene introdotto inizialmente:

```text
contact_id
```

e non viene effettuato matching automatico per nome, email o altri campi.

Una futura convergenza con Contacts dovrà essere esplicita.

---

## 25. Property Activities

`Property.activities[]` non possiede una authority runtime sufficientemente consolidata.

Non viene quindi creata:

```text
property_activities
```

soltanto per replicare il record locale.

Una futura activity/audit authority dovrà essere progettata esplicitamente.

---

## 26. Relazioni Lease/Tenant derivate

Le attuali:

```text
Property.relations.leaseIds[]
Property.relations.tenantIds[]
```

sono projection.

Non vengono persistite in `properties`.

Le future authority saranno definite dal dominio Lease:

```text
Lease → Property
Lease → participants
```

---

## 27. Financial asset data

Restano Property authority:

```text
acquisition_date
purchase_price
acquisition_costs
agency_costs
current_value
sale_price
```

Descrivono il bene e non sostituiscono Payment.

Gli importi utilizzeranno tipi PostgreSQL monetariamente sicuri secondo S1.1.

---

## 28. Property fiscal code

Il codice fiscale Property viene preservato come business metadata.

Non esiste evidenza sufficiente per considerarlo:

```text
unique identity
```

Quindi non viene introdotta uniqueness per inerzia.

---

## 29. Publication metadata

I flag:

```text
is_public
is_address_public
is_phone_public
```

restano metadata di presentazione.

Non costituiscono authorization.

In particolare:

```text
is_public = true
```

non significa automaticamente:

```text
anonymous database access
```

L’eventuale pubblicazione esterna richiederà policy dedicate.

---

## 30. Documents, Photos e File

S1.3 stabilisce la necessità di rappresentare:

```text
Property
→ cadastral attachment

Property
→ photos

Property
→ contracts/certificates

Property
→ documents
```

Gli ID persistenti già esistenti devono essere preservati.

Il modello fisico comune di:

```text
file metadata
document metadata
ownership
provenance
Storage object
document links
```

appartiene a S1.6.

I file binari non vengono persistiti in PostgreSQL.

Target:

```text
PostgreSQL
→ metadata e relazioni

Supabase Storage
→ contenuto binario
```

`StoredLocalFile.dataUrl` non viene migrato.

---

## 31. Ordine delle child collection

Le child collection il cui ordine è semanticamente osservabile possono mantenere:

```text
position
```

Esempi:

```text
property_access_items
property_contacts
future document/photo relations
```

Le pure value relation come `property_equipment` non richiedono ordine persistente.

---

## 32. Coordinates e legacy data

Non vengono migrati per inerzia:

```text
Property.coordinates
Property.legacy
```

Non viene introdotto:

```text
legacy jsonb
```

né geospatial data senza una vera geocoding authority.

Un futuro sistema geografico dovrà definirne esplicitamente source e lifecycle.

---

## 33. Read-model derivati

Non diventano colonne Property:

```text
current tenant
effective status
lease ids
tenant ids
gross income
expenses
net result
occupancy
profitability
financial chart
generated URLs
```

Non diventa colonna Building:

```text
units_count
```

Questi valori appartengono a query/read-model S1.10.

---

## 34. Optimistic concurrency

Building e Property utilizzano:

```text
row_version bigint
```

come base per optimistic concurrency.

Semantica:

```text
read version N
→ altro writer produce N+1
→ update basato su N
→ conflict
```

Non è accettato last-write-wins silenzioso sulle aggregate root condivise.

La command concreta appartiene a S1.9/S3.

---

## 35. Bulk operation

Le operazioni:

```text
archiveMany
restoreMany
deleteMany
```

devono mantenere semantica all-or-nothing.

Non devono diventare una sequenza di mutation indipendenti che possa produrre partial persistence.

Le transaction concrete appartengono a S1.9.

---

## 36. Workspace consistency

Le relazioni devono impedire riferimenti cross-workspace.

Esempi:

```text
Property.workspace_id
=
Building.workspace_id

PropertyNote.workspace_id
=
Property.workspace_id

PropertyAccessItem.workspace_id
=
Property.workspace_id
```

RLS non sostituisce questa integrità referenziale.

La forma concreta delle FK workspace-consistent appartiene a S1.8.
