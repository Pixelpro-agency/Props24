## S1.8 — Matrice constraint e index

### Scopo

S1.8 traduce il modello approvato in S1.2–S1.7 nei constraint e negli indici strutturali del database PostgreSQL.

La regola generale è:

```text
constraint row-local / referenziale
→ PostgreSQL

invariant cross-row / cross-table dinamico
→ transaction command S1.9

authorization
→ RLS S1.11
```

Non vengono introdotti constraint artificiali che richiedano duplicazione delle authority o denormalizzazione preventiva.

---

## Vincoli ereditati da S1.1–S1.7

Restano vincolanti:

* UUID come identity standard;
* `timestamptz` per istanti e `date` per date civili;
* `numeric` per importi e percentuali;
* `archived_at` come lifecycle archive;
* `row_version` sulle root condivise;
* `NULL` per valori semanticamente assenti;
* `text + CHECK` per vocabolari finiti;
* FK reali per le relazioni canoniche;
* `RESTRICT / NO ACTION` come delete policy business predefinita;
* `CASCADE` soltanto per child realmente owned;
* workspace consistency protetta dal database;
* derived data esclusi dalla persistence authority;
* nessun indice duplicato di PK/UNIQUE;
* indici specifici per search/read-model rinviati a S1.10 quando non già giustificati dal runtime.

---

# Convenzioni SQL consolidate

## 1. Tipi comuni

Baseline:

```text
id
→ uuid

money
→ numeric(14,2)

percentage / rate
→ numeric(7,4)

row_version
→ bigint not null default 1
→ CHECK row_version >= 1

position
→ integer
→ CHECK position >= 0

file size
→ bigint

snapshot / payload eterogeneo motivato
→ jsonb
```

Le stringhe realmente obbligatorie usano:

```text
NOT NULL
+
CHECK (btrim(value) <> '')
```

---

## 2. Workspace consistency

Le business root Workspace-scoped utilizzate da child/link espongono, quando necessario:

```text
UNIQUE (workspace_id, id)
```

Le relazioni usano il pattern:

```text
child(workspace_id, parent_id)
→ parent(workspace_id, id)
```

così una relazione cross-workspace è impossibile anche senza RLS.

---

# Auth, Workspace e Membership

## 3. Profile e Workspace

`profiles`:

```text
PRIMARY KEY (user_id)
FK user_id → auth.users
ON DELETE CASCADE
```

`profiles.fiscal_code`, quando valorizzato, viene salvato in forma canonica NFKC / senza whitespace / uppercase ed è globalmente unique.

`workspaces` usa UUID, `row_version` e `name` obbligatorio non blank.

`workspace_profiles`:

```text
PRIMARY KEY (workspace_id)
FK → workspaces
ON DELETE CASCADE
```

con `display_name` obbligatorio.

---

## 4. Membership

`workspace_memberships`:

```text
PRIMARY KEY (id)
UNIQUE (workspace_id, user_id)

role
→ owner | member
```

FK verso Workspace e Auth User.

Sono previsti indici dedicati per:

```text
membership attive di un User
owner attivi di un Workspace
```

Il requisito:

```text
Workspace operativo
→ almeno un owner attivo
```

resta invariant transazionale S1.9.

---

# Buildings e Properties

## 5. Building

`buildings` usa:

```text
PRIMARY KEY (id)
UNIQUE (workspace_id, id)
```

L'identificatore Building è unique nel Workspace tramite expression index normalizzato.

Anche la location:

```text
address
city
postal_code
country
```

costituisce identity Workspace-scoped normalizzata.

Gli archived continuano a partecipare alle uniqueness.

`building_features` è una pure relation con composite primary key.

---

## 6. Property

`properties`:

```text
PRIMARY KEY (id)
UNIQUE (workspace_id, id)

building_id nullable
FK Workspace-safe → buildings
ON DELETE RESTRICT
```

La Property resta quindi blocker della delete Building anche quando archived.

La cadastral identity usa la key approvata:

```text
country
cadastre_municipality_code
cadastre_registry_type
cadastre_municipality
urban_section
cadastre_sheet
cadastre_part
cadastre_sub
```

con partial unique expression index Workspace-scoped.

Le componenti catastali opzionali usano semantica `NULLS NOT DISTINCT`.

Non viene introdotta una seconda authority `cadastral_key`.

---

## 7. Property child

Le child realmente owned dalla Property possono usare:

```text
ON DELETE CASCADE
```

Comprendono le relative righe strutturate approvate in S1.3.

Le business relation esterne non usano cascade.

`property_private_notes` ha identity:

```text
(property_id, user_id)
```

con FK verso Property e Auth User.

---

# Contacts e Tenants

## 8. Contact

`contacts`:

```text
PRIMARY KEY (id)
UNIQUE (workspace_id, id)

type
→ person | company
```

Required:

```text
person
→ first_name + last_name

company
→ company_name
```

La fiscal identity usa partial unique index separati per:

```text
person fiscal_code

company fiscal_code

company vat_number
```

sempre Workspace-scoped, type-aware e comprensivi degli archived.

---

## 9. Tenant

`tenants` usa la stessa struttura person/company.

Fiscal uniqueness:

```text
person
→ fiscal_code

company
→ company_fiscal_code
→ vat_number
```

Il fiscal code del rappresentante legale non diventa identity della società.

Non esiste uniqueness fiscale Contact↔Tenant.

---

## 10. Tenant–Contact relations

`tenant_guarantors` e `tenant_emergency_contacts` conservano il proprio UUID persistente e FK Workspace-safe verso Tenant e Contact.

La delete Tenant può eliminare queste child.

La delete Contact resta `RESTRICT`.

`position` è unique nel relativo Tenant.

Per Emergency:

```text
UNIQUE tenant_id
WHERE is_primary = true
```

garantisce al massimo un primary.

Restano S1.9:

```text
massimo 5 Emergency
se presenti → esattamente un primary
Contact active alla nuova relazione
telefono obbligatorio alla nuova Emergency relation
```

# Lease e Payments

## 11. Lease

`leases`:

```text
PRIMARY KEY (id)
UNIQUE (workspace_id, id)

property_id
FK Workspace-safe → properties
ON DELETE RESTRICT
```

Constraint principali:

```text
start_date <= end_date

contract_status
→ active | inactive | terminated

billing_period
→ monthly | quarterly | semiannual | annual

payment_timing
→ anticipato | arretrato

payment_day
receipt_period_day
→ 1..31

VAT
→ 0..100
```

Sono inoltre controllati i cataloghi approvati per deposito, spese, balance carry e rent update.

---

## 12. Lease participants

`lease_tenants`:

```text
PRIMARY KEY (lease_id, tenant_id)
UNIQUE (lease_id, position)
```

`lease_guarantors`:

```text
PRIMARY KEY (lease_id, contact_id)
UNIQUE (lease_id, position)
```

Entrambe usano FK Workspace-safe.

L'overlap Tenant fra Lease resta invariant transazionale S1.9.

Non viene introdotta denormalizzazione di date/Property nelle join e non viene richiesto `btree_gist`.

---

## 13. Lease Payment Items e Insurance

`lease_payment_items` conserva UUID autonomo, `position` unique per Lease e CHECK su:

```text
type
amount
vat_percent
```

`lease_insurance_contracts` usa identity:

```text
(lease_id, type)
```

con tipi iniziali:

```text
locativa
affitti_non_pagati
```

e document link verificabile rispetto alla stessa Lease.

---

## 14. Payment

`payments`:

```text
PRIMARY KEY (id)
UNIQUE (workspace_id, id)
```

Property è obbligatoria.

Lease e Tenant attribution restano nullable.

Se la Lease è presente, il database garantisce:

```text
Payment.workspace_id = Lease.workspace_id

Payment.property_id = Lease.property_id
```

Se anche `tenant_id` è presente:

```text
Payment Tenant
→ deve appartenere a lease_tenants
```

---

## 15. Payment semantics

Sono validati tramite CHECK:

```text
type
→ income | expense

source
→ generated | manual | deposit | deposit_return

accounting_role
→ revenue | expense | deposit
```

e le combinazioni approvate fra source, type e accounting role.

`category` resta text estensibile.

Non esiste una colonna persistita `status`.

---

## 16. Generated schedule

Le rate generated hanno uniqueness:

```text
UNIQUE (
  lease_id,
  category,
  due_date
)
WHERE source = 'generated'
```

Gli indici baseline Payment supportano lookup per:

```text
Lease + due_date
Property + due_date
Tenant + due_date
```

---

## 17. Confirmation e Prepaid

`payment_confirmations`:

```text
PRIMARY KEY (payment_id)
FK → payments
ON DELETE CASCADE
```

Il metodo appartiene al catalogo approvato.

Restano S1.9:

```text
confirmation.amount = payment.amount
paid_date non futura
```

`lease_prepaid_allocations` usa identity:

```text
(lease_id, payment_id)
```

con FK che garantisce che il Payment appartenga alla stessa Lease.

L'eleggibilità economica del Payment resta invariant S1.9.

---

# Documents e Files

## 18. File Object

`file_objects`:

```text
PRIMARY KEY (id)
UNIQUE (workspace_id, id)
UNIQUE (storage_bucket, storage_path)

CHECK size_bytes >= 0
```

Nessuna FK verso `storage.objects`.

---

## 19. Document

`documents`:

```text
PRIMARY KEY (id)
UNIQUE (workspace_id, id)
```

FK Workspace-safe verso File Object e Source Document.

Constraint:

```text
source_document_id IS NULL
OR source_document_id <> id

origin
→ uploaded | linked | generated | metadata
```

La delete del Source Document è `RESTRICT` finché esistono linked Document che ne conservano la provenance.

---

## 20. Document Link

`document_links` usa:

```text
PRIMARY KEY (document_id)
```

e richiede esattamente uno fra:

```text
property_id
tenant_id
lease_id
```

Le FK sono Workspace-safe.

`role` viene validato rispetto al tipo di owner:

```text
Property
→ photo | cadastral_attachment | contract | document

Tenant
→ photo | identity_front | identity_back | company_registry | document

Lease
→ document | contract_snapshot | signature
```

Le owner FK usano `RESTRICT`.

Il cleanup Document/File resta quindi esplicito e non viene affidato a cascade distruttivi.

---

# Signature

## 21. Signature Process

`lease_signature_processes`:

```text
PRIMARY KEY (lease_id)
```

con FK verso Lease `RESTRICT`.

Il contract snapshot deve appartenere alla stessa Lease.

`completed_at`, quando presente, non può precedere `started_at`.

---

## 22. Signature Signers

Identity:

```text
(lease_id, signer_key)
```

e:

```text
UNIQUE (lease_id, position)
```

Role:

```text
landlord
tenant
guarantor
```

Il database garantisce la coerenza della relativa identity:

```text
landlord
→ nessun Tenant/Contact

tenant
→ Tenant appartenente alla Lease

guarantor
→ Contact appartenente ai guarantor della Lease
```

`signed_at` e `signature_document_id` devono essere entrambi presenti o entrambi assenti.

---

# Drafts

## 23. Draft

`drafts`:

```text
PRIMARY KEY (id)
```

FK verso Workspace e Auth User con cascade, essendo dati temporanei owned.

Cataloghi:

```text
form_type
→ building | property | tenant | lease

mode
→ create | edit
```

Regola:

```text
create
→ entity_id NULL

edit
→ entity_id NOT NULL
```

`payload` deve essere un JSON object e `schema_version > 0`.

---

## 24. Draft uniqueness

La logical identity usa:

```text
UNIQUE NULLS NOT DISTINCT (
  user_id,
  workspace_id,
  form_type,
  mode,
  entity_id
)
```

così viene garantita una sola Draft per lo stesso form/context sia in create sia in edit.

`draft_files` usa la composite identity:

```text
(draft_id, file_object_id)
```

con FK verso Draft e File Object.

---

# Communications

## 25. Communication

`communications` mantiene nel primo modello:

```text
channel = email
status = prepared
```

ed è append-oriented.

`communication_targets` usa:

```text
PRIMARY KEY (
  communication_id,
  lease_id,
  tenant_id
)
```

con FK Workspace-safe verso Communication, Lease e Tenant.

---

## 26. Communication come storico

Le FK Target→Lease/Tenant usano:

```text
ON DELETE RESTRICT
```

Di conseguenza:

```text
Lease/Tenant con Communication storica
→ hard delete bloccato
```

La normale risposta lifecycle diventa archive.

Questo preserva lo storico di comunicazione invece di cancellarlo implicitamente per rendere possibile un hard delete.

# Lease Activity

## 27. Lease Activity

`lease_activities`:

```text
PRIMARY KEY (id)
UNIQUE (workspace_id, id)
```

FK:

```text
Lease
→ ON DELETE CASCADE

actor_user_id
→ auth.users
→ ON DELETE SET NULL
```

`actor_type`:

```text
user | system
```

Per gli eventi user resta obbligatorio `actor_name_snapshot`.

Gli eventi system non possiedono `actor_user_id`.

---

## 28. Event, related entity e reason

`event_type` usa il catalogo approvato in S1.7.

`related_entity_type`:

```text
payment
document
communication
signature_process
```

`related_entity_type` e `related_entity_id` devono essere entrambi presenti o entrambi assenti.

Reason override:

```text
death
authority_order
eviction
other
```

`other` richiede `reason_details`.

`lease_end_date_overridden` richiede una motivazione.

---

## 29. Lease Activity Changes

`lease_activity_changes`:

```text
PRIMARY KEY (
  activity_id,
  field_key
)
```

FK Workspace-safe verso Activity con:

```text
ON DELETE CASCADE
```

`field_key` è obbligatorio e non blank.

`previous_value` e `next_value` restano `jsonb`.

Indice timeline:

```text
workspace_id
lease_id
occurred_at DESC
id DESC
```

e indice dedicato per related-entity correlation.

# Invariant assegnati a S1.9

Non vengono implementati tramite CHECK impropri:

```text
almeno un owner attivo per Workspace

Emergency Contact max 5
Emergency exactly-one primary quando presenti

active Contact per nuova relation
telefono Emergency alla nuova relation

Lease almeno un Tenant
massimo Tenant dipendente da lease_type
Tenant Lease overlap

Payment confirmation amount/date

prepaid eligibility

Document Library ↔ DocumentLink consistency

Signature semantic role validation non esprimibile localmente

row_version compare-and-increment
```

Questi invariant richiedono transaction, lock o lettura coordinata di più row.

---

# Strategia index

S1.8 introduce soltanto:

```text
PK / UNIQUE indexes
FK indexes necessari
reverse lookup dimostrati
partial/expression uniqueness
timeline index
```

Non viene ancora costruita una matrice esaustiva di:

```text
search
sorting UI
dashboard
analytics
filter avanzati
```

perché i relativi query contract vengono definiti in S1.10.
