# S1.2 — Auth identity, Profile, Workspace e Membership

## Stato

**APPROVATA — decisioni architetturali consolidate**

S1.2 definisce il modello target per identità autenticata, profilo personale, workspace, membership e identità rappresentata dal workspace nel passaggio dal prototipo locale a Supabase.

Le decisioni contenute in questo documento sono da considerare **contratti architetturali acquisiti** del progetto. Non devono essere riaperte durante l'implementazione salvo conflitti concreti emersi da codice, vincoli tecnici reali o decisioni successive esplicitamente approvate.

---

# 1. Obiettivo

Il prototipo locale lega concetti che nel target devono essere indipendenti:

```txt
utente
=
profilo
=
scope dei dati
=
database
```

Il target separa invece:

```txt
Auth identity
≠
Personal Profile
≠
Workspace
≠
Workspace Membership
≠
business / landlord identity
```

Il modello deve permettere contemporaneamente:

- autenticazione tramite Supabase Auth;
- profilo personale dell'utente separato dalle credenziali;
- isolamento dei dati tramite Workspace;
- collaborazione reale fra più utenti sullo stesso Workspace;
- un utente appartenente a zero, uno o più Workspace;
- più owner dello stesso Workspace;
- revoca immediata dell'accesso tramite RLS;
- futuro accesso Tenant senza trasformare il Tenant in membro del Workspace gestionale;
- futura gestione multi-ruolo senza accoppiare Auth User e business domain;
- identità stabile del soggetto rappresentato nei documenti indipendentemente dall'utente attualmente autenticato.

---

# 2. Modello concettuale target

```txt
Supabase Auth User
        │
        ▼
     Profile
        │
        │ 0..N
        ▼
Workspace Membership
        │
        ▼
     Workspace
        │
        ├── Workspace Profile
        │
        └── business data
             ├── Buildings
             ├── Properties
             ├── Contacts
             ├── Tenants
             ├── Leases
             ├── Payments
             ├── Documents
             └── ...
```

Il futuro accesso Tenant segue una relazione differente:

```txt
Auth User
   │
   └── future Party / Tenant link
           │
           └── accesso alle proprie Lease / risorse consentite
```

Un Tenant invitato **non diventa membro del Workspace gestionale del proprietario**.

---

# 3. Auth authority

## 3.1 `auth.users` è l'unica identity autenticata canonica

Supabase Auth è l'authority per:

```txt
user id
email / login identity
password / hash
sessioni
JWT
provider identities
email verification state
```

Il progetto non introduce una tabella applicativa che duplichi integralmente l'utente Auth.

Non esiste quindi come target:

```txt
public.accounts
```

intesa come seconda authority dell'identità autenticata.

Il vecchio identificatore locale:

```txt
LocalAccount.id = user-001
```

viene sostituito dall'identità canonica:

```txt
auth.users.id = UUID
```

---

# 4. Personal Profile

## 4.1 Tabella `public.profiles`

Il profilo personale applicativo è separato da Auth.

Modello concettuale:

```txt
public.profiles

user_id
first_name
last_name
fiscal_code
created_at
updated_at
```

Vincolo identitario:

```txt
profiles.user_id
PRIMARY KEY
FK → auth.users(id)
```

Non viene introdotto un secondo `profiles.id`.

Il Profile è una relazione 1:1 con Auth User.

---

## 4.2 Ownership e lifecycle del Profile

Il Profile non ha vita autonoma senza Auth User.

Target:

```txt
profiles.user_id
→ auth.users.id
ON DELETE CASCADE
```

Questo cascade è ammesso perché il Profile è realmente owned dall'Auth User.

---

## 4.3 Email non duplicata nel Profile

`profiles.email` **non viene introdotto come seconda authority**.

L'email resta proprietà di Supabase Auth.

Il read-model UI compone i dati necessari:

```txt
Auth user.email
+
Profile.first_name
+
Profile.last_name
+
Profile.fiscal_code
```

La UI non deve usare una tabella applicativa come authority alternativa dell'email di login.

---

## 4.4 Creazione automatica del Profile

Ogni Auth User Props24 deve avere un Profile.

Flusso target:

```txt
auth.users INSERT
        ↓
DB trigger
        ↓
public.profiles INSERT
```

Il trigger può usare `raw_user_meta_data` soltanto per il bootstrap iniziale di campi non autorizzativi, per esempio:

```txt
first_name
last_name
```

Dopo il bootstrap:

```txt
public.profiles
→ authority applicativa del profilo
```

`raw_user_meta_data` non diventa business authority.

Il trigger di creazione Profile deve essere testato perché un errore in questa fase non deve compromettere il signup.

---

# 5. Metadata Auth

## 5.1 `user_metadata` non è authorization authority

`raw_user_meta_data` può essere usato per bootstrap o convenience.

Non deve contenere o determinare in modo canonico:

```txt
workspace memberships
permission
workspace role
business authority
fiscal authority
```

Hard rule:

```txt
raw_user_meta_data
→ bootstrap / convenience
→ NON authorization
→ NON business authority
```

---

## 5.2 Membership non canoniche nel JWT

La lista canonica dei Workspace accessibili non viene memorizzata nel JWT come authorization authority.

Anche se informazioni autorizzative potrebbero tecnicamente essere inserite in metadata più protetti, il token può restare stale fino al refresh.

Il target richiede invece che:

```txt
owner revoca member
→ successiva query DB
→ accesso negato
```

senza aspettare il refresh del JWT.

Quindi:

```txt
workspace_memberships
→ authorization authority
```

mentre:

```txt
JWT
→ Auth identity
→ NON lista canonica dei Workspace
```

---

# 6. Codice fiscale Account

Il codice fiscale dell'account appartiene al Personal Profile.

Target:

```txt
profiles.fiscal_code
→ nullable
→ normalized
→ globalmente unique quando valorizzato
```

Non è workspace-scoped.

Rappresenta l'identità personale dell'account Props24.

Il constraint SQL concreto e la strategia di normalizzazione appartengono alla task dedicata ai constraint/schema definitivi.

---

## 6.1 Registrazione

Il codice fiscale **non è obbligatorio alla registrazione**.

Target primo cutover:

```txt
registrazione
→ nome
→ cognome
→ email
→ password

fiscal_code
→ opzionale
→ compilabile successivamente
```

Il vecchio requisito locale che rendeva il CF obbligatorio viene rimosso.

---

## 6.2 Login

Il primo cutover Supabase usa:

```txt
email + password
```

Il login:

```txt
codice fiscale + password
```

non fa parte del primo cutover.

Il CF rimane Profile identity e **non diventa Auth credential**.

Un eventuale login tramite CF richiederebbe un flusso Auth custom server-side e viene rimandato alla futura area Auth di produzione.

---

# 7. Anonymous Auth

Anonymous Auth non è richiesta dai contratti attuali di Props24.

Per il Block S:

```txt
anonymous Auth
→ FUORI SCOPE
```

Il sistema lavora con utenti Auth permanenti.

---

# 8. Workspace

## 8.1 Workspace come confine business condiviso

Il Workspace è l'authority del confine business condiviso.

Modello concettuale:

```txt
public.workspaces

id
name
created_at
updated_at
row_version
```

`name` è una label gestionale/UI.

Esempi:

```txt
"I miei immobili"
"Studio Rossi"
"Cliente Bianchi"
```

Non rappresenta automaticamente il nome legale del locatore o del soggetto rappresentato.

---

## 8.2 Nessun `owner_user_id`

Il Workspace non contiene:

```txt
workspaces.owner_user_id
```

come authority della proprietà gestionale.

L'ownership del Workspace è rappresentata dalla Membership:

```txt
workspace_memberships.role
```

Questo permette:

- più owner;
- cambio di owner;
- collaborazione;
- trasferimento graduale dell'ownership;
- eliminazione dell'accoppiamento diretto User → Workspace.

---

## 8.3 Un Auth User può avere zero Workspace

Relazione canonica:

```txt
Auth User
→ 0..N Workspace Memberships
```

Zero Workspace è uno stato valido e non rappresenta database corruption.

Può indicare:

- nuovo account non ancora onboarded;
- futuro utente Tenant-only;
- utente rimosso da un Workspace;
- account che non ha ancora creato un proprio Workspace.

La UI deve gestire esplicitamente questo stato.

---

## 8.4 Un Workspace non nasce automaticamente al signup

Non vale:

```txt
Auth User creato
→ crea automaticamente Workspace
```

La creazione del Workspace è un'operazione applicativa esplicita.

Questo mantiene separati:

```txt
esistenza dell'account
≠
esistenza di un contesto gestionale
```

---

# 9. Creazione Workspace

Il bootstrap del Workspace avviene tramite una command esplicita.

Flusso target:

```txt
Authenticated User
        ↓
CreateWorkspace
        ↓
Workspace
+
Workspace Profile
+
Owner Membership
```

Le tre write devono essere **atomiche**.

Non deve esistere un flusso browser del tipo:

```txt
insert workspace
await
insert membership
await
insert workspace profile
```

che possa lasciare oggetti parzialmente creati o irraggiungibili.

Target:

```txt
CreateWorkspace
→ server/database transaction
```

L'implementazione concreta della command appartiene alla fase dedicata.

---

# 10. Workspace Membership

## 10.1 Tabella `public.workspace_memberships`

Modello concettuale:

```txt
public.workspace_memberships

id
workspace_id
user_id
role
revoked_at
created_at
updated_at
```

La Membership possiede identity propria:

```txt
id uuid
```

perché ha lifecycle autonomo rispetto alla semplice relazione User ↔ Workspace.

Possiede almeno:

- ruolo;
- stato di revoca;
- lifecycle;
- futura auditabilità;
- possibilità di evoluzione.

---

## 10.2 Unicità logica

Un User può avere una sola Membership logica per Workspace:

```txt
UNIQUE(workspace_id, user_id)
```

La revoca non crea una nuova Membership.

Lifecycle:

```txt
membership attiva
→ revoked_at IS NULL

membership revocata
→ revoked_at IS NOT NULL

riattivazione
→ revoked_at torna NULL
```

La storia completa delle transizioni potrà appartenere al futuro audit.

---

# 11. Ruoli iniziali

Il primo cutover usa soltanto:

```txt
owner
member
```

Non viene anticipato un permission engine completo.

---

## 11.1 `owner`

Può:

- usare i CRUD business;
- amministrare il Workspace;
- amministrare le Membership.

---

## 11.2 `member`

Può:

- usare i CRUD business condivisi.

Nel primo modello non può:

- eliminare/amministrare il Workspace;
- gestire le Membership.

I ruoli futuri più granulari appartengono a una fase successiva.

---

# 12. Tenant non è un Workspace role

Hard rule:

```txt
workspace_memberships.role = tenant
```

**non deve esistere**.

L'accesso futuro del Tenant segue un modello relation-level separato:

```txt
Auth User
→ verified party/account link
→ Lease participation
→ specific resource access
```

Un Tenant non deve diventare membro del dataset gestionale del proprietario per poi essere limitato artificialmente da decine di eccezioni RLS.

---

# 13. Ownership del Workspace

## 13.1 Almeno un owner attivo

Ogni Workspace operativo deve mantenere:

```txt
>= 1 active owner
```

Devono quindi essere bloccati:

```txt
revoca ultimo owner
demotion ultimo owner
```

Il vincolo è cross-row e non viene affidato a un semplice CHECK.

La garanzia deve vivere nella command/transaction che modifica le Membership, con test dedicati.

---

## 13.2 Più owner ammessi

Non vale:

```txt
exactly one owner
```

Sono validi, per esempio:

```txt
owner A
owner B
member C
```

Più owner:

- riducono il rischio di lockout;
- permettono collaborazione;
- permettono trasferimenti graduali;
- evitano una singola FK come authority dell'ownership.

---

## 13.3 Membership ownership ≠ legal ownership

Il ruolo:

```txt
owner
```

significa:

```txt
Workspace owner / admin
```

Non significa:

```txt
proprietario legale di ogni immobile
```

La proprietà legale o contrattuale appartiene al business domain, non al permission model.

---

# 14. Workspace Profile

## 14.1 Separazione fra Personal Profile e business identity

Il sistema distingue:

```txt
profiles
→ chi sei TU come utente Props24
```

da:

```txt
workspace_profiles
→ chi rappresenta QUESTO Workspace nei business data e nei documenti
```

Esempio:

```txt
Auth User
Mario Verdi

Profile
Mario Verdi

Workspace
Immobili Famiglia Rossi

Workspace Profile
Famiglia Rossi
```

oppure:

```txt
Auth User
Giulia Bianchi

Workspace
Rossi Immobiliare

Workspace Profile
Rossi Immobiliare SRL
```

Il soggetto mostrato in ricevute e documenti non può dipendere dall'utente attualmente autenticato.

---

## 14.2 Tabella `public.workspace_profiles`

Per S1.2 il modello rimane volutamente minimale:

```txt
public.workspace_profiles

workspace_id
display_name
created_at
updated_at
```

Vincolo:

```txt
workspace_id
PRIMARY KEY
FK → workspaces
ON DELETE CASCADE
```

Il Workspace Profile è un child 1:1 realmente owned dal Workspace.

`display_name` è l'authority minima iniziale del soggetto rappresentato dai consumer correnti.

Non vengono ancora anticipati campi e modelli completi relativi a:

- CF/P.IVA del locatore;
- sede;
- persona fisica / società;
- coordinate fiscali;
- intestazione documenti;
- modello `parties`.

Questi verranno introdotti quando il relativo business domain sarà definito.

---

## 14.3 `workspaces.name` ≠ `workspace_profiles.display_name`

Distinzione canonica:

```txt
workspaces.name
→ label UI / gestionale
```

```txt
workspace_profiles.display_name
→ soggetto rappresentato
```

Esempio:

```txt
workspace.name
"Cliente Bianchi — Gestione Roma"

workspace_profile.display_name
"Luigi Bianchi"
```

Cambiare il nome gestionale del Workspace non deve modificare automaticamente l'identità mostrata nei documenti.

---

# 15. RLS e authorization

## 15.1 Business rows workspace-scoped

Le business rows appartengono al Workspace tramite:

```txt
workspace_id
```

L'accesso concettuale è:

```txt
auth.uid()
        ↓
workspace_memberships
        ↓
active membership?
        ↓
workspace_id access
```

Non:

```txt
business_row.user_id = auth.uid()
```

La security authority resta la RLS del database.

---

## 15.2 Membership table come authorization authority

`workspace_memberships` è la fonte canonica per verificare l'accesso corrente a un Workspace.

La revoca:

```txt
revoked_at = now()
```

deve produrre:

```txt
successiva query business
→ DENY
```

anche se il JWT del membro è ancora valido.

La revoca deve quindi avere effetto immediato sulle policy RLS.

---

## 15.3 Helper RLS

Le policy workspace-scoped richiederanno helper dedicati, concettualmente equivalenti a:

```txt
private.is_workspace_member(workspace_id)
private.is_workspace_owner(workspace_id)
```

Gli helper servono a:

- evitare duplicazione nelle policy;
- ridurre complessità;
- evitare recursion sulla Membership table;
- centralizzare semantica di membership attiva e ownership;
- facilitare controllo di performance e sicurezza.

La firma SQL definitiva appartiene alla task dedicata alla RLS matrix.

---

# 16. Schema `private`

S1.2 introduce una necessità concreta per uno schema server/security non esposto dalla Data API.

Target:

```txt
public.*
→ application tables
```

```txt
private.*
→ RLS / security helper functions
→ server-only helpers
```

Gli helper `SECURITY DEFINER`, quando introdotti, devono vivere in uno schema non esposto e seguire le regole di hardening definite nella task RLS/SQL concreta.

---

# 17. Active Workspace

`activeWorkspaceId` è stato UI/runtime.

Non è:

- Auth identity;
- authorization authority;
- campo canonico dell'utente;
- lista canonica degli accessi.

Flusso concettuale:

```txt
login
→ load active memberships
→ 0 / 1 / N workspace disponibili
→ selezione UI
→ workspace-scoped dependencies
```

La RLS verifica comunque l'accesso ad ogni operazione.

---

## 17.1 Zero Workspace

```txt
0 active memberships
→ stato valido
```

La UI deve gestire onboarding, rimozione o futuri scenari Tenant-only senza trattarli come errore strutturale.

---

## 17.2 Un Workspace

```txt
1 active membership
→ workspace selezionabile automaticamente
```

---

## 17.3 Più Workspace

```txt
N active memberships
→ workspace selector
```

Il modello deve supportare da subito il multi-workspace anche se la prima UI può essere minimale.

---

## 17.4 Active Workspace non memorizzato in Auth

Non viene introdotto come authority:

```txt
auth.users.current_workspace_id
```

né:

```txt
JWT currentWorkspace
```

La selezione può essere:

- runtime state;
- browser preference;
- futura user preference.

Mai authorization authority.

---

# 18. Cache scope

Il principio target per le query workspace-scoped è:

```txt
query key
→ contiene workspace_id
```

e:

```txt
workspace switch
→ nessun riuso accidentale dei dati del Workspace precedente
```

La strategia concreta di cache invalidation e query scoping appartiene alla task frontend/data-fetching dedicata.

---

# 19. User deletion e offboarding

Il Profile personale può essere owned dall'Auth User e quindi seguire il lifecycle Auth.

Le Membership richiedono invece un workflow controllato.

Non deve essere possibile:

```txt
delete Auth User
→ cancellazione silenziosa delle Membership
→ Workspace senza owner
```

Lifecycle concettuale:

```txt
prima
→ trasferisci / revoca / gestisci Membership correttamente

poi
→ elimina Auth User
```

Se l'utente è l'ultimo owner:

```txt
delete account
→ BLOCKED
```

finché:

- l'ownership non viene trasferita; oppure
- il Workspace non viene chiuso tramite una futura procedura esplicita.

La delete rule SQL esatta appartiene alla task schema/constraint dedicata.

---

# 20. Workspace membership provisioning

S1.2 definisce il **modello**, non il sistema prodotto di invito.

Per il Block S è sufficiente poter creare più Auth User e collegarli in modo controllato allo stesso Workspace per verificare la collaborazione reale.

Il provisioning iniziale può essere realizzato tramite:

- seed/test;
- admin/dev command;
- minimal secure command.

Non è necessario fingere che esista già un sistema completo di invitation lifecycle.

---

# 21. Invitations fuori scope

S1.2 non introduce ancora:

```txt
invitations
```

né definisce:

- email invite;
- token;
- acceptance;
- resend;
- expiry;
- invitation revocation UX.

Queste capability appartengono alle future task dedicate alla collaborazione/inviti.

---

# 22. Party fuori scope

S1.2 non introduce:

```txt
parties
party_account_links
```

Il modello Party potrà essere corretto in futuro per:

- Tenant identity;
- landlord legal identity;
- contract participants;
- account linking;
- multi-role;
- Tenant portal.

Non viene anticipato finché il relativo business domain non sarà progettato.

---

# 23. Nessun matching automatico Account ↔ Tenant

Hard rule:

```txt
Profile.email == Tenant.email
```

non significa:

```txt
account linked to tenant
```

Lo stesso vale per il codice fiscale.

Il futuro collegamento deve essere:

```txt
esplicito
verificato
auditabile
```

Nessuna relazione Account ↔ Tenant viene inferita euristicamente da email, CF o altri campi coincidenti.

# 28. Hard invariants

Le seguenti regole sono vincoli architetturali da preservare nelle task successive.

## Identity

1. `auth.users` è l'unica Auth identity canonica.
2. Non esiste una seconda tabella `public.accounts` come copia dell'utente Auth.
3. Il Profile personale è 1:1 con Auth User.
4. L'email Auth non viene duplicata come seconda authority in `profiles`.
5. `user_metadata` non è authority per authorization o business data.
6. Il CF è Profile identity, non Auth credential nel primo cutover.
7. Il primo login Supabase usa email + password.

## Workspace

8. Auth User e Workspace sono concetti indipendenti.
9. Un Auth User può avere 0..N Workspace Memberships.
10. Il Workspace non viene creato automaticamente al signup.
11. `workspaces.owner_user_id` non esiste come ownership authority.
12. L'ownership gestionale deriva dalle Membership.
13. `workspaces.name` e `workspace_profiles.display_name` hanno semantiche diverse.
14. Personal Profile e Workspace Profile non sono intercambiabili.

## Membership

15. Una Membership possiede UUID proprio.
16. Esiste una sola Membership logica per `(workspace_id, user_id)`.
17. La revoca usa `revoked_at`, senza status duplicato.
18. I ruoli iniziali sono soltanto `owner | member`.
19. `tenant` non è un Workspace role.
20. Ogni Workspace operativo mantiene almeno un owner attivo.
21. Più owner sono ammessi.
22. `owner` indica amministrazione del Workspace, non proprietà legale degli immobili.

## Security

23. Le business rows sono workspace-scoped.
24. La Membership table è authorization authority.
25. La RLS resta security authority.
26. La revoca Membership deve incidere sulla query successiva senza attendere JWT refresh.
27. Active Workspace è UI/runtime state, non security authority.
28. Gli helper security/RLS server-only appartengono allo schema `private`.

## Lifecycle

29. `CreateWorkspace` crea atomicamente almeno Workspace + Workspace Profile + Owner Membership.
30. La cancellazione Auth non può aggirare la protezione dell'ultimo owner.
31. L'offboarding Membership precede la cancellazione dell'Auth User quando necessario.
32. Il Profile personale può essere owned dall'Auth User.
33. Workspace Profile è owned dal Workspace.

## Future access models

34. Tenant access ≠ Workspace Membership.
35. Nessun matching automatico Account ↔ Tenant tramite email o CF.

# 32. Decisioni S1.2 approvate

Sono approvate e consolidate le seguenti decisioni:

1. `auth.users` come unica Auth identity.
2. `profiles.user_id` PK/FK verso `auth.users`.
3. Email non duplicata in `profiles`.
4. Profile creato automaticamente dal signup.
5. CF in `profiles`, nullable e globalmente unique quando valorizzato.
6. Primo login Supabase solo email + password.
7. Un Auth User può avere zero Workspace.
8. Workspace creato tramite command esplicita.
9. Nessun `owner_user_id` in `workspaces`.
10. Introduzione di `workspace_profiles`.
11. Workspace Profile inizialmente minimale.
12. Membership con identity UUID propria.
13. Una Membership logica per User + Workspace.
14. Revoca tramite `revoked_at`.
15. Ruoli minimi `owner | member`.
16. `tenant` non è un Workspace role.
17. Almeno un owner attivo per Workspace.
18. Più owner ammessi.
19. Membership table come authorization authority.
20. Revoca Membership con effetto immediato sulle RLS.
21. Introduzione dello schema `private`.
22. Active Workspace come UI/runtime state.
23. Creazione atomica di Workspace + Workspace Profile + Owner Membership.
24. User deletion/offboarding protetto dal vincolo dell'ultimo owner.
25. Nessuna Invitation/Party table introdotta in S1.2.

# 33. Esito

S1.2 risolve l'accoppiamento del prototipo locale fra utente, profilo e scope dei dati e fissa il foundation model per il cutover Supabase.

Il risultato è:

```txt
Auth identity
+
Personal Profile
+
Workspace
+
Workspace Membership
+
Workspace Profile
+
workspace-scoped business data
+
RLS membership-based
```

con separazione esplicita fra:

```txt
utente autenticato
≠
soggetto rappresentato dal Workspace
≠
Tenant / party futuro
≠
ownership legale del business domain
```

Questo modello costituisce la base per l'implementazione SQL, RLS, read-model, frontend multi-workspace e successiva rimozione delle authority locali legacy.

**S1.2 è chiusa a livello decisionale.**
