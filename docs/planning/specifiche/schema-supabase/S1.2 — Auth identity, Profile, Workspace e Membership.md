## S1.2 — Auth identity, Profile, Workspace e Membership

### Scopo

S1.2 definisce la struttura target di Auth identity, Profile personale, Workspace, Workspace Membership e Workspace Profile nel modello PostgreSQL/Supabase di Props24.

Questa sottotask specializza i principi strutturali approvati in S1.1 e sostituisce l'equazione implicita del prototipo locale:

```text
utente
=
profilo
=
scope dei dati
=
database
```

con un modello in cui:

```text
Auth User
≠
Profile
≠
Workspace
≠
Membership
≠
business / landlord identity
```

S1.2 definisce le authority e le relazioni necessarie per:

* autenticazione tramite Supabase Auth;
* profilo personale indipendente dalle credenziali;
* isolamento dei dati tramite Workspace;
* collaborazione fra più utenti nello stesso Workspace;
* appartenenza di un utente a zero, uno o più Workspace;
* ownership gestionale rappresentata tramite Membership;
* revoca immediata dell'accesso tramite RLS;
* identità stabile del soggetto rappresentato nei documenti;
* futuro accesso Tenant separato dal Workspace gestionale.

Non vengono ancora definiti il permission engine completo, il sistema di inviti, il Party model, le policy RLS concrete o i workflow Auth avanzati.

---

## Vincoli ereditati da S0/S1.1

Restano vincolanti:

* Auth User, Profile, Workspace e Membership sono concetti separati;
* il database locale costituisce baseline comportamentale e non modello fisico da copiare;
* i dati business condivisi devono essere workspace-scoped;
* RLS/server authorization costituisce il confine di sicurezza;
* le identity persistite sono UUID opachi salvo eccezioni 1:1 motivate;
* `ON DELETE CASCADE` è ammesso soltanto per child realmente owned dal parent;
* una mutation multi-record che costituisce una singola operazione business deve avere una vera transaction boundary;
* query/read-model e business authority devono rimanere distinti;
* un dato derivabile non deve diventare una seconda authority persistita senza motivazione;
* la UI deve dipendere da boundary applicative e non dalla shape fisica del database;
* le relazioni canoniche devono essere rappresentate esplicitamente e non inferite euristicamente;
* una successiva task non può modificare implicitamente i contratti approvati soltanto per adattarli alla persistence locale.

S1.2 introduce inoltre una necessità concreta per lo schema server-only `private`, che S1.1 aveva lasciato aperto fino all'emergere di un reale requisito security-side.

# Modello Auth, Profile e Workspace approvato

## 1. `auth.users` come unica Auth identity

Supabase Auth costituisce l'unica authority dell'identità autenticata.

Appartengono ad Auth:

```text
user id
email / login identity
password / hash
sessioni
JWT
provider identities
email verification state
```

Il progetto non introduce una tabella applicativa equivalente a:

```text
public.accounts
```

come copia integrale o seconda authority dell'utente Auth.

Il vecchio identificatore locale:

```text
LocalAccount.id = user-001
```

viene sostituito dall'identità canonica:

```text
auth.users.id = UUID
```

La password non viene mai duplicata nel modello applicativo.

Il vecchio:

```text
LocalAccount.password
```

non ha equivalente nelle tabelle Props24.

---

## 2. Personal Profile

Il profilo personale applicativo vive in:

```text
public.profiles
```

Modello concettuale:

```text
public.profiles

user_id
first_name
last_name
fiscal_code
created_at
updated_at
```

Identity:

```text
user_id uuid
PRIMARY KEY
FK → auth.users(id)
```

Non viene introdotto un secondo:

```text
profiles.id
```

Il Profile è una relazione 1:1 con Auth User e costituisce una delle eccezioni motivate alla regola generale degli UUID indipendenti definita in S1.1.

---

## 3. Lifecycle del Profile

Il Profile non possiede vita autonoma senza Auth User.

Relazione target:

```text
profiles.user_id
→ auth.users.id
ON DELETE CASCADE
```

Il cascade è coerente con S1.1 perché il Profile è realmente owned dall'Auth User.

La cancellazione del Profile non deve però essere confusa con il lifecycle delle Membership, che richiede un offboarding esplicito prima dell'eventuale cancellazione dell'utente.

---

## 4. Email come authority Auth

L'email di login non viene duplicata in:

```text
profiles.email
```

come seconda authority.

La source of truth rimane Supabase Auth.

Il read-model applicativo può comporre:

```text
Auth user.email
+
Profile.first_name
+
Profile.last_name
+
Profile.fiscal_code
```

senza introdurre una tabella che replichi integralmente Auth e Profile.

---

## 5. Creazione automatica del Profile

Ogni Auth User Props24 deve avere il proprio Profile.

Flusso target:

```text
auth.users INSERT
        ↓
DB trigger
        ↓
public.profiles INSERT
```

Il trigger può utilizzare `raw_user_meta_data` soltanto per il bootstrap iniziale di campi non autorizzativi, per esempio:

```text
first_name
last_name
```

Dopo il bootstrap:

```text
public.profiles
→ authority applicativa del profilo
```

`raw_user_meta_data` non diventa business authority.

Il trigger deve essere coperto da test perché un errore nel provisioning del Profile non deve produrre un signup inconsistente.

---

## 6. Auth metadata

`raw_user_meta_data` può essere usato per bootstrap o convenience.

Non deve essere authority per:

```text
workspace memberships
permissions
workspace role
business authority
fiscal authority
```

Principio:

```text
raw_user_meta_data
→ bootstrap / convenience
→ NON authorization
→ NON business authority
```

La lista canonica dei Workspace accessibili non viene inoltre memorizzata nel JWT come authorization authority.

Il JWT identifica l'utente; l'accesso corrente ai Workspace viene determinato dal database tramite Membership e RLS.

---

## 7. Codice fiscale Account

Il codice fiscale dell'account appartiene al Personal Profile.

Target:

```text
profiles.fiscal_code
→ nullable
→ normalized
→ globalmente unique quando valorizzato
```

Non è workspace-scoped perché rappresenta l'identità personale dell'account Props24.

Il constraint SQL concreto e la normalizzazione definitiva appartengono alla matrice constraint di S1.8.

Il CF dell'account rimane distinto dalle duplicate policy future di Contact/Tenant.

---

## 8. Registrazione e login del primo cutover

Il codice fiscale non è obbligatorio alla registrazione.

Target:

```text
registrazione
→ nome
→ cognome
→ email
→ password

fiscal_code
→ opzionale
→ compilabile successivamente
```

Il primo cutover Supabase usa:

```text
email + password
```

Il login:

```text
codice fiscale + password
```

non fa parte del primo cutover.

Il CF rimane Profile identity e non Auth credential.

Un eventuale login tramite CF richiederebbe un flusso Auth custom server-side e viene rinviato alla futura area Auth di produzione.

Anonymous Auth non è richiesto dai contratti attuali e resta fuori scope del Block S.

---

## 9. Workspace come confine business condiviso

Il Workspace rappresenta il confine business condiviso.

Modello concettuale:

```text
public.workspaces

id
name
created_at
updated_at
row_version
```

`name` è una label gestionale/UI.

Esempi:

```text
"I miei immobili"
"Studio Rossi"
"Cliente Bianchi"
```

Non rappresenta automaticamente il nome legale del proprietario, locatore o soggetto rappresentato.

Le business row condivise fanno riferimento al Workspace tramite `workspace_id` secondo i principi definiti in S1.1.

---

## 10. Nessun `owner_user_id` nel Workspace

Il modello non utilizza:

```text
workspaces.owner_user_id
```

come authority dell'ownership gestionale.

L'ownership del Workspace è rappresentata da:

```text
workspace_memberships.role
```

Questa scelta permette:

* più owner;
* cambio di owner;
* collaborazione;
* trasferimento graduale dell'ownership;
* eliminazione dell'accoppiamento diretto User → Workspace.

Il ruolo `owner` indica ownership/amministrazione del Workspace e non proprietà legale degli immobili.

La proprietà legale o contrattuale appartiene al business domain.

---

## 11. Cardinalità User → Workspace

Relazione canonica:

```text
Auth User
→ 0..N Workspace Memberships
```

Un Auth User può quindi avere zero, uno o più Workspace.

Zero Workspace è uno stato valido e può rappresentare:

* nuovo account non ancora onboarded;
* futuro utente Tenant-only;
* utente rimosso da un Workspace;
* account che non ha ancora creato un proprio Workspace.

Con una sola Membership attiva la UI può selezionare automaticamente il Workspace.

Con più Membership attive deve essere supportato un Workspace selector, anche se la prima UI potrà essere minimale.

---

## 12. Workspace non creato automaticamente al signup

Non vale:

```text
Auth User creato
→ crea sempre Workspace
```

La creazione dell'account e la creazione di un contesto gestionale sono operazioni distinte.

Un Workspace viene creato tramite una command esplicita quando l'utente vuole utilizzare Props24 come proprietario/gestore.

---

## 13. Creazione atomica del Workspace

Flusso target:

```text
Authenticated User
        ↓
CreateWorkspace
        ↓
Workspace
+
Workspace Profile
+
Owner Membership
```

Le tre write costituiscono una singola operazione logica e devono essere atomiche.

Non è ammesso sostituirle con una sequenza browser:

```text
insert workspace
await
insert membership
await
insert workspace profile
```

che possa lasciare un Workspace parzialmente creato o irraggiungibile.

Target:

```text
CreateWorkspace
→ server/database transaction
```

La command concreta e il relativo meccanismo transazionale appartengono a S1.9/S2.

---

## 14. Workspace Membership

Le Membership vivono in:

```text
public.workspace_memberships
```

Modello concettuale:

```text
public.workspace_memberships

id
workspace_id
user_id
role
revoked_at
created_at
updated_at
```

La Membership possiede una identity propria:

```text
id uuid
```

perché ha attributi e lifecycle propri:

* ruolo;
* revoca;
* riattivazione;
* futura auditabilità;
* possibili evoluzioni successive.

---

## 15. Unicità e revoca della Membership

Un User può avere una sola Membership logica per Workspace:

```text
UNIQUE(workspace_id, user_id)
```

La revoca non crea una seconda riga.

Semantica:

```text
membership attiva
→ revoked_at IS NULL

membership revocata
→ revoked_at IS NOT NULL

riattivazione
→ revoked_at torna NULL
```

Non viene introdotto uno status duplicato che rappresenti la stessa informazione.

La storia completa delle revoche potrà essere conservata dal futuro audit.

---

## 16. Ruoli iniziali

Il primo cutover utilizza soltanto:

```text
owner
member
```

### `owner`

Può:

* utilizzare i CRUD business;
* amministrare il Workspace;
* amministrare le Membership.

### `member`

Può:

* utilizzare i CRUD business condivisi.

Nel modello iniziale non può:

* eliminare/amministrare il Workspace;
* amministrare le Membership.

Il permission engine completo e ruoli più granulari vengono rinviati alle future task dedicate.

---

## 17. Regole di ownership

Ogni Workspace operativo deve mantenere:

```text
>= 1 active owner
```

Devono quindi essere bloccati:

```text
revoca ultimo owner
demotion ultimo owner
```

Il vincolo è cross-row e non viene affidato a un semplice `CHECK`.

La garanzia deve vivere nella command/transaction che modifica le Membership e deve essere coperta da test dedicati.

Non viene imposto:

```text
exactly one owner
```

Più owner sono ammessi.

Esempio valido:

```text
owner A
owner B
member C
```

Questo riduce il rischio di lockout e permette trasferimenti graduali senza trasformare l'ownership in una singola FK.

---

## 18. Tenant non è un Workspace role

Non deve esistere:

```text
workspace_memberships.role = tenant
```

Il futuro accesso Tenant segue un modello differente:

```text
Auth User
→ verified party/account link
→ Lease participation
→ specific resource access
```

Un Tenant invitato non diventa membro del Workspace gestionale del proprietario.

Questo evita di modellare il Tenant come membro del dataset completo per poi nascondergli quasi tutte le risorse tramite eccezioni RLS.

---

## 19. Workspace Profile

Il sistema distingue:

```text
profiles
→ chi sei TU come utente Props24
```

da:

```text
workspace_profiles
→ chi rappresenta QUESTO Workspace nei business data/documenti
```

Modello concettuale minimo:

```text
public.workspace_profiles

workspace_id
display_name
created_at
updated_at
```

Identity:

```text
workspace_id
PRIMARY KEY
FK → workspaces
ON DELETE CASCADE
```

Il Workspace Profile è un child 1:1 realmente owned dal Workspace.

`display_name` è l'authority minima iniziale del soggetto rappresentato dai consumer correnti.

Non vengono ancora anticipati:

* CF/P.IVA del locatore;
* sede;
* persona fisica/società;
* coordinate fiscali;
* intestazione documenti;
* Party model completo.

Questi aspetti verranno definiti quando il relativo business domain sarà progettato.

---

## 20. `workspaces.name` e `workspace_profiles.display_name`

Le due proprietà hanno semantiche differenti.

```text
workspaces.name
→ label UI / gestionale
```

```text
workspace_profiles.display_name
→ soggetto rappresentato
```

Esempio:

```text
workspace.name
"Cliente Bianchi — Gestione Roma"

workspace_profile.display_name
"Luigi Bianchi"
```

Cambiare il nome gestionale del Workspace non deve cambiare automaticamente il soggetto rappresentato nei documenti.

---

## 21. Receipt e document identity

L'attuale dipendenza locale:

```text
receipt
→ LocalDatabase.userProfile
```

deve essere eliminata.

Target concettuale:

```text
Payment
→ Lease
→ Workspace
→ Workspace Profile
→ represented / landlord display identity
```

Non:

```text
→ current authenticated user's Profile
```

Due collaboratori che operano sullo stesso Workspace devono produrre documenti con la stessa identità rappresentata, salvo una futura business rule esplicita differente.

---

## 22. Authorization tramite Membership

Le business row condivise sono workspace-scoped.

L'accesso concettuale è:

```text
auth.uid()
        ↓
workspace_memberships
        ↓
active membership?
        ↓
workspace_id access
```

Non:

```text
business_row.user_id = auth.uid()
```

`workspace_memberships` è la source of truth dell'accesso corrente al Workspace.

La RLS rimane la security authority del database.

---

## 23. Revoca immediata

La revoca:

```text
revoked_at = now()
```

deve comportare:

```text
successiva query business
→ DENY
```

anche se il JWT del membro è ancora valido.

Per questo motivo la lista canonica delle Membership non viene usata dal JWT come authorization authority.

Principio:

```text
JWT
→ Auth identity

workspace_memberships
→ authorization authority
```

La revoca deve essere osservata dalle policy RLS senza attendere un refresh del token.

---

## 24. Helper RLS e schema `private`

Le policy workspace-scoped richiederanno helper security dedicati, concettualmente equivalenti a:

```text
private.is_workspace_member(workspace_id)
private.is_workspace_owner(workspace_id)
```

Gli helper permettono di:

* centralizzare la semantica di Membership attiva e ownership;
* evitare duplicazione nelle policy;
* evitare recursion sulla Membership table;
* ridurre complessità;
* rendere verificabili performance e security boundary.

S1.2 approva quindi l'introduzione dello schema:

```text
private.*
```

per funzioni security/server-only non esposte dalla Data API.

Target:

```text
public.*
→ application tables

private.*
→ RLS/security helper functions
→ server-only helpers
```

La firma SQL definitiva, l'eventuale uso di `SECURITY DEFINER`, `search_path` e le policy concrete appartengono a S1.11.

# Runtime e lifecycle derivati

## 25. Active Workspace

`activeWorkspaceId` è runtime/UI state.

Non è:

* Auth identity;
* authorization authority;
* campo canonico dell'utente;
* lista canonica degli accessi.

Flusso concettuale:

```text
login
→ load active memberships
→ 0 / 1 / N Workspace disponibili
→ selezione UI
→ workspace-scoped dependencies
```

La RLS verifica comunque l'accesso alle singole operazioni.

Non viene introdotto come authority:

```text
auth.users.current_workspace_id
```

né:

```text
JWT currentWorkspace
```

La selezione attiva può vivere come runtime state, browser preference o futura user preference.

---

## 26. Cache e query scope

Per le query workspace-scoped il principio target è:

```text
query key
→ contiene workspace_id
```

e:

```text
workspace switch
→ nessun riuso accidentale dei dati del Workspace precedente
```

La strategia concreta di cache invalidation e query scoping appartiene alle task frontend/data-fetching successive.

Questo requisito è una conseguenza del boundary Workspace, non una nuova authority.

---

## 27. Read-model Auth/UI

L'attuale:

```text
useUserProfile()
→ LocalAccount
```

viene sostituito concettualmente da:

```text
Auth session
+
profiles
        ↓
CurrentUserView
```

Il read-model potrà esporre per esempio:

```text
userId
email
firstName
lastName
fiscalCode
```

senza che esista una tabella unica che duplichi tutto.

La forma concreta del read-model appartiene a S1.10/S3.

---

## 28. Read-model Workspace

Analogamente:

```text
active membership
+
workspace
+
workspace_profile
        ↓
CurrentWorkspaceView
```

potrà esporre almeno:

```text
workspaceId
workspaceName
role
representedDisplayName
```

La UI non deve ricostruire direttamente il join fra più tabelle in ogni consumer.

La forma concreta del read-model appartiene a S1.10/S3.

---

## 29. User deletion e offboarding

Il Profile personale può seguire il lifecycle dell'Auth User.

Le Membership richiedono invece un workflow controllato.

Non deve essere possibile:

```text
delete Auth User
→ cancellazione silenziosa Membership
→ Workspace senza owner
```

Lifecycle concettuale:

```text
prima
→ trasferisci / revoca / gestisci Membership

poi
→ elimina Auth User
```

Se l'utente è l'ultimo owner:

```text
delete account
→ BLOCKED
```

finché:

* l'ownership non viene trasferita; oppure
* il Workspace non viene chiuso tramite una futura procedura esplicita.

La FK/delete rule concreta appartiene a S1.8.

La cancellazione Auth non deve poter aggirare la protezione dell'ultimo owner.

# Provisioning e access model futuri

## Membership provisioning iniziale

S1.2 definisce il modello delle Membership, non il sistema prodotto di invito.

Per il Block S è sufficiente poter creare più Auth User e collegarli in modo controllato allo stesso Workspace per verificare collaborazione e isolamento.

Il provisioning iniziale può essere implementato tramite:

* seed/test;
* admin/dev command;
* minimal secure command.

Non deve essere simulato un invitation lifecycle completo prima che venga progettato.

---

## Nessun matching automatico Account ↔ Tenant

Una coincidenza del tipo:

```text
Profile.email == Tenant.email
```

non significa:

```text
account linked to tenant
```

Lo stesso principio vale per il codice fiscale.

Il futuro collegamento Account ↔ Tenant/Party deve essere:

```text
esplicito
verificato
auditabile
```

Nessuna relazione viene inferita euristicamente da email, CF o altri campi coincidenti.

---

# Authority sostituite dal cutover

Alla fine del Block S non devono più essere runtime authority:

```text
LocalAccount
LocalSession
props24.auth.accounts
props24.auth.session
user-NNN identity
password localStorage
AuthContext → setActiveDatabaseAccount
activeDatabaseAccountId
```

S1.2 definisce il modello target.

La rimozione definitiva del codice legacy appartiene alla fase di cutover prevista dal Block S e non viene eseguita da questa sottotask di progettazione.
