## S1.9 — Matrice delle transaction command

### Scopo

S1.9 definisce quali operazioni Props24 devono essere eseguite come singola transaction PostgreSQL e quali regole di concorrenza devono proteggerle.

Il principio target è:

```text
una business operation
→ un solo confine transazionale
→ commit completo oppure rollback completo
```

La decomposizione del vecchio `LocalDatabase` non deve trasformare mutation oggi atomiche in sequenze parzialmente persistite.

---

## Vincoli ereditati da S1.1–S1.8

Restano vincolanti:

* query side-effect free;
* command per mutation aggregate o cross-domain;
* constraint PostgreSQL come prima difesa dell'integrità;
* RLS distinta dalla transaction logic;
* optimistic concurrency tramite `row_version`;
* bulk all-or-nothing;
* Activity nella stessa transaction della mutation che la produce;
* Storage e PostgreSQL non condividono una transaction ACID;
* nessun generic CRUD che aggiri le business rule finanziarie;
* schedule Payment generata soltanto da command/job;
* Draft cleanup separato dal submit business riuscito.

---

# Confine transazionale

## 1. Transaction server-side

Le operation multi-table o con invariant cross-row devono essere eseguite server/database-side.

Primo adapter previsto:

```text
UI
→ Command
→ PostgreSQL function / RPC
→ transaction
```

È vietato implementare una business command atomica come sequenza:

```text
insert A
await

update B
await

insert C
```

dal browser.

Le mutation realmente single-row e completamente protette da constraint/RLS possono invece restare repository operation semplici.

---

## 2. Concorrenza

Baseline:

```text
READ COMMITTED
+
constraint S1.8
+
row lock mirati
+
transaction advisory lock dove necessario
```

Non viene imposto `SERIALIZABLE` globalmente.

Quando più righe devono essere bloccate:

```text
dedupe ID
→ ordinamento deterministico
→ lock nello stesso ordine
```

per ridurre i deadlock.

---

## 3. Optimistic concurrency

Le root condivise usano:

```text
id
+
expected_row_version
```

La mutation riesce soltanto se la versione corrente coincide.

Successo:

```text
row_version = row_version + 1
```

Mismatch:

```text
stale_record
```

Una singola business command incrementa la root version una sola volta, indipendentemente dal numero di statement SQL interni.

---

## 4. Bulk

I bulk ricevono concettualmente:

```text
[
  { id, expected_row_version },
  ...
]
```

La command:

```text
valida tutto
→ blocca tutto
→ verifica tutto
→ muta tutto
```

Qualunque elemento mancante, stale o bloccato causa rollback dell'intero batch.

---

## 5. Identity retry-safe

Le principali create utilizzano UUID generato una sola volta prima della command.

Lo stesso UUID viene riutilizzato in un eventuale retry transitorio.

Questo vale almeno per:

```text
Workspace
Building
Property
Tenant
Lease
Payment manuale
Document
Communication
File Object
```

Un errore di rete non deve poter generare una seconda entity equivalente.

---

# Workspace e Membership

## 6. CreateWorkspace

`CreateWorkspace` crea atomicamente:

```text
workspaces
workspace_profiles
workspace_memberships(role = owner)
```

L'owner deriva dall'Auth User corrente.

Il client non fornisce un `owner_user_id` arbitrario.

---

## 7. Membership lifecycle

Le mutation Membership sono command semantiche:

```text
AddWorkspaceMember
ReactivateWorkspaceMember
ChangeWorkspaceMemberRole
RevokeWorkspaceMember
```

La Workspace row viene bloccata e costituisce il punto di serializzazione delle modifiche di ownership.

Revoca o demotion dell'ultimo owner vengono bloccate nella stessa transaction.

Anche l'offboarding Auth deve rispettare questo invariant.

---

# Buildings e Properties

## 8. Building aggregate

`CreateBuilding` atomizza:

```text
Building
+
building_features
```

`UpdateBuilding`:

```text
lock Building
check row_version
update root
reconcile features
increment row_version
```

Archive, restore e delete bulk restano all-or-nothing.

---

## 9. Property aggregate

`CreateProperty` può comprendere:

```text
Property
Building relation
equipment/features
access items
Property Contacts
owned child
Document metadata/link già disponibili
```

Una nuova relazione Building richiede una Building active dello stesso Workspace.

Una relazione già esistente resta valida se la Building viene archiviata successivamente.

---

## 10. UpdateProperty

`UpdateProperty`:

```text
lock Property
check row_version
validate nuova Building quando cambia
update root
reconcile owned child
reconcile document links
increment row_version
```

Archive/restore/delete bulk restano atomici.

Lease e Payment storici continuano a bloccare l'hard delete Property.

---

# Contacts e Tenants

## 11. Contact

Contact resta un dominio semplice.

Create/update/lifecycle possono utilizzare repository mutation dirette quando una sola row è coinvolta e constraint/FK sono sufficienti.

La delete protection resta affidata alle FK come authority finale.

---

## 12. Tenant aggregate

`CreateTenant` atomizza:

```text
Tenant
tenant_guarantors
tenant_emergency_contacts
eventuale private note
Documents / DocumentLinks
```

La transaction verifica:

```text
identità fiscale
max 5 Emergency
exactly one primary se presenti
Contact references
```

---

## 13. Nuove relation Contact

Un Contact nuovo o sostituito nella relation Tenant deve essere:

```text
stesso Workspace
active
```

Per Emergency deve inoltre possedere un telefono valido.

La verifica viene protetta da lock durante la transaction.

Una relation già esistente resta valida se il Contact viene archiviato successivamente.

---

## 14. UpdateTenant

`UpdateTenant`:

```text
lock Tenant
check row_version

validate fiscal identity
validate nuove relation Contact
validate Emergency set

update root
reconcile guarantors
reconcile emergency contacts
reconcile private note
reconcile Documents

increment row_version
```

Un Contact creato esplicitamente dal form resta una mutation autonoma: il fallimento successivo della Tenant command non lo elimina.

---

## 15. Tenant lifecycle

Archive/restore/delete bulk:

```text
dedupe
sort
lock
check version
validate blocker
mutate all
```

Hard delete è bloccato da storico:

```text
Lease
Payment
Communication
```

---

# Lease concurrency

## 16. Tenant advisory lock

La regola overlap:

```text
stesso Tenant
+
date sovrapposte
+
Property differente
+
Lease non archived
→ BLOCK
```

viene resa concurrency-safe tramite transaction advisory lock logico per:

```text
workspace_id + tenant_id
```

I Tenant ID vengono deduplicati e ordinati prima dell'acquisizione dei lock.

---

## 17. Quando applicare l'advisory lock

Lo stesso protocollo viene usato da tutte le Lease command che possono cambiare il conflict set:

```text
CreateLease
UpdateLease
TerminateLease
ArchiveLease
RestoreLease
DeleteLease
```

e da eventuali future mutation di:

```text
Tenant
Property
start_date
end_date
archived_at
```

---

# Lease aggregate

## 18. CreateLease

`CreateLease` atomizza:

```text
Lease
lease_tenants
lease_guarantors
lease_payment_items
lease_insurance_contracts
generated Payment schedule
deposit Payment quando applicabile
lease_created Activity
```

Prima del commit vengono validati:

```text
Property
Tenant
Guarantor
Workspace consistency
overlap
```

La schedule economica viene calcolata dal trusted command boundary, non accettata dal client come authority.

---

## 19. UpdateLease

`UpdateLease` atomizza:

```text
Lease root
participants
payment items
insurance
generated schedule reconciliation
deposit consistency
Activity
Activity Changes
```

La command protegge:

```text
Payment paid
manual Payment
deposit/return
generated storico
prepaid-linked Payment
```

e rigenera soltanto future generated unpaid realmente rigenerabili.

Property/Tenant non possono essere modificati quando produrrebbero incoerenza con evidenza finanziaria protetta.

---

## 20. Manual end-date override

L'override manuale resta parte di `UpdateLease`.

Quando presente richiede:

```text
reason_code
reason_details quando necessario
```

e genera nella stessa transaction:

```text
lease_end_date_overridden
+
before/after end_date
```

Non viene introdotto un secondo save separato.

---

## 21. Lease lifecycle

### Activate

Rivalida:

```text
Property active
Tenant active
Guarantor active
overlap
```

e riconcilia schedule/deposito.

### Deactivate

Modifica soltanto il lifecycle e conserva lo storico economico.

### Archive

Preserva:

```text
Payments
Documents
participants
Activity
```

### Restore

Rivalida reference attive e overlap prima del ripristino.

Tutte incrementano `row_version` e appendono Activity quando previsto.

---

## 22. TerminateLease

`TerminateLease`:

```text
lock Lease
lock Payment rilevanti
validate termination
```

poi:

```text
contract_status = terminated
end_date = termination date
auto_renew = false
termination_reason = ...
terminated_at = now()
```

Può rimuovere soltanto future generated unpaid oltre la nuova fine.

Storico economico reale viene preservato.

---

## 23. DeleteLease

L'hard delete richiede assenza di blocker quali:

```text
Payment paid
Payment non-generated
Documents
Signature process
Communication history
```

Quando consentito elimina soltanto schedule rigenerabile e successivamente la Lease.

Le child owned e l'Activity possono essere eliminate tramite i cascade approvati in S1.8.

---

# Payment Schedule

## 24. EnsureLeasePaymentSchedule

La materializzazione della schedule appartiene a una system command esplicita:

```text
EnsureLeasePaymentSchedule
```

La command:

```text
lock Lease
legge i termini canonici
calcola rate
crea generated Payment mancanti
```

La uniqueness della generated schedule rende l'operazione idempotente.

La semplice riconciliazione tecnica non produce Lease Activity.

---

# Payment commands

## 25. Manual Payment

Sono command distinte:

```text
CreateManualPayment
UpdateManualPayment
DeleteManualPayment
```

La Property e l'eventuale Tenant attribution coerenti con la Lease vengono derivati dal command boundary.

Un Payment manuale paid non è modificabile o eliminabile.

Ogni mutation significativa produce Activity.

---

## 26. ConfirmPayment

`ConfirmPayment` atomizza:

```text
Payment
PaymentConfirmation
Lease Activity
Activity Changes
```

e verifica:

```text
Payment non già paid
full settlement
paid_date valida
source/date rules
```

La Confirmation usa upsert perché `MarkPaymentUnpaid` conserva il record precedente.

---

## 27. MarkPaymentUnpaid

La command:

```text
paid_date → NULL
```

e conserva:

```text
receipt_number
payment_confirmation
```

come già approvato in S1.5.

Produce Activity e incremento `row_version`.

---

# Prepaid

## 28. AllocatePrepaidRent

La command serializza tramite Lease lock e blocca i Payment selezionati.

Verifica:

```text
stessa Lease
generated
categoria eleggibile
unpaid
non già allocato
credito disponibile
```

e crea le allocation atomicamente.

---

## 29. Guardrail prepaid

Nel primo cutover:

```text
Payment con prepaid allocation pending
→ ConfirmPayment BLOCCATA
```

per evitare settlement manuale e prepaid contemporaneamente.

Inoltre:

```text
Payment con prepaid allocation applied
→ MarkPaymentUnpaid BLOCCATA
```

finché PA-10 non definirà una vera reversal policy.

Queste regole non risolvono la contabilità prepaid definitiva: impediscono soltanto stati incoerenti.

---

## 30. ApplyDuePrepaidAllocations

System command:

```text
lock allocation
lock Payment
```

Se la scadenza è raggiunta e Payment resta unpaid:

```text
set paid_date
set applied_on
increment Payment row_version
append prepaid_applied
actor = system
```

---

# Deposit

## 31. Deposit lifecycle

La creazione/riconciliazione del deposito è un helper interno alle Lease command e non un generic Payment CRUD.

Se il deposito è già paid, i termini incompatibili non possono essere modificati liberamente.

`RegisterDepositReturn` blocca Lease e deposito originario e impedisce return duplicati.

---

# Documents e Storage

## 32. Nessun accesso Storage dentro una DB transaction

Upload, delete o altre chiamate esterne non avvengono mentre sono mantenuti lock PostgreSQL.

La transaction DB deve restare breve.

---

## 33. Upload workflow

Workflow standard:

```text
genera FileObject UUID
→ upload Storage
→ business DB transaction
→ commit
```

La transaction può creare:

```text
file_object
document
document_link
Activity
```

Se il commit DB fallisce:

```text
→ cleanup compensativo Storage
```

Un fallimento del cleanup produce un object fisico orphan recuperabile, non metadata business che puntano intenzionalmente a un file assente.

---

## 34. Delete workflow

Ordine:

```text
DB transaction
→ rimuove business reference / Document / FileObject se orphan
→ commit

poi

Storage delete
```

Se il delete Storage fallisce, il database business resta consistente e il cleanup può essere ritentato.

---

## 35. Lease Document commands

Command:

```text
CreateLeaseDocument
LinkLeaseDocument
UpdateLeaseDocument
DeleteLeaseDocument
```

mantengono Document mutation e Lease Activity nella stessa transaction.

Un linked Document riusa il `file_object_id`.

Un file replacement crea sempre un nuovo File Object.

Delete verifica almeno:

```text
signature usage
insurance usage
```

prima della rimozione.

---

# Signature

## 36. StartSignature

Il contract snapshot deve corrispondere esattamente alla versione Lease che si intende firmare.

Workflow:

```text
render snapshot
upload Storage

DB transaction:
lock Lease
check expected_row_version
validate lifecycle
validate no existing process

create FileObject
create generated Document
create contract_snapshot link
create SignatureProcess
create Signers
append Activity
```

Se la Lease è diventata stale, la command fallisce e lo Storage upload viene compensato.

---

## 37. SignLease

Dopo l'upload della firma:

```text
lock process/signer
validate signer pending

create FileObject
create signature Document
link signer

set signed_at

se tutti firmati
→ completed_at

append Activity
```

DB failure comporta cleanup compensativo del file appena caricato.

---

## 38. ResetSignature

La command elimina:

```text
SignatureProcess
Signers
signature Documents/Links
```

ma preserva:

```text
contract snapshot
```

e aggiunge `signature_reset`.

Gli eventuali File Object orphan vengono puliti dopo il commit.

---

# Communications

## 39. PrepareCommunication

Una preparazione multi-Lease produce atomicamente:

```text
1 Communication
N Communication Targets
1 Lease Activity per Lease coinvolta
```

Lease e Tenant vengono letti/bloccati in ordine deterministico e nome/email vengono snapshot.

---

## 40. Mailto

`mailto` non appartiene alla transaction.

Viene costruito/aperto soltanto dopo il commit.

Il mancato avvio del client email non trasforma:

```text
status = prepared
```

in errore di persistence e non implica mai `sent`.

---

# Drafts

## 41. SaveDraft

Una Draft senza file può essere un normale atomic upsert.

Quando comprende attachment già caricati:

```text
Draft
DraftFiles
eventuali FileObjects
```

devono essere coerenti nella stessa DB transaction.

La logical uniqueness S1.8 protegge la concorrenza sulla stessa Draft key.

---

## 42. Submit e cleanup Draft

Il submit definitivo e la cancellazione Draft restano separati:

```text
business mutation
→ COMMIT

poi
→ Draft cleanup
```

Se il cleanup fallisce:

```text
business result resta valido
business mutation non viene ripetuta
si ritenta soltanto il cleanup
```

---

## 43. Draft file promotion

Un File Object già associato alla Draft viene riutilizzato:

```text
Draft File
→ stesso File Object
→ Document
→ Document Link
```

Non viene ricaricato o copiato inutilmente.

---

# Lease Activity

## 44. Audit atomico

Quando una command produce Activity:

```text
business mutation
+
lease_activities
+
lease_activity_changes
```

devono appartenere alla stessa transaction.

Non è ammesso:

```text
business commit
→ append audit successivo
```

---

## 45. Actor

L'autore viene derivato nel trusted boundary:

```text
actor_user_id = auth.uid()
```

Il client non decide:

```text
actor_user_id
actor_name_snapshot
```

come authority.

---

# Security delle command

## 46. Function security

`SECURITY INVOKER` resta il default.

`SECURITY DEFINER` viene usato soltanto dove necessario, per esempio quando una command deve scrivere Activity non direttamente modificabili dal client.

In tal caso sono obbligatori:

```text
search_path = ''
schema qualification esplicita
Auth identity verificata
Membership/role verificati
EXECUTE grants limitati
```

La matrice authorization completa appartiene a S1.11.

---

## 47. Trusted derivation

Il browser comunica business intent, ma non decide autonomamente valori authority quali:

```text
workspace_id dei child
actor_user_id
created_at
updated_at
nuovo row_version

Property/Tenant Payment derivabili dalla Lease
generated schedule
generated amount
signature completion state
audit actor
```

Questi vengono determinati dalla command.

---

# Command result e retry

## 48. Result minimale

La command restituisce soltanto informazioni necessarie al commit, come:

```text
id
new_row_version
child ID rilevanti
eventuali Storage object da pulire
```

Dopo il successo:

```text
UI
→ invalidate/refetch
→ Query S1.10
```

Non viene ricostruito un nuovo mega-read-model.

---

## 49. Retry

Retry automatico soltanto per errori realmente transitori, per esempio:

```text
deadlock
serialization/transient failure
```

e sempre:

```text
bounded
+
stesso UUID
+
stesso business intent
```

Non vengono ritentati automaticamente:

```text
stale_record
validation error
duplicate
historical blocker
permission denied
overlap conflict
```
