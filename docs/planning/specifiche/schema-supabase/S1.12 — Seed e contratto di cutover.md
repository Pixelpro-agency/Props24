## S1.12 — Seed e contratto di cutover

### Scopo

S1.12 definisce il contratto con cui Props24 passa dalla persistenza locale a Supabase senza introdurre dual-write, fallback silenziosi, import impliciti o due authority concorrenti.

La regola fondamentale è:

```text
una capability runtime
→ una sola authority

local
oppure
Supabase
```

Seed, migration, bootstrap business e legacy import sono processi distinti.

---

## 1. Migration e versioning

Le migration SQL versionate sono l’unica authority della versione dello schema PostgreSQL.

Non viene replicato il modello locale:

```text
schemaVersion
seedVersion
normalize/repair runtime
```

in una nuova table di metadata applicativa.

Una migration già applicata in un ambiente condiviso non viene modificata retroattivamente: eventuali correzioni producono una nuova migration.

Le migration possono contenere:

```text
table
constraint
index
function
policy
grant
data migration necessarie
```

ma non fixture demo/test.

---

## 2. Seed

Il nuovo seed viene costruito direttamente sul modello target S1.

Non viene convertito automaticamente:

```text
src/db/database.json
```

perché il dataset locale contiene anche shape legacy, dati derivati e strutture che non appartengono più alle authority PostgreSQL.

Il seed serve esclusivamente a sviluppo e test.

---

## 3. Nessun import automatico locale

Non vengono importati automaticamente:

```text
database.json
props24.localDb.*
legacy local DB
backup locali
Draft localStorage
StoredLocalFile / Data URL
LocalAccount
LocalSession
```

L’import non avviene:

```text
al login
al signup
al primo accesso
alla prima query
alla prima mutation
alla CreateWorkspace
```

Sono vietati sia `import-on-read` sia `import-on-write`.

---

## 4. Auth locale

Gli attuali account locali:

```text
user-001
user-002
...
```

non diventano automaticamente Supabase Auth User.

Le password locali non vengono:

```text
copiate
trasformate
hashate
riutilizzate
```

nel nuovo Auth system.

Supabase Auth parte con identità reali create tramite i propri workflow.

---

## 5. Bootstrap business

Signup e business seed sono separati.

Signup crea il Profile secondo S1.2.

Workspace viene creato soltanto tramite:

```text
CreateWorkspace
```

Un nuovo account o Workspace non riceve automaticamente:

```text
Building demo
Property demo
Tenant demo
Lease demo
Payment demo
```

Il comportamento storico per cui il primo account locale può essere inizializzato da `database.json` viene eliminato.

---

## 6. Ambienti seed

Baseline:

```text
local development
→ seed consentito

CI / automated test
→ seed consentito

staging test
→ seed sintetico consentito

production
→ nessun business demo seed automatico
```

Il deploy production applica migration, non fixture demo.

Le procedure distruttive di reset remoto non fanno parte del normale workflow production.

---

## 7. Fixture sintetiche

Il seed committato contiene soltanto dati sintetici.

Non devono essere presenti:

```text
dati personali reali
codici fiscali reali
documenti reali
password reali
token
API key
secret
```

Le fixture usano UUID deterministici quando i test devono conoscere le identity.

Timestamp e date rilevanti per test deterministici vengono anch’essi fissati esplicitamente.

---

## 8. Temporalità dei test

I test temporali non dipendono dal giorno reale in cui vengono eseguiti.

Usano:

```text
fixture stabile
+
referenceDate esplicita
```

secondo il contratto S1.10.

Non è necessario aggiornare periodicamente il seed solo per mantenere una Lease “corrente”.

---

## 9. Riproducibilità

Il contratto fondamentale del seed è:

```text
database vuoto
→ tutte le migration
→ seed
→ database valido
```

Il seed comune non deve mascherare errori strutturali tramite `ON CONFLICT DO NOTHING` indiscriminati.

Duplicati o fixture incoerenti devono normalmente fallire.

---

## 10. Personas test

Le fixture devono poter rappresentare almeno:

```text
user senza Workspace

owner Workspace A
member Workspace A
revoked member Workspace A

owner Workspace B

user member sia A sia B
```

così da supportare i test RLS S1.11.

Gli account login-capable per browser/e2e vengono creati tramite il setup Auth di test appropriato, non tramite credenziali production hardcoded nel seed business.

---

## 11. Seed modulare

Il seed può crescere per fasi:

```text
S2
→ Auth/Profile/Workspace/Membership

S4
→ Contact/Building/Draft

S5
→ Property/Tenant/Documents

S6
→ Lease/Payments/Activity/Communications
```

Il seed comune contiene soltanto stati validi rispetto ai constraint S1.8.

Gli stati volutamente invalidi restano fixture isolate dei relativi test.

---

## 12. Seed e command

Il fatto che un seed privilegiato inserisca direttamente una row valida non costituisce test della relativa business command.

Per esempio:

```text
seed crea Lease
≠ test CreateLease

seed crea Payment
≠ test ConfirmPayment
```

I command vengono verificati attraverso i veri entry point S1.9.

---

## 13. Storage fixture

Il seed SQL non manipola direttamente:

```text
storage.objects
```

e non introduce Data URL nel target.

Quando un integration test richiede un file reale, usa Storage API e workflow FileObject/Document coerenti con S1.6, S1.9 e S1.11.

---

# Legacy data

## 14. Legacy ID

Gli ID locali legacy non modificano il target UUID.

Non viene allargato lo schema soltanto per accettare identity come:

```text
property-001
tenant-001
54707
```

perché questi dati non sono oggetto di import automatico.

---

## 15. Eventuale import futuro

Un eventuale futuro dataset che debba realmente essere preservato richiederà un processo separato:

```text
export
→ validation
→ legacy ID mapping
→ relation mapping
→ file upload
→ dry-run
→ conflict report
→ import
→ reconciliation
```

Non fa parte implicitamente del Blocco S.

Un eventuale mapping `legacy_id → target_uuid` resta artefatto di import e non nuova business authority.

---

# Authority runtime

## 16. Stati ammessi

Per ogni capability esistono soltanto:

```text
local
Supabase
```

Sono vietati:

```text
hybrid
auto
both
prefer_remote
fallback
shadow-write
```

---

## 17. Read authority

Quando una capability passa a Supabase:

```text
list
detail
reference lookup autoritativo
```

leggono Supabase.

È vietato:

```text
Supabase restituisce []
→ usa LocalDatabase
```

Una lista remota vuota è un risultato valido.

---

## 18. Write authority

Quando una capability è Supabase-authoritative:

```text
write
→ Supabase soltanto
```

Non vengono mantenute shadow write verso `jsonDb`.

Il dual-write non è utilizzato neppure temporaneamente come meccanismo di sicurezza o comparazione.

---

## 19. Legacy locale dopo il cutover

I vecchi dati locali possono rimanere fisicamente presenti fino a S7.

Dopo il cutover diventano però:

```text
non-authoritative
non-readable dal dominio migrato
non-writable dal dominio migrato
stale
```

Authority cutover e cleanup fisico sono due momenti distinti.

---

## 20. Authority selection

La scelta dell’adapter autoritativo appartiene alla composition applicativa e alla versione del software.

Non è:

```text
user preference
localStorage toggle
feature switch modificabile dall’utente
```

---

## 21. Remote failure

Dopo il cutover:

```text
network failure
RLS failure
PostgreSQL failure
Storage failure
```

producono un errore esplicito.

È vietato:

```text
catch
→ usa LocalDatabase
```

Il fallback locale/in-memory del prototipo non viene mantenuto.

---

# Pilot e parity

## 22. Pilot

Un pilot può confrontare:

```text
scenario su Local adapter
scenario su Supabase adapter
```

con fixture indipendenti.

Questo è parity testing.

Non è consentito eseguire in runtime:

```text
mutation
→ write Local
→ write Supabase
→ confronta
```

---

# Dipendenze cross-domain

## 23. Invariant e authority

Una business command deve poter verificare tutti i propri invariant nell’authority che esegue la mutation.

Non è ammesso:

```text
Supabase command
→ verifica parte dell’invariant nel localStorage
```

e non esiste transaction ACID fra browser storage e PostgreSQL.

---

## 24. Lookup cross-authority

Durante la migrazione può essere temporaneamente ammesso un lookup read-only verso un dominio già migrato, quando serve esclusivamente a selection/display.

Non può essere usato per costruire un invariant transazionale distribuito fra due persistence authority.

---

# Delete transitorie fail-closed

## 25. Building

`DeleteBuilding` richiede conoscere tutte le Property collegate.

Se Building è già Supabase e Property è ancora locale:

```text
DeleteBuilding
→ temporaneamente unavailable / fail-closed
```

Archive resta disponibile.

La delete completa torna disponibile quando Property diventa Supabase-authoritative.

---

## 26. Contact

`DeleteContact` dipende da riferimenti presenti in Tenant e Lease.

Finché tali blocker non sono tutti remoti:

```text
DeleteContact
→ fail-closed
```

Non viene consultato il database locale come fallback.

---

## 27. Property

L’hard delete Property richiede conoscere Lease e Payment history.

Durante S5, finché Lease/Payment restano locali:

```text
DeleteProperty
→ fail-closed
```

---

## 28. Tenant

L’hard delete Tenant dipende da:

```text
Lease
Payment
Communication
```

e resta fail-closed finché tali blocker non sono Supabase-authoritative.

---

## 29. File cleanup

La rimozione fisica definitiva di FileObject/Storage resta conservativa finché tutti i domini che possono referenziare quei file non sono stati migrati.

Il cleanup completo resta owner di S7.

---

## 30. Nessun mirror transitorio

Non vengono create copie/mirror delle relazioni locali nel database remoto solo per mantenere attive le delete durante le fasi intermedie.

Il modello preferisce:

```text
authority singola
+
destructive operation temporaneamente bloccata
```

rispetto a:

```text
due authority sincronizzate
```

---

# Cutover gate

## 31. Prerequisiti

Una capability cambia authority soltanto dopo un gate tecnico.

Il gate comprende almeno:

```text
migration ricostruibili da zero
seed riproducibile
schema/constraint PASS
RLS PASS
cross-workspace PASS
command integration PASS
query/read-model PASS
atomic rollback PASS
optimistic concurrency PASS
Storage PASS quando rilevante
functional parity PASS
cache/scope teardown PASS
zero direct write non previsto
zero legacy fallback
zero dual-write
authority unica configurata
```

Quando esistono blocker non ancora remoti, la relativa destructive command deve risultare esplicitamente fail-closed.

---

## 32. Zero legacy writer

Prima del cutover devono essere rimossi tutti i writer locali appartenenti alla capability.

Non è sufficiente migrare la schermata principale se restano:

```text
modal
bulk action
utility
legacy gateway
```

che scrivono ancora `jsonDb`.

---

## 33. Zero legacy reader autoritativo

Anche tutti i reader autoritativi della capability devono utilizzare la nuova authority.

Possono restare consumer locali soltanto per domini non ancora migrati.

---

## 34. Cache

Al cambio di:

```text
Auth User
Workspace
authority
```

la cache del vecchio scope viene invalidata o eliminata.

Il primo risultato dopo il cutover viene letto nuovamente dalla nuova authority.

La vecchia cache locale non viene copiata nel nuovo Query cache come dato remoto verificato.

---

## 35. Subscription

Le subscription appartenenti al vecchio scope/adapter vengono smontate.

Non devono esistere contemporaneamente:

```text
jsonDb subscription
+
Supabase subscription
```

che alimentano la stessa capability.

---

# Rollback

## 36. Prima del primo write remoto

Prima che Supabase abbia ricevuto business mutation autoritative reali, il cutover può essere abortito e l’adapter precedente può restare authority.

---

## 37. Dopo il primo write remoto

Dopo:

```text
Supabase business COMMIT
```

il LocalDatabase è potenzialmente stale.

Non è quindi consentito:

```text
problema
→ torna al local adapter
```

come rollback automatico.

---

## 38. Recovery post-cutover

Dopo il cutover i problemi vengono gestiti tramite:

```text
fix applicativo
nuova migration correttiva
database recovery
forward fix
```

non tramite fallback locale.

Rollback del frontend e rollback dei dati sono concetti distinti.

Una vecchia versione dell’app che utilizza `jsonDb` non può essere ripubblicata come authority dopo che Supabase ha accumulato nuove mutation.

---

# Strategia deploy

## 39. Expand → cutover → cleanup

La transizione segue:

```text
1. aggiungi schema/function compatibili
2. implementa adapter/command/query
3. esegui test e gate
4. cambia authority
5. verifica
6. elimina legacy più avanti
```

Il cleanup distruttivo non viene eseguito nello stesso momento dell’introduzione della nuova persistence.

---

## 40. S2

Introduce:

```text

migration
Auth
Profile
Workspace
Membership
RLS
Storage foundation
seed/test
```

senza forzare immediatamente il cutover di tutti i business domain.

---

## 41. S3

Introduce:

```text
Supabase client
repository adapter
command adapter
query layer
cache/invalidation
Storage port

```

senza fallback automatico.

---

## 42. S4

Cutover:

```text
Contacts
Buildings
Drafts
```

Con guard transitori:

```text
DeleteContact
→ fail-closed fino a Tenant/Lease

DeleteBuilding
→ fail-closed fino a Property
```

---

## 43. S5

Cutover:

```text
Properties
Tenants
Property/Tenant files
```

Dopo Property cutover:

```text
DeleteBuilding
→ completamente enforceable da Supabase
```

Restano temporaneamente fail-closed:

```text
DeleteContact
DeleteProperty

```

quando i relativi blocker dipendono ancora da S6.

---

Cutover:

```text

Payments
Lease Activity
Communications
Signature
Lease Documents
financial read-model
```

Dopo il relativo gate, Supabase possiede anche i principali historical blocker.

Possono quindi essere rimosse le guard transitorie sulle delete precedenti quando tutti i relativi invariant sono remotamente verificabili.

---

## 45. S7

S7 completa il cleanup:

```text

jsonDb runtime
local seed runtime
legacy migration/read-repair
Data URL
placeholder collection
legacy subscriptions
residual local adapters
```

e chiude il final Storage audit e la QA multi-user/concurrency.

# Dataset locale

## 46. Nessuna continuity guarantee

I dati presenti attualmente nel database locale sono dati di sviluppo/collaudo.

Il cutover non garantisce che:

```text
record locale X
→ record Supabase X
```

La baseline da preservare è:

```text
comportamento
business rule
atomicità
lifecycle
UX rilevante
read-model
authorization
```

non il contenuto del dataset locale.

---

## 47. Dataset rappresentativo

Il nuovo seed può riprodurre scenari funzionalmente equivalenti:

```text
Building con Property
Tenant con Contact
Lease con Payment
record archived
multi-workspace
member/revoked member
```

utilizzando però entity target-native e nuovi UUID sintetici.

Non viene prodotta una copia convertita del vecchio database.

---

# Empty, error e repair

## 48. Empty vs failure

Il Query adapter distingue sempre:

```text
success + zero rows
```

da:

```text
network error
RLS error
database error
```

Una risposta vuota non attiva fallback.

Un errore remoto non viene trasformato in una lista vuota.

---

## 49. Nessun read-repair

Nel target:

```text
SELECT
→ nessuna mutation
```

Non vengono portati nel normale read path i comportamenti locali:

```text
normalize
repair
rebuild relation
generate Payment
fix status
persist corrected DB
```

Uno stato invalido richiede:

```text
migration
maintenance
command
```

esplicita.

---

## 50. Future data migration

Una futura modifica dello schema che richieda trasformazioni sui dati autoritativi può usare una migration/backfill versionata.

Questo non costituisce read-repair e non riapre il modello legacy.

---

# Contratto finale

Il lifecycle della persistence diventa:

```text
FASE LOCALE

jsonDb
→ authority

        ↓

SUPABASE PREPARATO

migration
RLS
command
query
Storage
seed/test
gate

        ↓

CUTOVER ESPLICITO

Supabase
→ unica authority

LocalDatabase
→ legacy inert

        ↓

S7

runtime locale eliminato
```
